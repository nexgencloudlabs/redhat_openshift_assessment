Pillar 3: Performance & Scalability

Architecture assessment page for validating bare-metal compute optimization, NUMA alignment, high-performance networking, memory tuning, hardware-aware scheduling, real-time processing, autoscaling, and storage I/O controls.

Use note: This page is a consulting assessment artefact for OpenShift architecture and operations review. It is not an official Red Hat methodology. Validate technical statements and command syntax against the target OpenShift version and client environment before use.

Performance and Scalability define the platform's capability to deliver predictable transaction latency, efficient resource utilization, and elastic capacity under changing workload demand. For OpenShift environments supporting containerized workloads and OpenShift Virtualization on bare-metal infrastructure, these controls validate that CPU, memory, NUMA topology, network acceleration, specialized hardware, autoscaling, and storage I/O are configured through tested, policy-driven, and evidence-backed performance practices.

The expanded pillar also includes platform-wide scalability, resource governance, node stability, pod density, and performance assurance controls so that specialized tuning is validated alongside broader capacity management practices.

Summary of Controls

Pillar 3 contains 14 assessment controls grouped by performance and scalability domain to support deterministic compute behaviour, network acceleration, memory optimization, hardware-aware scheduling, workload and node elasticity, resource governance, node stability, pod density, and evidence-backed performance assurance.

PS-001Compute Optimization

CPU Manager (Static Policy)

High

Description

By default, the Kubernetes scheduler and Linux kernel share CPU resources across all running pods, leading to frequent context switching. The CPU Manager with a static policy allows for the allocation of exclusive, dedicated CPU cores to specific high-performance containers.

Key Aspects of CPU Manager:

  • Core Pinning: Ensures that a container’s threads are pinned to specific physical CPU cores (pCPUs).

  • Isolation: Prevents other pods from using the cores assigned to a "guaranteed" pod, eliminating resource contention.

  • Static Policy: Once a pod is assigned cores, they are reserved for the duration of the pod's lifecycle.

  • Guaranteed QoS: Only pods with specific CPU requests and limits that are equal (integers) will be granted exclusive cores.

What to Assess

  • Kubelet Configuration: Verify the cpuManagerPolicy is set to static in the KubeletConfig resource.

  • QoS Class: Confirm that critical application pods are assigned the Guaranteed Quality of Service (QoS) class (CPU request = CPU limit).

  • Node Status: Verify that nodes have recognized the static policy and are reporting "pinned" cores.

Technical Rationale

Latency-sensitive and high-throughput workloads can be affected by CPU context switching, scheduler contention, and noisy-neighbor activity on shared bare-metal nodes.

  • Predictable Latency: Reducing context switches helps improve p99 latency for transaction-processing, messaging, and other performance-sensitive workloads.

  • L1/L2 Cache Efficiency: Pinning a process to a core helps it use the local CPU cache efficiently, reducing cache thrashing from unrelated workloads.

  • Bare-Metal Performance: Directly leverages physical CPU capacity without hypervisor overhead, supporting deterministic performance for workloads that require dedicated compute resources.

Verification

  • Validation Method: Kubelet configuration audit and pod-level verification.

Verification Steps:

  1. Check Kubelet config:

    oc get kubeletconfig -o yaml | grep cpuManagerPolicy

  2. Check pod QoS:

    oc get pod <pod-name> -o jsonpath='{.status.qosClass}' (Must be Guaranteed).

  3. Verify pinning on node:

    oc debug node/<node-name> -- chroot /host cat /var/lib/kubelet/cpu_manager_state

Evidence

  • Kubelet Config YAML: Export showing the static policy definition.

  • Pod Manifest Snippet: Showing identical CPU requests and limits.

  • CPU Manager State File: A snippet from the master/worker node proving core reservation is active.

Risk Impact

  • High Risk (Performance Jitter): Without core pinning, high-transaction apps may experience random latency spikes, leading to timed-out banking sessions.

  • Operational Risk: Performance becomes unpredictable during peak hours as different pods fight for the same CPU cycles.

  • Efficiency Risk: Sub-optimal use of expensive bare-metal high-frequency processors.

Mapping

  • BNM RMiT (2025): Section 10.5 (Performance Management).

  • CIS Benchmarks v8: Control 18 (Service Software Continuity).

  • NIST SP 800-53: SC-6 (Resource Availability).

PS-002Compute Optimization

Topology Manager (NUMA Alignment)

Moderate

Description

Modern multi-socket bare-metal servers use Non-Uniform Memory Access (NUMA). The Topology Manager coordinates the alignment of CPU, Memory, and PCI devices (like NICs or GPUs) so they all reside on the same NUMA node (the same physical CPU socket).

Key Aspects of Topology Manager:

  • NUMA Affinity: Ensures a pod's CPU and Memory are allocated from the same socket to avoid the "cross-socket" latency penalty.

  • Device Alignment: If a pod uses an SR-IOV NIC (PS-003), the Topology Manager ensures the CPU cores assigned to that pod are the ones directly connected to that NIC.

  • Scope: Operates at the container or pod level.

  • Policy Types: single-numa-node (strict) or best-effort.

What to Assess

  • Kubelet Config: Verify topologyManagerPolicy is set to single-numa-node.

  • Node Hardware: Confirm nodes are multi-socket or have multi-NUMA configurations.

  • Pod Alignment: Audit high-performance pods to see if they are successfully aligned to a single NUMA zone.

Technical Rationale

Data traveling across the QPI/UPI link between sockets can double the latency.

  • Maximum Throughput: Critical for 25Gbps/100Gbps networking and high-speed local AI processing.

  • Eliminating Bottlenecks: Prevents "memory starvation" that occurs when a CPU is waiting for data from a remote NUMA node.

  • Optimization for Bare Metal: Essential for clusters running heavy database workloads or virtualization.

Verification

  • Validation Method: Kubelet and Node status audit.

Verification Steps:

  1. Check Topology policy:

    oc get kubeletconfig -o yaml | grep topologyManagerPolicy

  2. Check NUMA nodes:

    oc debug node/<node-name> -- chroot /host lscpu | grep NUMA

  3. Verify alignment in logs:

    Check journalctl -u kubelet for Topology Manager admission successes/failures.

Evidence

  • KubeletConfig YAML: Showing the single-numa-node policy.

  • Node lscpu Output: Proving the hardware has multiple NUMA nodes to manage.

  • Alignment Log: Snippet from the Kubelet log showing a pod successfully admitted with NUMA alignment.

Risk Impact

  • Moderate Risk (Latency Penalty): Misaligned pods will suffer from sub-optimal performance, adding 10–30% latency to every memory operation.

  • Performance Risk: High-speed network interfaces (SR-IOV) will not reach their rated speeds if CPU cores are on a different NUMA node than the NIC.

  • Efficiency Risk: Inconsistent application performance that is difficult for developers to troubleshoot.

Mapping

  • BNM RMiT (2025): Section 10.5 (Performance Management).

  • CIS Benchmarks v8: Control 18 (Service Software Continuity).

  • NIST SP 800-53: SC-6 (Resource Availability).

PS-003Network Optimization

SR-IOV for High-Performance Networking

High

Description

SR-IOV (Single Root I/O Virtualization) allows supported physical network interface cards (NICs) to expose multiple Virtual Functions (VFs) that can be allocated directly to pods or virtualized workloads. In current OpenShift releases, SR-IOV device configuration and lifecycle management are handled through the SR-IOV Network Operator, SriovNetworkNodePolicy, SriovNetworkNodeState, and SR-IOV network attachment resources.

Key Aspects of SR-IOV:

  • Hardware-Backed Networking: Virtual Functions are exposed from supported physical NICs and advertised as allocatable resources on selected worker nodes.

  • SR-IOV Network Operator: The Operator manages SR-IOV configuration through the sriovnetwork.openshift.io API group and applies node-level policy changes.

  • Node State Inventory: SriovNetworkNodeState resources report detected physical functions, virtual functions, drivers, sync status, and allocatable SR-IOV resources.

  • Network Attachment: Workloads consume SR-IOV through SriovNetwork or NetworkAttachmentDefinition resources, commonly as secondary interfaces through Multus.

  • Deterministic Performance: SR-IOV reduces software switching overhead and supports low-latency, high-throughput network paths for workloads that require predictable network behavior.

What to Assess

  • SR-IOV Network Operator Health: Confirm the SR-IOV Network Operator is installed in the openshift-sriov-network-operator namespace and reports a healthy installation status.

  • Supported Hardware Readiness: Verify that target worker nodes have supported SR-IOV-capable NICs, appropriate firmware, BIOS/UEFI SR-IOV settings, and required driver support.

  • SR-IOV Node Policy: Verify that SriovNetworkNodePolicy resources exist in the sriovnetwork.openshift.io API group and target the correct worker nodes or high-performance node pools.

  • Node State and VF Inventory: Confirm that SriovNetworkNodeState resources show the expected physical functions, virtual functions, drivers, sync status, and allocatable SR-IOV resources.

  • Network Attachment Availability: Confirm that the required SriovNetwork or NetworkAttachmentDefinition resources are available for workloads that need SR-IOV secondary interfaces.

  • Workload Consumption: Verify that workloads request the correct SR-IOV resource name and attach the intended network using the k8s.v1.cni.cncf.io/networks annotation.

  • NUMA / Topology Alignment: For latency-sensitive workloads, confirm that SR-IOV device placement is aligned with CPU and memory placement through Topology Manager where applicable.

  • Change Impact Awareness: Confirm that SR-IOV policy changes are managed through change control because applying a node policy can drain nodes and, in some cases, reboot nodes.

Technical Rationale

Standard software-defined networking (SDN) can consume significant node CPU resources for packet processing under high load.

  • Throughput for Data-Intensive Workloads: Supports high-bandwidth use cases such as data processing, storage replication, AI/ML workloads, and low-latency service communication.

  • Reduced CPU Overhead: Frees CPU cycles for application processing rather than software-based network forwarding.

  • Low Latency: Reduces network jitter for time-sensitive workloads where predictable response times are required.

Verification

  • Validation Method: SR-IOV Operator, node policy, node state, network attachment, and workload consumption audit.

Verification Steps:

  1. Check SR-IOV Operator pods:

    oc get pods -n openshift-sriov-network-operator

  2. Check SR-IOV network node policies:

    oc get sriovnetworknodepolicies -n openshift-sriov-network-operator

  3. Inspect SR-IOV node state and detected NIC/VF inventory:

    oc get sriovnetworknodestates -n openshift-sriov-network-operator -o yaml

  4. Check SR-IOV networks and network attachment definitions:

    oc get sriovnetwork -n openshift-sriov-network-operator
oc get network-attachment-definitions -A

  5. Confirm SR-IOV-capable node labels:

    oc get nodes --show-labels | grep network-sriov

  6. Confirm workload resource requests and network attachment:

    oc get pod <pod-name> -n <namespace> -o yaml | grep -A 20 resources
oc get pod <pod-name> -n <namespace> -o yaml | grep k8s.v1.cni.cncf.io/networks

  7. Confirm secondary interface inside the pod:

    oc exec -n <namespace> <pod-name> -- ip addr

Evidence

  • SR-IOV Operator Status: Output showing the SR-IOV Network Operator pods and installation status are healthy.

  • SR-IOV Node Policy YAML: Export of SriovNetworkNodePolicy resources showing target nodes, resource names, NIC selectors, number of VFs, and driver configuration.

  • SR-IOV Node State YAML: Export showing physical NICs, available VFs, drivers, sync status, and allocatable SR-IOV resources.

  • Network Attachment Evidence: SriovNetwork or NetworkAttachmentDefinition YAML showing the network name, namespace, resource name, VLAN or IPAM configuration where applicable.

  • Workload Manifest Snippet: Pod or deployment YAML showing SR-IOV resource requests and the k8s.v1.cni.cncf.io/networks annotation.

  • Pod Interface List: Output of oc exec <pod> -- ip addr showing the secondary SR-IOV interface and expected driver-backed network path.

  • Performance Benchmark: Results from an approved throughput or latency test, such as iperf, proving expected line-rate or low-latency performance.

  • Change Record: Evidence that SR-IOV policy changes were implemented through change control, including node drain or reboot impact assessment where applicable.

Risk Impact

  • High Risk (Network Bottlenecks): Without SR-IOV for workloads that require deterministic high-throughput networking, traffic may be limited by software switching overhead, causing dropped packets, jitter, or increased latency.

  • Performance Risk: Inability to fully utilize 25GbE, 50GbE, 100GbE, RDMA-capable, or other specialized network hardware investments for workloads that require hardware acceleration.

  • Operational Risk: Incorrect SR-IOV policy configuration can drain or reboot worker nodes unexpectedly if not governed through change control, creating avoidable service disruption.

  • Placement Risk: If SR-IOV resources are not aligned with node labels, workload requests, and topology settings, pods may remain unschedulable or run with suboptimal NUMA placement.

Mapping

  • BNM RMiT (2025): Section 10.3 (Resilience); Section 10.5 (Performance).

  • CIS Benchmarks v8: Control 12 (Network Infrastructure Management).

  • NIST SP 800-53: SC-6 (Resource Availability).

PS-004Memory Optimization

HugePages Allocation

Moderate

Description

By default, Linux uses a 4KB memory page size. For memory-intensive applications (like databases or Java-based banking engines), managing millions of 4KB pages creates significant overhead in the Translation Lookaside Buffer (TLB). HugePages increases the page size to 2MB or 1GB, drastically reducing the number of page table entries.

Key Aspects of HugePages:

  • Pre-allocation: HugePages must be pre-allocated at the node level via the MachineConfig.

  • Non-swappable: HugePages are locked in physical RAM and cannot be swapped to disk, ensuring consistent performance.

  • Pod Requests: Applications must explicitly request HugePages in their container resource specifications.

  • Efficiency: Reduces TLB misses, which is a major source of hidden latency in large-scale applications.

What to Assess

  • Node Configuration: Verify that HugePages are allocated in the MachineConfig or KubeletConfig.

  • Pod Requests: Audit application manifests for hugepages-2Mi or hugepages-1Gi resource requests.

  • Memory Availability: Confirm that HugePages haven't consumed so much RAM that the node's OS is starved.

Technical Rationale

Large applications like Oracle, SQL Server, or large JBoss instances perform significantly better with HugePages.

  • Reduced Memory Management Overhead: Decreases the CPU cycles the kernel spends managing memory addresses.

  • Consistent Response Times: Prevents the latency spikes associated with page faults and memory swapping.

  • Bare-Metal Advantage: Provides direct control over memory architecture that is often obscured in virtualized environments.

Verification

  • Validation Method: Node and Pod resource audit.

Verification Steps:

  1. Check HugePage allocation:

    oc describe node <node-name> | grep -i hugepages

  2. Check pod request:

    oc get pod <pod> -o yaml | grep hugepages

  3. Verify on host:

    oc debug node/<node-name> -- chroot /host cat /proc/meminfo | grep Huge

Evidence

  • MachineConfig YAML: Showing the kernel arguments used to pre-allocate HugePages.

  • Pod Resource YAML: Snippet showing the limits and requests for HugePages.

  • Meminfo Report: Output from a production node proving HugePages are active and being used by the application.

Risk Impact

  • Moderate Risk (Performance Sluggishness): Memory-heavy apps will run slower due to TLB misses, impacting transaction throughput.

  • Efficiency Risk: Higher CPU usage by the kernel to manage memory, leaving less room for application business logic.

  • Operational Risk: If HugePages are requested but not pre-allocated, pods will fail to schedule with an OutOfhugepages error.

Mapping

  • BNM RMiT (2025): Section 10.5 (Performance Management).

  • CIS Benchmarks v8: Control 18 (Service Software Continuity).

  • NIST SP 800-53: SC-6 (Resource Availability).

PS-005Hardware Optimization

Node Feature Discovery (NFD) and Specialized Hardware

Moderate

Description

Node Feature Discovery (NFD) is an operator that detects specialized hardware capabilities on bare-metal nodes (e.g., AVX instructions, GPUs, FPGA, or specific NIC drivers) and exposes them as labels on the Kubernetes node objects.

Key Aspects of NFD:

  • Automated Labeling: Scans the physical hardware and adds labels like feature.node.kubernetes.io/cpu-cpuid.AVX512F=true.

  • Targeted Scheduling: Allows developers to use nodeSelector or affinity (AR-015) to ensure their app runs on the specific hardware it was optimized for.

  • GPU Integration: Essential for AI/ML workloads where pods must land on nodes with specific NVIDIA or AMD GPU hardware.

  • Precision: Ensures that software compiled for specific CPU instructions (like AES-NI for encryption) is never scheduled on a node that doesn't support them.

What to Assess

  • NFD Operator: Verify the Node Feature Discovery Operator is installed and running.

  • Node Labels: Audit node objects to see if they are populated with feature.node.kubernetes.io labels.

  • Scheduling Logic: Check critical application manifests for nodeSelector requirements that match NFD labels.

Technical Rationale

Heterogeneous hardware is common in modern high-performance OpenShift environments, including specialized CPU instruction sets, GPUs, FPGAs, and high-speed network adapters.

  • Hardware Acceleration: Ensures that encryption-heavy, analytics, AI/ML, or performance-optimized workloads are scheduled onto nodes with the correct hardware capabilities.

  • Operational Intelligence: Provides the platform team with a clear inventory of hardware capabilities available across the data center.

  • Security and Performance Optimization: Helps route workloads that benefit from hardware acceleration, such as AES-NI or GPU-enabled processing, to nodes that can execute them efficiently.

Verification

  • Validation Method: Node label and Operator audit.

Verification Steps:

  1. Check NFD pods:

    oc get pods -n openshift-nfd

  2. Review node labels:

    oc get nodes --show-labels | grep feature.node

  3. Verify application affinity:

    oc describe deployment <app-name> (Check for node selectors).

Evidence

  • NFD Resource YAML: Showing the configuration for the feature discovery.

  • Node Label Export: A list of nodes showing the detected hardware features (e.g., AVX, SR-IOV, GPU).

  • Deployment YAML: Snippet showing a pod correctly targeting a specific hardware feature.

Risk Impact

  • Moderate Risk (Sub-optimal Placement): Applications may land on hardware that doesn't support their optimizations, leading to slow performance or crashes.

  • Operational Risk: Manually labeling nodes for hardware features is error-prone and doesn't scale; NFD automates this and removes human error.

  • Performance Risk: Failure to utilize available hardware accelerators (like encryption or AI chips) leads to inefficient software processing.

Mapping

  • BNM RMiT (2025): Section 10.5 (Performance Management); Section 10.1 (Operations Management).

  • CIS Benchmarks v8: Control 18 (Service Software Continuity).

  • NIST SP 800-53: SC-6 (Resource Availability).

PS-006Compute Optimization

Real-Time Kernel for Latency-Sensitive Workloads

High

Description

For workloads that require deterministic response times—such as high-frequency trading engines or real-time payment validation—standard Linux kernel scheduling can introduce unpredictable "micro-latencies." This control involves deploying worker nodes with the Red Hat Enterprise Linux (RHEL) Real-Time Kernel.

Key Aspects of Real-Time Kernel:

  • Preemptible Kernel: Allows the kernel to be interrupted by high-priority tasks even when executing system calls.

  • Deterministic Scheduling: Replaces the "Completely Fair Scheduler" (CFS) with a scheduler that prioritizes task completion timing over overall throughput.

  • Reduced Jitter: Minimizes the variance in execution time, ensuring that a task taking 1ms usually takes 1ms every time.

  • MachineConfig Deployment: Applied via the PerformanceProfile where the realTimeKernel: enabled: true flag is set.

What to Assess

  • Performance Profile: Verify that a PerformanceProfile resource is active and targeting the specific high-performance worker nodes.

  • Kernel Version: Check the running kernel on the target nodes to ensure it contains the rt suffix (e.g., 5.14.0-xxx.rt.el9).

  • Node Labels: Confirm that real-time nodes are correctly labeled to prevent non-RT workloads from consuming their specialized resources.

Technical Rationale

Standard kernels optimize for general-purpose fairness, which can introduce unpredictable micro-latencies when high-priority workloads compete with background system activity.

  • Hard Real-Time Requirements: Supports applications where missing a strict processing window can result in transaction failure, control-loop delay, or service degradation.

  • Eliminating Spikes: Reduces the long tail of latency (p99.9), helping workloads maintain consistent performance regardless of background system load.

  • Bare-Metal Synergy: The real-time kernel is most effective on bare metal where it has direct control over physical hardware interrupts without hypervisor interference.

Verification

  • Validation Method: Node-level kernel audit.

Verification Steps:

  1. Check Performance Profile:

    oc get performanceprofiles

  2. Check Kernel status:

    oc debug node/<node-name> -- chroot /host uname -a (Look for PREEMPT_RT).

  3. Verify RT scheduling:

    oc debug node/<node-name> -- chroot /host cat /sys/kernel/realtime (Should return 1).

Evidence

  • PerformanceProfile YAML: Export showing the realTimeKernel activation.

  • Uname Output: Proof of the RT kernel string from a production node.

  • Latency Benchmark: A report showing reduced p99.9 jitter compared to standard worker nodes.

Risk Impact

  • High Risk (Transaction Timeouts): Critical real-time tasks may be delayed by standard kernel house-keeping, leading to failed banking operations.

  • Operational Risk: Real-time kernels have lower overall throughput; applying them to nodes running "batch" or "web" workloads may actually decrease their performance.

  • Compliance Risk: Inability to meet strict RTOs for high-speed transaction processing as specified in the service design.

Mapping

  • BNM RMiT (2025): Section 10.5 (Performance Management).

  • CIS Benchmarks v8: Control 18 (Service Software Continuity).

  • NIST SP 800-53: SC-6 (Resource Availability).

PS-007Scalability & Resource Elasticity

Vertical & Horizontal Pod Autoscaling (VPA/HPA)

High

Description

Autoscaling ensures that applications can handle sudden bursts in banking traffic without manual intervention. Horizontal Pod Autoscaling (HPA) scales the number of instances, while Vertical Pod Autoscaling (VPA) adjusts the CPU and Memory requests of existing instances.

Key Aspects of Autoscaling:

  • HPA (Scale Out): Monitors metrics like CPU utilization or custom transaction-per-second (TPS) counts to add more replicas (AR-014) when load increases.

  • VPA (Scale Up): Automatically recommends and applies the "Right-Size" for container resources based on historical usage patterns, preventing "OOM" (Out of Memory) kills.

  • Metrics Server Integration: Both depend on the metrics-server or Prometheus to provide real-time resource data.

  • Cooldown Periods: Ensuring the cluster doesn't "thrash" by scaling up and down too rapidly.

What to Assess

  • HPA Coverage: Verify that critical application services requiring scale-out have Horizontal Pod Autoscaler (HPA) configured with appropriate minReplicas, maxReplicas, and scaling metrics such as CPU, memory, or custom application metrics.

  • VPA Usage: Verify that Vertical Pod Autoscaler (VPA) is used selectively for resource recommendation, right-sizing, or workloads suitable for vertical scaling, rather than as a substitute for horizontal scaling.

  • HPA/VPA Compatibility: Confirm that HPA and VPA are not configured in a conflicting manner for the same workload, especially where both attempt to influence CPU or memory behaviour.

  • Scaling Thresholds: Confirm that target utilization values provide sufficient burst capacity and do not trigger excessive scale-up or scale-down behaviour.

  • Node Capacity Alignment: Ensure autoscaling limits are aligned with available bare-metal node capacity to avoid unschedulable pods, resource pressure, or unnecessary contention with other workloads.

Technical Rationale

Application demand is rarely constant; it can increase during peak business periods, scheduled processing windows, product launches, seasonal activity, or unexpected usage spikes.

  • Dynamic Response: Ensures that customer-facing and business-critical services remain responsive during peak load by automatically deploying additional capacity.

  • Resource Efficiency: Automatically scales down during off-peak periods, freeing up bare-metal resources for other workloads such as batch processing, backups, or analytics.

  • Capacity Management: Prevents over-provisioning of expensive RAM and CPU by aligning application capacity with actual demand.

Verification

  • Validation Method: Resource check and scaling test.

Verification Steps:

  1. List HPAs across namespaces:

    oc get hpa -A

  2. Check HPA status and scaling conditions:

    oc describe hpa <name>

    Look for AbleToScale, ScalingActive, current metrics, minReplicas, and maxReplicas.

  3. Review VPA usage and recommendations:

    oc get vpa -A

  4. Check for HPA/VPA overlap on the same workload:

    oc describe vpa <name> -n <namespace>

    Confirm VPA recommendation or update mode is appropriate and does not conflict with HPA scaling behaviour.

Evidence

  • HPA Resource YAML: Showing minReplicas, maxReplicas, target metrics, and scaleTargetRef for critical application services requiring scale-out.

  • HPA Status Output: Output of oc describe hpa <name> showing AbleToScale, ScalingActive, current metrics, and recent scaling events.

  • Prometheus / Grafana Scaling Graph: Screenshot showing pod replica count increasing in correlation with CPU, memory, traffic, or custom application metric spikes.

  • VPA Recommendation Output: Output showing recommended versus actual CPU and memory requests for workloads under VPA review.

  • HPA/VPA Compatibility Review: Evidence that HPA and VPA are not conflicting on the same resource dimension for the same workload.

  • Node Capacity Validation: Cluster capacity or scheduling evidence showing that autoscaling limits are aligned with available bare-metal node capacity and do not create unschedulable pods or node pressure.

Risk Impact

  • High Risk (Capacity Exhaustion): Without autoscaling, a sudden spike in users will crash the application, leading to a service outage.

  • Operational Risk: Manual scaling is too slow to react to real-time traffic spikes, leading to "firefighting" by the operations team.

  • Performance Risk: If HPA is set too aggressively without enough node capacity, it can trigger "Node Pressure," impacting other apps.

Mapping

  • BNM RMiT (2025): Section 10.5 (Performance Management); Section 10.3 (Resilience).

  • CIS Benchmarks v8: Control 18 (Service Software Continuity).

  • NIST SP 800-53: SC-6 (Resource Availability).

PS-008Storage Optimization

I/O Priority and Bandwidth Management (cgroup v2)

High

Description

On bare-metal nodes with shared storage (ODF), different applications often compete for disk I/O. Using cgroup v2 (the default in OpenShift 4.x), this control allows for the enforcement of I/O limits and weights to ensure that high-priority database containers are not "starved" by low-priority logging or backup tasks.

Key Aspects of I/O Management:

  • I/O Weight: Assigning a relative priority (e.g., 1–1000) to pods. High-priority pods get a larger "slice" of the disk's bandwidth during contention.

  • IOPS/Bandwidth Limits: Hard caps on the number of Read/Write operations or Megabytes per second a specific pod can consume.

  • cgroup v2 Hierarchy: Provides a unified controller for CPU, Memory, and I/O, allowing for more granular resource "fairness."

  • Storage Class Interaction: Can be integrated with specific ODF profiles to prioritize different types of application data.

What to Assess

  • Cgroup Version: Confirm the nodes are running cgroup v2 (stat -fc %T /sys/fs/cgroup returns cgroup2fs).

  • Resource Stanza: Review pod manifests for io.weight or specific annotations used by the storage provisioner to limit bandwidth.

  • Contention Monitoring: Check for I/O Wait metrics in Prometheus to identify unmanaged contention.

Technical Rationale

Noisy-neighbor activity at the storage layer is a common cause of unpredictable database, analytics, and stateful application latency.

  • Protecting Core Services: Ensures that batch exports, log rotation, backup jobs, or other I/O-heavy workloads do not starve critical stateful services of disk bandwidth.

  • Predictable Disk Performance: Provides I/O isolation on bare metal similar to what users expect from differentiated storage tiers in cloud environments.

  • SLA Enforcement: Allows the platform team to allocate or protect storage performance for services that require predictable IOPS or throughput.

Verification

  • Validation Method: Node-level cgroup audit and manifest review.

Verification Steps:

  1. Verify cgroup v2:

    oc debug node/<node-name> -- stat -fc %T /sys/fs/cgroup

  2. Check for I/O limits in pods:

    oc describe pod <pod-name> (Look for resource limits).

  3. Monitor disk latency:

    Check irate(node_disk_io_time_seconds_total[5m]).

Evidence

  • Pod Manifest Snippet: Showing I/O weight or limit configurations.

  • Cgroup Status Output: Proof that the unified cgroup v2 controller is active.

  • Prometheus IOPS Graph: Showing a "flat" I/O curve for a pod that has reached its configured limit, protecting the rest of the node.

Risk Impact

  • High Risk (Database Stalls): A rogue pod consuming 100% of the disk's I/O will cause the banking database to hang, resulting in timed-out transactions.

  • Operational Risk: Difficult to troubleshoot "intermittent" database slowness that is actually caused by unrelated background tasks.

  • Performance Risk: Inefficient use of high-speed NVMe storage by allowing "unrestricted" access to all workloads.

PS-009Scalability & Resource Elasticity

Cluster Autoscaler and Machine Autoscaler

High

Description

Cluster Autoscaler and Machine Autoscaler validate the platform's ability to add or remove worker capacity when workloads cannot be scheduled due to insufficient CPU, memory, or placement constraints. This complements PS-007, which scales pods, by ensuring there is enough node capacity for the additional replicas to run.

Key Aspects of Cluster and Machine Autoscaling:

  • ClusterAutoscaler: Defines cluster-wide autoscaling limits such as maximum nodes, cores, memory, GPU resources, and scale-down behaviour.

  • MachineAutoscaler: Applies autoscaling boundaries to specific MachineSets or machine pools that host scalable application workloads.

  • Unschedulable Pod Response: Adds capacity when pending pods cannot be scheduled because no node has sufficient resources or compatible labels.

  • Scale-Down Governance: Removes unused capacity safely while respecting disruption constraints, utilization thresholds, and operational stability.

What to Assess

  • Cluster Autoscaler Scope: Verify that ClusterAutoscaler is configured where the Machine API and infrastructure platform support automated node scaling.

  • Machine Autoscaler Boundaries: Confirm MachineAutoscaler resources exist for relevant worker MachineSets and define appropriate minimum and maximum replica counts.

  • Capacity Limits: Verify that maxNodesTotal, maxCoresTotal, maxMemoryTotal, and similar limits prevent uncontrolled scale-out.

  • Workload Compatibility: Confirm scalable workloads have appropriate requests, labels, tolerations, and placement rules so additional nodes are usable.

  • Scale-Down Safety: Review scale-down delay and utilization thresholds to avoid premature removal of capacity during variable load.

Technical Rationale

  • Pod autoscaling is ineffective if the cluster has no available node capacity to place new replicas.

  • Automated node scaling reduces manual capacity intervention during peak demand and improves recovery from sudden workload growth.

  • Defined upper and lower limits prevent runaway infrastructure expansion while still allowing controlled elasticity.

  • For environments where automated machine scaling is not supported, the same control should be satisfied through documented capacity buffers, manual expansion procedures, and tested provisioning timelines.

Verification

Validation Method: Autoscaler resource inspection and scheduling behaviour review.

Verification Steps:

  1. Check ClusterAutoscaler configuration:

    oc get clusterautoscaler -o yaml

  2. Check MachineAutoscaler resources:

    oc get machineautoscaler -A

  3. Check MachineSets targeted for scaling:

    oc get machinesets -n openshift-machine-api

  4. Review unschedulable pod events:

    oc get events -A | grep -i "FailedScheduling"

Evidence

  • ClusterAutoscaler YAML showing global scale limits and scale-down behaviour.:ClusterAutoscaler YAML showing global scale limits and scale-down behaviour.

  • MachineAutoscaler YAML showing min/max replicas for worker MachineSets or node pools.:MachineAutoscaler YAML showing min/max replicas for worker MachineSets or node pools.

  • Pending pod / scheduling event report showing how autoscaling responds to insufficient capacity.:Pending pod / scheduling event report showing how autoscaling responds to insufficient capacity.

  • Capacity expansion test report demonstrating that additional worker capacity becomes Ready and schedulable.:Capacity expansion test report demonstrating that additional worker capacity becomes Ready and schedulable.

  • Exception record where automated node scaling is not supported, with documented manual capacity expansion procedure and RTO.:Exception record where automated node scaling is not supported, with documented manual capacity expansion procedure and RTO.

Risk Impact

  • High Risk (Scale-Out Failure): HPA may create additional pod replicas, but those pods remain Pending when no node capacity is available.

  • Operational Risk: Manual node expansion may be too slow during demand spikes, causing avoidable service degradation.

  • Cost Risk: Poorly governed autoscaler limits can create uncontrolled infrastructure growth or prevent safe scale-down of idle resources.

Mapping

PS-010Resource Governance

Resource Requests, Limits, Quotas and LimitRanges

High

Description

Resource Requests, Limits, Quotas and LimitRanges establish the foundation for fair scheduling, predictable performance, and namespace-level capacity control. Without accurate CPU and memory requests, OpenShift cannot make reliable scheduling decisions, and autoscaling behaviour becomes inconsistent.

Key Aspects of Resource Governance:

  • Requests: Define the minimum CPU and memory required for scheduling and capacity planning.

  • Limits: Define the maximum resource consumption allowed for a container to prevent uncontrolled usage.

  • ResourceQuota: Controls aggregate namespace consumption across CPU, memory, storage, objects, and services.

  • LimitRange: Provides default and maximum request/limit values for containers within a namespace.

  • QoS Classes: Influences eviction behaviour and performance predictability through Guaranteed, Burstable, and BestEffort classes.

What to Assess

  • Requests and Limits Coverage: Verify that production workloads define appropriate CPU and memory requests, and limits where required by policy.

  • Namespace ResourceQuota: Confirm that namespaces have ResourceQuota objects aligned to approved capacity allocations.

  • LimitRange Defaults: Verify that LimitRange objects define sensible default requests/limits and maximum values to prevent unbounded workloads.

  • QoS Review: Identify BestEffort or poorly sized Burstable workloads in production namespaces and validate exception handling.

  • Autoscaling Dependency: Confirm HPA targets have requests defined, because utilization-based HPA calculations depend on resource requests.

Technical Rationale

  • Accurate requests allow the scheduler to place workloads safely and avoid oversubscription that leads to node pressure.

  • Namespace quotas prevent one team or application from consuming shared cluster resources at the expense of others.

  • LimitRanges reduce configuration gaps by applying default resource boundaries when developers omit resource settings.

  • Proper resource governance improves autoscaling accuracy, chargeback/showback quality, and capacity forecasting.

Verification

Validation Method: Namespace and workload resource policy audit.

Verification Steps:

  1. List ResourceQuotas across namespaces:

    oc get resourcequota -A

  2. List LimitRanges across namespaces:

    oc get limitrange -A

  3. Review workload requests and limits:

    oc get pods -A -o jsonpath='{range .items[*]}{.metadata.namespace}{"/"}{.metadata.name}{" "}{.spec.containers[*].resources}{"\n"}{end}'

  4. Check QoS class for selected pods:

    oc get pod <pod-name> -n <namespace> -o jsonpath='{.status.qosClass}'

Evidence

  • ResourceQuota YAML showing approved CPU, memory, storage, and object limits for production namespaces.:ResourceQuota YAML showing approved CPU, memory, storage, and object limits for production namespaces.

  • LimitRange YAML showing default requests, default limits, and maximum allowed resource values.:LimitRange YAML showing default requests, default limits, and maximum allowed resource values.

  • Workload resource audit report identifying pods without requests or limits.:Workload resource audit report identifying pods without requests or limits.

  • QoS class report showing critical workloads are not unintentionally BestEffort.:QoS class report showing critical workloads are not unintentionally BestEffort.

  • Remediation record showing right-sizing actions taken for workloads with missing or excessive requests.:Remediation record showing right-sizing actions taken for workloads with missing or excessive requests.

Risk Impact

  • High Risk (Resource Contention): Workloads without requests and limits can consume shared node capacity unpredictably and impact neighbouring services.

  • Operational Risk: Pods may be evicted or throttled unexpectedly because resources were not sized or governed consistently.

  • Capacity Risk: Inaccurate requests distort capacity planning, autoscaling decisions, and showback reporting.

Mapping

  • BNM RMiT (2025): Section 10.5 (Capacity Management and Performance); Section 10.1 (Operations Management).

  • CIS Benchmarks v8: Control 1 (Inventory and Control of Enterprise Assets); Control 18 (Service Software Continuity).

PS-011Node Performance Governance

PerformanceProfile and Node Tuning Governance

High

Description

PerformanceProfile and Node Tuning Governance ensures that low-latency and high-performance node configuration is applied through supported OpenShift mechanisms rather than manual node-level changes. This control acts as the governance layer for CPU isolation, reserved CPUs, huge pages, real-time kernel usage, workload hints, and tuned profiles.

Key Aspects of PerformanceProfile Governance:

  • PerformanceProfile: Defines isolated CPUs, reserved CPUs, NUMA topology behaviour, huge pages, and real-time kernel options for selected node pools.

  • Node Tuning Operator: Applies tuned profiles consistently across matching nodes.

  • Targeted Node Selection: Ensures specialized tuning is applied only to nodes intended for performance-sensitive workloads.

  • Change Control: Treats kernel and performance tuning changes as controlled infrastructure changes due to their impact on scheduling and node behaviour.

What to Assess

  • PerformanceProfile Presence: Verify PerformanceProfile resources exist for performance-sensitive node pools where CPU isolation, huge pages, or real-time kernel tuning is required.

  • Node Selector Accuracy: Confirm profiles target only the intended nodes and do not accidentally tune general-purpose workers.

  • Reserved and Isolated CPU Design: Validate that reserved CPUs are sufficient for platform and operating system duties and that isolated CPUs are allocated to application workloads.

  • Tuned Profile Status: Confirm tuned profiles generated by the Node Tuning Operator are applied successfully to the target MachineConfigPool.

  • Change Governance: Review whether performance tuning changes are managed through GitOps or formal change control.

Technical Rationale

  • Performance tuning can significantly alter node scheduling, CPU availability, and kernel behaviour; it must therefore be standardized and auditable.

  • PerformanceProfile provides a supported, declarative method to configure multiple low-latency settings consistently across a node pool.

  • Using targeted profiles avoids applying specialized tuning to workloads that would not benefit from it or may be negatively affected.

  • Governed tuning reduces configuration drift and supports repeatable recovery or rebuild of performance-sensitive nodes.

Verification

Validation Method: PerformanceProfile, MachineConfigPool, and tuned profile inspection.

Verification Steps:

  1. List performance profiles:

    oc get performanceprofiles

  2. Inspect a performance profile:

    oc get performanceprofile <profile-name> -o yaml

  3. Check MachineConfigPool status:

    oc get mcp

  4. Review tuned profiles:

    oc get tuned -A

  5. Check node labels targeted by the profile:

    oc get nodes --show-labels | grep -i performance

Evidence

  • PerformanceProfile YAML showing isolated CPUs, reserved CPUs, huge pages, real-time kernel setting, and nodeSelector.:PerformanceProfile YAML showing isolated CPUs, reserved CPUs, huge pages, real-time kernel setting, and nodeSelector.

  • MachineConfigPool status showing target nodes are Updated and Ready after profile application.:MachineConfigPool status showing target nodes are Updated and Ready after profile application.

  • Node Tuning Operator / tuned profile export showing generated tuning configuration.:Node Tuning Operator / tuned profile export showing generated tuning configuration.

  • Change approval or Git commit history for performance tuning changes.:Change approval or Git commit history for performance tuning changes.

  • Benchmark or validation report showing workload performance after tuning.:Benchmark or validation report showing workload performance after tuning.

Risk Impact

  • High Risk (Node Instability): Incorrect CPU isolation or kernel tuning can starve system daemons and make nodes unstable.

  • Performance Risk: Untuned or inconsistently tuned nodes can create unpredictable latency across replicas of the same workload.

  • Operational Risk: Manual tuning creates snowflake nodes that are difficult to troubleshoot, patch, or recover.

PS-012Node Performance Governance

System Reserved Resources and Node Stability

High

Description

System Reserved Resources and Node Stability validates that each worker node reserves enough CPU and memory for the operating system, kubelet, CRI-O, and platform services. This prevents application workloads from starving node-level components and causing NodePressure, evictions, or instability.

Key Aspects of Node Resource Reservation:

  • systemReserved: Reserves CPU and memory for node system daemons and platform processes using supported OpenShift configuration.

  • AutoSizingReserved: Uses OpenShift automatic reservation behaviour where available to calculate suitable reserved resources for worker nodes.

  • Eviction Thresholds: Defines when kubelet should evict pods to protect node health during memory, disk, or inode pressure.

  • Performance Profile Interaction: Ensures reserved CPUs in PerformanceProfile nodes are handled separately and intentionally.

What to Assess

  • Reservation Configuration: Verify supported system resource reservation is enabled or explicitly configured for each relevant MachineConfigPool.

  • Unsupported Settings Review: Confirm the design does not rely on unsupported kubeReserved configuration for OpenShift nodes.

  • Node Pressure Monitoring: Review alerts and events for MemoryPressure, DiskPressure, PIDPressure, and frequent pod evictions.

  • Eviction Thresholds: Confirm eviction settings protect node stability without causing unnecessary workload disruption.

  • Specialized Node Handling: Validate that performance-profile, infra, and storage nodes have reservation values appropriate to their workload type.

Technical Rationale

  • Node-level daemons must remain healthy for the platform to schedule, start, stop, monitor, and recover workloads.

  • If applications consume all available CPU or memory, kubelet and CRI-O can become unstable, leading to pod evictions or node NotReady conditions.

  • Automatic or explicitly governed reservations provide a safer baseline for shared worker nodes.

  • Reservation settings must be aligned with pod density, workload type, and performance tuning profiles.

Verification

Validation Method: Kubelet configuration, node condition, and event review.

Verification Steps:

  1. Review KubeletConfig resources:

    oc get kubeletconfig -o yaml

  2. Check MachineConfigPools:

    oc get mcp

  3. Review node pressure conditions:

    oc get nodes -o custom-columns=NAME:.metadata.name,STATUS:.status.conditions[-1].type

  4. Check recent eviction or pressure events:

    oc get events -A | grep -Ei "Evicted|MemoryPressure|DiskPressure|PIDPressure"

  5. Inspect node allocatable resources:

    oc describe node <node-name> | grep -A 8 Allocatable

Evidence

  • KubeletConfig or cluster configuration showing supported systemReserved / automatic reservation settings.:KubeletConfig or cluster configuration showing supported systemReserved / automatic reservation settings.

  • Node allocatable report showing reserved capacity has been accounted for.:Node allocatable report showing reserved capacity has been accounted for.

  • Node pressure event history demonstrating whether resource pressure is recurring.:Node pressure event history demonstrating whether resource pressure is recurring.

  • Prometheus or Grafana graph showing node CPU, memory, disk pressure, and eviction trends.:Prometheus or Grafana graph showing node CPU, memory, disk pressure, and eviction trends.

  • Exception or design note for performance-profile nodes where reservedSystemCPUs is used.:Exception or design note for performance-profile nodes where reservedSystemCPUs is used.

Risk Impact

  • High Risk (Node Instability): Insufficient reserved resources can cause kubelet, CRI-O, and system daemons to become resource-starved.

  • Operational Risk: Frequent evictions and NodePressure events can create unstable application behaviour and difficult troubleshooting.

  • Capacity Risk: Over-reservation reduces usable application capacity, while under-reservation increases the risk of platform instability.

PS-013Scalability & Resource Elasticity

Pod Density and Cluster Sizing

High

Description

Pod Density and Cluster Sizing validates that worker-node sizing, pod density, control-plane capacity, network ranges, and object growth remain within supported OpenShift scalability boundaries. This prevents clusters from becoming unstable as workload count and API object volume increase.

Key Aspects of Pod Density and Sizing:

  • maxPods: Defines how many pods can run on each node before scheduler placement is restricted.

  • Node Sizing: Aligns CPU, memory, storage, and network capacity to the expected number and type of workloads.

  • Control Plane Load: Considers API object count, namespace growth, event volume, and etcd pressure as scalability factors.

  • Network Capacity: Ensures clusterNetwork and serviceNetwork ranges are sized to support expected pod and service growth.

What to Assess

  • Pod Density Settings: Verify maxPods and related kubelet settings are appropriate for node size and workload profile.

  • Cluster Object Growth: Review namespace, pod, service, route, secret, ConfigMap, and CRD object counts for growth trends.

  • Control Plane Capacity: Validate that API server and etcd metrics remain healthy under expected object and request volume.

  • Network Range Capacity: Confirm pod and service CIDR ranges are sufficient for expected cluster growth.

  • Density Testing: Review performance or scale-test results proving that the selected pod density does not create node pressure or excessive API load.

Technical Rationale

  • Scaling a cluster is not only about adding nodes; excessive pod density or object count can overload kubelet, API server, networking, and etcd.

  • A pod density value that works for small stateless containers may not be suitable for heavier workloads, service mesh sidecars, or high-log-volume applications.

  • Sizing should account for current demand, expected growth, failure capacity, and upgrade behaviour.

  • Validated density limits reduce the risk of performance degradation caused by uncontrolled platform growth.

Verification

Validation Method: Kubelet configuration, object count, and cluster capacity review.

Verification Steps:

  1. Check maxPods configuration:

    oc get kubeletconfig -o yaml | grep -i maxPods

  2. Count pods by node:

    oc get pods -A -o wide | awk '{print $8}' | sort | uniq -c | sort -nr

  3. Review node allocatable and usage:

    oc adm top nodes

  4. Review API object counts:

    oc get ns --no-headers | wc -l && oc get pods -A --no-headers | wc -l

  5. Check cluster network sizing:

    oc get network.config/cluster -o yaml | grep -A 10 clusterNetwork

Evidence

  • KubeletConfig YAML showing maxPods or related pod density configuration.:KubeletConfig YAML showing maxPods or related pod density configuration.

  • Pod distribution report showing pods per node and density hot spots.:Pod distribution report showing pods per node and density hot spots.

  • Cluster object inventory report showing namespace, pod, service, route, and secret counts.:Cluster object inventory report showing namespace, pod, service, route, and secret counts.

  • Prometheus / Grafana dashboards showing API server latency, etcd metrics, and node pressure under normal and peak load.:Prometheus / Grafana dashboards showing API server latency, etcd metrics, and node pressure under normal and peak load.

  • Capacity forecast showing expected pod, node, and object growth over the planning horizon.:Capacity forecast showing expected pod, node, and object growth over the planning horizon.

Risk Impact

  • High Risk (Cluster Degradation): Excessive pod density can overload kubelet, CRI-O, node networking, and logging pipelines.

  • Control Plane Risk: Rapid object growth increases API and etcd load, affecting cluster responsiveness and upgrade stability.

  • Operational Risk: Poorly sized CIDR ranges or node pools can require disruptive reconfiguration when the cluster grows.

PS-014Performance Assurance

Performance Baseline and Load Testing

High

Description

Performance Baseline and Load Testing validates that the platform and critical workloads have measurable baseline performance, tested scaling behaviour, and documented capacity forecasts. This converts performance tuning from a configuration exercise into an evidence-backed assurance practice.

Key Aspects of Performance Assurance:

  • Baseline Metrics: Establishes normal CPU, memory, storage I/O, network throughput, API latency, and application response-time baselines.

  • Load and Stress Testing: Tests the platform under expected peak, burst, failure, and recovery scenarios.

  • p95/p99 Latency: Measures tail latency rather than relying only on averages.

  • Capacity Forecasting: Uses historical trends and load-test results to forecast hardware, storage, and network growth.

What to Assess

  • Baseline Coverage: Verify baseline metrics exist for platform components, worker nodes, storage, networking, and critical application services.

  • Load-Test Evidence: Confirm load tests cover normal peak, burst, failover, node maintenance, and recovery scenarios.

  • Latency and Throughput Targets: Validate p95/p99 latency, throughput, error rate, and saturation targets are defined and monitored.

  • Scaling Behaviour: Review whether HPA, VPA, ClusterAutoscaler, and MachineAutoscaler behaviour has been tested rather than only configured.

  • Capacity Forecast: Confirm forecast reports use historical metrics and expected demand growth to guide hardware and subscription planning.

Technical Rationale

  • Configuration alone does not prove that a platform can meet performance and scalability expectations under real load.

  • Baselines help teams detect performance regression after upgrades, tuning changes, application releases, or infrastructure refreshes.

  • Load testing exposes bottlenecks in scheduling, storage, network, ingress, API server, and application dependencies before production incidents occur.

  • Capacity forecasting supports planned expansion rather than emergency procurement.

Verification

Validation Method: Performance evidence review and metric validation.

Verification Steps:

  1. Review node utilization:

    oc adm top nodes

  2. Review pod utilization:

    oc adm top pods -A

  3. Query historical metrics in Prometheus:

    histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket[5m])) by (le))

  4. Check HPA behaviour during test:

    oc describe hpa <name>

  5. Review cluster events during load test:

    oc get events -A --sort-by=.lastTimestamp | tail -50

Evidence

  • Performance baseline report covering CPU, memory, network, storage, API latency, and application response time.:Performance baseline report covering CPU, memory, network, storage, API latency, and application response time.

  • Load-test report showing test profile, concurrency, throughput, error rate, p95/p99 latency, and saturation points.:Load-test report showing test profile, concurrency, throughput, error rate, p95/p99 latency, and saturation points.

  • Autoscaling test evidence showing pod and node scaling behaviour under controlled load.:Autoscaling test evidence showing pod and node scaling behaviour under controlled load.

  • Regression comparison showing current performance against previous release or infrastructure baseline.:Regression comparison showing current performance against previous release or infrastructure baseline.

  • Capacity forecast showing expected growth and recommended scaling actions.:Capacity forecast showing expected growth and recommended scaling actions.

Risk Impact

  • High Risk (Unproven Scalability): The platform may appear healthy during normal operation but fail during peak demand or failure scenarios.

  • Performance Risk: Hidden bottlenecks can remain undetected until users experience slow response times or failed transactions.

  • Planning Risk: Lack of baseline and forecast data leads to reactive capacity decisions and avoidable procurement urgency.
