Pillar 1: Availability & Resilience

Architecture assessment page for validating control plane resilience, workload availability, storage readiness, bare-metal networking, OpenShift Virtualization readiness, and operational recovery controls.

Use note: This page is a consulting assessment artefact for OpenShift architecture and operations review. It is not an official Red Hat methodology. Validate technical statements and command syntax against the target OpenShift version and client environment before use.

Availability and Resilience define a platform's capacity to maintain continuous service uptime and automatically recover from hardware, software, or network disruptions. Unlike legacy virtualization environments that often rely on manual intervention or bolted-on high-availability clusters, Red Hat OpenShift integrates these principles directly into its declarative, Kubernetes-native architecture. Availability ensures that the management control plane, storage foundations, and physical networking lack single points of failure. Resilience goes a step further by introducing automated self-healing mechanisms—such as node fencing, dynamic workload rescheduling, Pod Disruption Budgets, and non-disruptive VM Live Migrations. Together, these controls guarantee that both modern containerized applications and traditional virtual machines can survive unexpected outages and routine maintenance with zero or minimal impact on business operations.

AR-001Control Plane

Control Plane Quorum in OpenShift Container Platform 4.x

Critical

Description

In OpenShift Container Platform 4.x, Control Plane Quorum refers to the mechanism that ensures high availability (HA) and data consistency for etcd, the distributed key-value store that maintains the cluster's configuration and state. Quorum represents the minimum number of control plane (master) nodes that must be online and able to communicate for the cluster to make decisions and accept configuration updates.

Key Aspects of Control Plane Quorum:

  • Etcd-Based: OpenShift 4.x relies on etcd for cluster state. Quorum ensures that write operations occur only when a majority of members agree, maintaining consistency.

  • Majority Rule: In a standard 3-node control plane, quorum is 2 ($n/2 + 1$). The cluster remains operational with one node down but loses quorum if two nodes fail.

  • Minimum Nodes: Although reduced-node topologies exist, a minimum of 3 control plane nodes is required for a highly available production deployment.

  • Even Node Limitation: Even-numbered control planes (e.g., 4 nodes) offer no HA advantage because quorum still requires more than half (e.g., 3/4). Therefore, an odd number of control plane nodes (3, 5, etc.) is recommended.

  • Split-Brain Prevention: If network partitions occur, only the partition containing most control plane nodes remains active, preventing conflicting or corrupt cluster state.

  • Operation Halt on Quorum Loss: If healthy nodes fall below quorum, etcd stops accepting writes and the API server becomes effectively read-only to protect cluster integrity.

What to Assess

  • Standard HA Requirement: Verify that a minimum of three control plane nodes is present.

  • Active Majority: Confirm that at least two of the three nodes (for a 3-node setup) are active and participating in the Raft index.

  • Enhanced Resilience: For Bare Metal environments requiring higher stability, verify if 5 nodes are used, requiring a minimum of 3 to maintain quorum.

  • Edge Topologies: If a 2-node edge deployment is used, verify the presence and health of a "lightweight arbiter node" acting as the third etcd member.

  • Operator Status: Assess the etcd and kube-apiserver Cluster Operators for any "Degraded" or "Unavailable" signals.

Technical Rationale

Maintaining quorum is the foundation of cluster stability and data integrity, particularly in a Bare Metal environment where hardware or power failures are inevitable.

  • Consensus Integrity: By requiring a majority for every transaction, the cluster ensures that the "Source of Truth" remains identical across all nodes, even during infrastructure instability.

  • Fault Tolerance: A 3-node or 5-node configuration allows for "N-1" fault tolerance, ensuring that scheduled maintenance or a single node crash does not halt business operations.

  • CAP Theorem Alignment: etcd prioritizes Consistency and Partition Tolerance (CP). This is essential for financial institutions (like Agrobank) where an incorrect cluster state could lead to inconsistent application data or security policy bypasses.

Verification

Technical verification is performed via the OpenShift CLI and internal etcd diagnostics:

  • Validation Method: Quorum is verified via etcd status. If a majority of nodes are not active, the etcd cluster Operator triggers alerts.

Verification Steps:

  1. Confirm all master nodes are in Ready status:

    oc get nodes -l node-role.kubernetes.io/master

  2. Check the health of the etcd operator:

    oc get clusteroperators etcd

  3. Verify synchronization across the cluster:

    oc rsh -n openshift-etcd -c etcd $(oc get pods -n openshift-etcd -l app=etcd -o name | head -1) etcdctl endpoint status --cluster -w table

Evidence

  • Operator Status Log: A timestamped export of oc get clusteroperators etcd.

  • Member Health Table: Output of etcdctl member list -w table showing all member IDs and status.

  • Node Role Report: A list of master nodes showing hostnames and failure domain distribution labels.

  • Dashboard Artefact: A PDF export of the OpenShift etcd Monitoring Dashboard showing stable quorum and leader presence.

Risk Impact

  • High Risk (Quorum Loss): If healthy nodes fall below the majority, the cluster will stop accepting all writes. This results in an immediate halt to all CI/CD pipelines, autoscaling events, and administrative changes.

  • Critical Risk (Data Corruption): If a "split-brain" occurs (rare but possible without strict quorum enforcement), the etcd database may become inconsistent, necessitating a complex and time-consuming manual restore from backups.

  • Operational Risk: Frequent loss of quorum due to poor hardware or network performance leads to "flapping" services, causing application downtime and inconsistent end-user experiences.

Mapping

  • BNM RMiT (2025): Section 10.3 (Availability and Resilience); Section 11.1 (Data Integrity).

  • CIS Benchmarks v8: Control 11 (Data Recovery).

  • NIST SP 800-53: CP-2 (Contingency Plan); SC-5 (DoS Protection).

AR-002Control Plane

etcd Storage Performance and Latency

Critical

Description

In a bare-metal OpenShift deployment, etcd performance is almost entirely dependent on the I/O characteristics of the underlying storage. Because etcd uses a leader-based consensus protocol, every write must be persisted to a Write-Ahead Log (WAL) and acknowledged by a majority of nodes before it is considered committed.

Key Aspects of etcd Storage Performance:

  • Fsync Latency: The primary metric for etcd health is the fsync duration. This is the time it takes to flush data from the kernel's disk cache to the physical storage media.

  • Sequential I/O: etcd writes to the WAL sequentially. Any interference from other high-I/O processes on the same disk can cause "head contention," significantly increasing latency.

  • Resource Contention: On bare metal, if the operating system or other containers are competing for disk bandwidth, etcd may miss its internal "heartbeat" intervals.

  • Strict p99 Requirements: For a "Well-Architected" cluster, the 99th percentile (p99) of disk synchronization should consistently remain below 10ms.

What to Assess

  • Storage Media Type: Confirm that master nodes are utilizing Enterprise-grade SSD or NVMe. Standard HDDs are non-compliant for production control planes.

  • Dedicated Mounts: Verify if /var/lib/etcd is mounted on a dedicated physical device or high-speed partition to isolate it from OS and container logs.

  • Latency Metrics: Assess the historical fsync duration over a 24-hour window to ensure no spikes above the 10ms threshold.

Technical Rationale

For financial institutions, storage latency isn't just a performance metric; it is a stability requirement.

  • Stability of the API: High disk latency causes the etcd leader to step down, triggering constant re-elections that freeze the OpenShift API.

  • Prevention of "Split-Brain": Fast disk I/O ensures that all members of the quorum stay synchronized in real-time, reducing the risk of data divergence during heavy load.

  • Bare Metal Advantage: Utilizing local NVMe or Enterprise SSDs on bare metal allows OpenShift to bypass the overhead of virtualized storage layers, provided the disks are correctly optimized.

Verification

Technical verification is performed via Prometheus metrics and the etcdctl performance suite:

  • Validation Method: Performance is verified by measuring the time taken for a standardized write load to be committed to disk.

Verification Steps:

  1. Direct Performance Test: Run a 60-second performance check:

    oc rsh -n openshift-etcd -c etcd $(oc get pods -n openshift-etcd -l app=etcd -o name | head -1) etcdctl check perf

  2. Metric Analysis: Query Prometheus for the p99 WAL sync duration:

    histogram_quantile(0.99, sum(rate(etcd_disk_wal_fsync_duration_seconds_bucket[5m])) by (le))

Evidence

  • etcd Perf Output: A log of the etcdctl check perf showing a "PASS" status for the defined workload.

  • Storage Configuration: Output of lsblk or /etc/fstab from a master node showing the mount point for etcd.

  • Prometheus Graph: A screenshot or PDF export of the "etcd Disk Sync" dashboard showing p99 latency consistently below 10ms.

Risk Impact

  • High Risk (Cluster Instability): Latency above 10ms leads to frequent leader re-elections, causing the OpenShift web console and CLI to become intermittently unresponsive.

  • Critical Risk (Cascading Failure): In high-churn environments (e.g., heavy pod scaling), slow storage can cause the etcd database to fall so far behind that it cannot recover without a manual restoration.

  • Operational Risk: Users will experience "Timeout" errors during deployment, and monitoring systems may trigger false-positive alerts regarding master node health.

Mapping

  • BNM RMiT (2025): Section 10.5 (Performance Management); Section 10.3 (Resilience).

  • CIS Benchmarks v8: Control 8 (Audit Log Management - ensuring log persistence speed).

  • NIST SP 800-53: CP-9 (System Backup); SI-13 (Predictable Failure Analysis).

AR-003Infrastructure Resilience

Automated Node Remediation (Fencing)

Critical

Description

In a bare-metal environment, if a node becomes unresponsive due to hardware failure, kernel panic, or network isolation, the cluster must ensure the node is truly "dead" before recovering workloads. Automated Node Remediation (Fencing) is the mechanism that detects an unhealthy node and "fences" it typically by forcing a reboot—to prevent data corruption and allow for safe workload migration.

Key Aspects of Automated Node Remediation:

  • Self-Node Remediation: Utilizing the Self-Node Remediation (SNR) Operator to allow a node to reboot itself if it loses connection to the API server for a specified duration.

  • Fencing Logic: Ensures that a "zombie" node cannot continue to access shared storage (PVs) or external resources while the cluster attempts to restart those same services on a healthy node.

  • Reboot-Based Recovery: Prioritizes a hard reboot to clear transient hardware or kernel errors, returning the node to a "Ready" state without manual intervention.

  • Out-of-Band Integration: In advanced bare-metal setups, this may integrate with the Baseboard Management Controller (BMC) via IPMI or Redfish to power-cycle the server.

What to Assess

  • Operator Installation: Confirm the Node Health Check and Self-Node Remediation operators are installed and in a "Succeeded" state.

  • Health Check Policy: Verify that a NodeHealthCheck (NHC) resource is defined for both worker and infra roles.

  • Remediation Strategy: Ensure the remediation strategy is set to SelfNodeRemediation and that the timeout values are tuned to avoid "flapping" during minor network blips.

Technical Rationale

For stateful banking applications and Virtual Machines (OpenShift Virtualization), data integrity is paramount.

  • Prevention of Data Corruption: Fencing prevents two nodes from simultaneously mounting the same ReadWriteOnce (RWO) volume, which would otherwise result in filesystem corruption.

  • Reduced MTTR: Automating the reboot of failed hardware significantly reduces the Mean Time to Recovery (MTTR) compared to manual sysadmin intervention.

  • High Availability for VMs: In a bare-metal context, if a host running a critical database VM hangs, fencing is the only way to safely trigger the VM's restart on a secondary host.

Verification

Technical verification confirms the automated policies are active in the cluster:

  • Validation Method: Review the custom resources governing node health and remediation actions.

Verification Steps:

  1. Check NHC status:

    oc get nodehealthchecks -A

  2. Check SNR status:

    oc get selfnoderemediations -n openshift-operators

  3. Inspect NHC configuration to confirm it targets the correct nodes:

    oc describe nodehealthcheck <name>

Evidence

  • NHC Configuration Log: Output of oc get nodehealthcheck -o yaml.

  • Operator Pod Status: A list of pods in the openshift-operators namespace related to remediation.

  • Event Logs: Historical oc get events -A showing any instances where a node was successfully remediated by the operator.

Risk Impact

  • High Risk (Data Corruption): Without fencing, a semi-responsive node may continue writing to storage while a recovered instance of the same app is also writing, leading to catastrophic database failure.

  • Critical Risk (Service Stalls): Critical workloads (especially VMs) will remain in an "Unknown" state indefinitely if the underlying host hangs, causing prolonged application downtime.

  • Operational Risk: Increases reliance on 24/7 manual monitoring and manual power-cycling of servers, which is prone to human error.

Mapping

  • BNM RMiT (2025): Section 10.3 (Availability and Resilience); Section 10.4 (Recovery Time Objective).

  • CIS Benchmarks v8: Control 11 (Data Recovery).

  • NIST SP 800-53: CP-2 (Contingency Plan); PE-13 (Fire Protection/Power - specifically hardware availability).

Machine Health Checks

High

Description

Machine Health Checks (MHC) provide an automated monitoring layer that observes the state of the Machine objects within an OpenShift cluster. While AR-003 focuses on "fencing" a crashed node, MHC focuses on the lifecycle of the machine—identifying nodes that are "NotReady" or meeting specific unhealthy criteria and triggering a replacement or repair.

Key Aspects of Machine Health Checks:

  • Condition Monitoring: MHC monitors for specific node conditions such as Ready=False, NetworkUnavailable=True, or DiskPressure=True.

  • Remediation Thresholds: Allows for a grace period (e.g., 5 minutes). If the condition persists beyond this time, the machine is marked for remediation.

  • MachineSet Integration: In a bare-metal environment using the Machine API, the MHC can trigger the deletion and re-provisioning of a host if the hardware supports automated provisioning.

  • Short-Circuit Protection: Prevents the MHC from remediating too many nodes at once (e.g., if more than 40% of the cluster is unhealthy, it stops to prevent a total cluster wipe-out).

What to Assess

  • MHC Definitions: Ensure MachineHealthCheck resources exist for each MachineSet (Master, Worker, Infra).

  • Unhealthy Conditions: Verify the defined conditions match the criticality of the banking workloads (e.g., monitoring DiskPressure on nodes running high-I/O databases).

  • MaxUnhealthy Limit: Confirm that the maxUnhealthy parameter is set to a safe percentage to prevent mass-remediation during a top-of-rack switch failure.

Technical Rationale

Maintaining a healthy fleet of nodes is essential for predictable application performance.

  • Declarative Infrastructure: MHC ensures that the actual state of the hardware fleet matches the desired state defined in the MachineSet.

  • Error Isolation: Automatically removes "gray failure" nodes (nodes that are partially functional but performing poorly) from the active scheduling pool.

  • Auditability: Provides a clear, automated record of when and why a specific piece of infrastructure was deemed unhealthy and remediated.

Verification

Verification is done by inspecting the Machine API resources:

  • Validation Method: Direct inspection of the MachineHealthCheck custom resources.

Verification Steps:

  1. List all MHCs:

    oc get machinehealthchecks -n openshift-machine-api

  2. Verify target selection:

    oc describe machinehealthcheck <name> -n openshift-machine-api

Evidence

  • MHC Resource YAML: Export of the MachineHealthCheck definitions.

  • Machine Status Log: Output of oc get machines -n openshift-machine-api showing any machines currently undergoing remediation.

  • Controller Logs: Logs from the machine-api-operator showing health check evaluations.

Risk Impact

  • High Risk (Capacity Degradation): Unhealthy nodes that are not remediated will continue to receive pod assignments, leading to "scheduling loops" where pods constantly fail.

  • Operational Risk: Manual intervention is required for common node failures, increasing the workload on the infrastructure team and slowing down recovery.

  • Compliance Risk: Failing to maintain the "Desired State" of the cluster may violate internal SLAs and RMiT resilience requirements.

Mapping

  • BNM RMiT (2025): Section 10.1 (Operations Management); Section 10.3 (Resilience).

  • CIS Benchmarks v8: Control 18 (Service Software Continuity).

  • NIST SP 800-53: SI-2 (Flaw Remediation); SI-4 (Information System Monitoring).

AR-005Workload Resilience

Anti-Affinity Rules

Critical

Description

Anti-Affinity Rules are scheduler instructions that ensure redundant instances (replicas) of a critical application or microservice are physically separated across the cluster's infrastructure. In a bare-metal environment, this ensures that a single hardware failure (server, rack, or PDU) does not result in the total loss of an application service.

Key Aspects of Anti-Affinity:

  • PodAntiAffinity: Prevents multiple pods of the same application from being scheduled on the same host.

  • Topology Keys: Uses keys such as kubernetes.io/hostname (node-level) or topology.kubernetes.io/rack (rack-level) to define the boundary of separation.

  • Hard vs. Soft Enforcement:

    • Required (Hard): The pod will not schedule unless it can find a unique node. Essential for production databases.

    • Preferred (Soft): The scheduler will try to separate pods but will co-locate them if the cluster is at capacity.

  • Workload Diversity: Ensures that "A" and "B" sides of an active-active banking service never share the same physical silicon.

What to Assess

  • Deployment Specs: Review the affinity stanza in application deployment manifests for critical services.

  • Topology Labels: Confirm that nodes are correctly labeled with their physical locations (rack, room, row) to allow the scheduler to make intelligent decisions.

  • Scheduling Balance: Assess the actual distribution of pods across nodes to ensure the anti-affinity rules are functioning as expected.

Technical Rationale

For critical banking services like payment gateways or core ledgers, local redundancy is not enough if the hardware is shared.

  • Blast Radius Limitation: Limits the impact of a single server "Purple Screen of Death" or NIC failure to only one instance of the service.

  • Hardware Maintenance: Allows for the maintenance of a physical server (e.g., firmware updates) without taking the entire application offline.

  • Compliance with Availability Zones: Even in a single data center, anti-affinity simulates "Availability Zones" at the rack level.

Verification

Verification is performed by auditing workload manifests and current pod distribution:

  • Validation Method: Manifest analysis and pod-to-node mapping.

Verification Steps:

  1. Inspect deployment affinity:

    oc get deployment <name> -o yaml | grep -A 15 affinity

  2. Verify pod distribution:

    oc get pods -o wide -l app=<label> (Check that NODE names are unique).

Evidence

  • Application Manifests: YAML snippets showing the podAntiAffinity configuration.

  • Pod Placement Report: A table showing the mapping of critical pods to their respective physical nodes.

  • Node Label Export: A list of nodes and their topology labels (oc get nodes --show-labels).

Risk Impact

  • Critical Risk (Total Service Outage): If all three replicas of a ledger service are scheduled on one bare-metal host, a single hardware failure results in a 100% service outage.

  • Operational Risk: Hardware upgrades become extremely high-risk "all-or-nothing" events because there is no guarantee that redundant pods are safe on other nodes.

  • Performance Risk: Co-locating resource-heavy pods on a single host can lead to "noisy neighbor" effects, degrading the performance of the entire service stack.

Mapping

  • BNM RMiT (2025): Section 10.3 (Availability and Resilience); Appendix 4 (Critical System Design).

  • CIS Benchmarks v8: Control 18 (Service Software Continuity).

  • NIST SP 800-53: SC-6 (Resource Availability); CP-2 (Contingency Plan).

Pod Disruption Budgets (PDB)

High

Description

A Pod Disruption Budget (PDB) is a safety guardrail that limits the number of pods of a replicated application that are down simultaneously from voluntary disruptions. Voluntary disruptions include actions like node drains for bare-metal firmware updates, cluster upgrades, or autoscaling events.

Key Aspects of Pod Disruption Budgets:

  • Minimum Availability: Ensures a specific number or percentage of pods (e.g., minAvailable: 2 or 80%) remain operational at all times.

  • Maximum Inavailability: Alternatively, it can specify the maximum number of pods that can be offline (e.g., maxUnavailable: 1).

  • Scheduler Integration: The oc adm drain command will respect these budgets; it will fail or hang if evacuating a node would violate the PDB, forcing the administrator to intervene or wait.

  • Quorum Protection: Essential for distributed systems (like clustered databases) that require a specific number of members to maintain their own internal quorum.

What to Assess

  • PDB Coverage: Verify that all "Critical" and "Essential" labeled workloads have an associated PDB resource.

  • Budget Logic: Confirm that the minAvailable value is not set to the total number of replicas (which would block all maintenance) but is sufficient for the application's performance baseline.

  • Selector Alignment: Ensure the PDB label selector accurately matches the labels on the application's pods.

Technical Rationale

In a banking environment where high availability is mandated by RMiT, manual errors during maintenance can be catastrophic.

  • Prevention of Accidental Outages: Prevents a platform engineer from accidentally taking down all instances of a service during a routine patch cycle.

  • SLA Enforcement: Guarantees that the "N-1" or "N-2" redundancy planned in the architecture is physically maintained during cluster operations.

  • Safe Automation: Allows automated lifecycle tools (like the Machine Config Operator) to safely roll out OS updates to bare-metal nodes without manual supervision for every pod.

Verification

Verification involves auditing the PDB resources against the running workloads:

  • Validation Method: Resource inspection and simulation of a disruption.

Verification Steps:

  1. List all PDBs in a namespace:

    oc get pdb -n <namespace>

  2. Check the "Allowed Disruptions" column:

    oc get pdb (A value of 0 indicates no more pods can be safely removed).

  3. Inspect a specific PDB:

    oc describe pdb <name>

Evidence

  • PDB Resource List: An export of oc get pdb -A showing all defined budgets.

  • Deployment Mapping: A report linking specific PDBs to their corresponding Deployments or StatefulSets.

  • Drain Test Log: A log of a failed oc adm drain command where the PDB correctly blocked the node evacuation to protect application availability.

Risk Impact

  • High Risk (Service Interruption): Without PDBs, a simple cluster upgrade could restart all pods of a service at once, causing a total blackout.

  • Operational Risk: Maintenance windows become high-stress events where engineers must manually verify pod counts before every action.

  • Compliance Risk: Failure to protect critical workloads during maintenance violates the "Continuous Availability" principles of RMiT.

Mapping

  • BNM RMiT (2025): Section 10.3 (Availability and Resilience); Section 10.1 (Operations Management).

  • CIS Benchmarks v8: Control 18 (Service Software Continuity).

  • NIST SP 800-53: CP-2 (Contingency Plan); SC-6 (Resource Availability).

AR-007Infrastructure Resilience (Virtualization)

Live Migration Storage Readiness

High

Description

For workloads running as Virtual Machines via OpenShift Virtualization, Live Migration is the ability to move a running VM from one bare-metal host to another with zero downtime. This control ensures that the underlying storage architecture is configured to support the high-speed data handoff required for migration.

Key Aspects of Storage Readiness:

  • Shared Storage Requirement: VMs must be backed by persistent volumes (PVs) that support ReadWriteMany (RWX) access modes (e.g., via OpenShift Data Foundation).

  • Storage Class Capability: The storage provider must support the LiveMigration capability, ensuring that locks on the disk can be transitioned between hosts without dropping the filesystem.

  • I/O Consistency: Ensures that disk writes remain consistent during the "dirty page" transfer phase of the migration.

What to Assess

  • Access Mode Check: Verify that VM disks are using ReadWriteMany (RWX) volumes.

  • Storage Class Audit: Check if the StorageClass used by the VMs is backed by a shared provider like ODF (Ceph), NFS, or an external SAN.

  • Migration Policy: Ensure evictionStrategy: LiveMigrate is set in the VirtualMachine specification.

Technical Rationale

Bare-metal nodes require physical maintenance (firmware, hardware replacement).

  • Zero Downtime Maintenance: Allows the infrastructure team to evacuate all VMs from a physical server for hardware repair without the application owner noticing a disruption.

  • Load Balancing: Enables the cluster to move "hot" VMs away from a CPU-congested host to a quieter host dynamically.

  • Data Integrity: Proper storage readiness ensures that the VM doesn't suffer from "split-brain" where two hosts think they own the virtual disk during the handoff.

Verification

Verification is done by checking the VM configuration and testing a migration:

  • Validation Method: Configuration review and live test.

Verification Steps:

  1. Verify volume access mode:

    oc get pvc <vmi-disk-pvc> -o jsonpath='{.spec.accessModes}'

  2. Check VM migration strategy:

    oc get vm <name> -o yaml | grep evictionStrategy

  3. Trigger a test migration:

    virtctl migrate <vm-name>

Evidence

  • StorageClass YAML: Snippet showing the provisioner and parameters.

  • PVC Report: Output of oc get pvc showing RWX status for VM disks.

  • Migration History: Output of oc get virtualmachineinstancemigration showing successful historical transitions.

Risk Impact

  • High Risk (Data Corruption): If storage is not properly "ReadWriteMany," a migration attempt may fail, or worse, leave the disk in a locked state that requires manual recovery.

  • Operational Risk: If Live Migration fails, every hardware patch requires a complete shutdown of all hosted VMs, significantly increasing the "Change Window" duration.

  • Performance Risk: Inadequate storage bandwidth during migration can lead to "migration timeouts," where the VM hangs in a transitional state.

Mapping

  • BNM RMiT (2025): Section 10.3 (Availability and Resilience); Section 10.5 (Performance Management).

  • CIS Benchmarks v8: Control 18 (Service Software Continuity).

  • NIST SP 800-53: CP-2 (Contingency Plan); SC-36 (Distributed Processing and Storage).

AR-008Infrastructure Resilience (Virtualization)

Live Migration Throttling

High

Description

When a Virtual Machine migrates between bare-metal hosts, its entire memory state (RAM) must be copied over the network. Live Migration Throttling (and bandwidth management) controls the speed of this transfer to ensure that migration traffic does not saturate the physical network links and negatively impact application traffic.

Key Aspects of Migration Throttling:

  • Bandwidth Limits: Setting a maximum Mbps/Gbps cap on migration traffic per VM.

  • Parallel Migration Limits: Controlling how many VMs can migrate simultaneously across the cluster or per node.

  • Dedicated Migration Network: Using a separate physical or VLAN interface for migration traffic to isolate it from the "Front-end" application network.

  • Completion Timeouts: Defining how long a migration is allowed to stay in the "pre-copy" phase before failing, preventing an endless loop if the VM's memory is changing faster than it can be copied.

What to Assess

In a high-transaction banking environment, "Network Jitter" is a major risk.

  • Predictable Performance: Ensures that migration is a background task that does not interfere with the primary mission of the cluster: serving application traffic.

  • Resource Fairness: Prevents a single large migration from consuming all available cluster bandwidth, which could block other critical migrations or health checks.

A balanced cluster is a resilient cluster.

  • Failure Impact Minimization: If an overloaded node fails, the loss of 100 pods is much harder for the cluster to recover from than the loss of 20 pods on a balanced node.

  • Optimal Hardware Use: Maximizes the ROI of the bare-metal investment by ensuring all purchased cores and RAM are being utilized effectively across the data center.

  • Moderate Risk (Resource Hotspots): An unbalanced cluster leads to "hotspots" where applications perform inconsistently depending on which node they landed on.

Description

  • Replica Count: Storing 3 independent copies of every block of data.

Technical Rationale

In bare-metal environments, disk failures are the most frequent hardware event.

  • Survival of Double Failure: While 3-way replication primarily protects against a single node/disk failure, it provides a safety margin to survive a second failure during the "rebuild" phase.

  • Zero Data Loss: Ensures that even if an entire physical server rack loses power, the data remains available from other racks.

  • High Availability for Databases: Provides the underlying "Shared Storage" needed for AR-007 (Live Migration) with the resilience required for financial records.

High

Description

Physical Link Aggregation (commonly implemented via LACP/Bonding) is the practice of combining multiple physical network interfaces (NICs) on a bare-metal node into a single logical channel. This provides both increased bandwidth and, more importantly, hardware-level network redundancy.

Key Aspects of Link Aggregation:

  • Active-Backup vs. LACP: * Active-Backup: One NIC is active; the other takes over only on failure.

    • LACP (802.3ad): Both NICs are active, providing increased throughput and sub-second failover.

  • Multi-Switch Bonding (MLAG): Connecting the two physical cables to two different physical switches (ToR - Top of Rack) to ensure a single switch failure doesn't isolate the node.

  • Declarative Config: Using the NMState Operator (AR-024) to ensure the bond is configured consistently across all nodes in the cluster.

What to Assess

  • Interface Configuration: Verify that each node shows a bond0 or similar interface comprised of at least two physical slaves.

  • Switch-Side Config: Confirm with the network team that LACP/MLAG is enabled on the corresponding switch ports.

  • NMState Policies: Verify that a NodeNetworkConfigurationPolicy (NNCP) exists to enforce the bonding across the worker pool.

Technical Rationale

Bare-metal nodes are susceptible to cable snags, transceiver failures, and switch port outages.

  • Zero-Downtime Network Failover: If a cable is pulled or a port fails, the LACP bond immediately reroutes traffic to the secondary link without dropping the TCP connection.

  • High-Throughput Requirements: Combines multiple 10Gbps or 25Gbps links to handle intensive traffic like ODF storage replication (AR-010) or VM live migrations (AR-007).

  • Standardization: Ensures that the "Data Plane" and "Management Plane" have consistent, resilient paths to the rest of the banking network.

Verification

Verification is performed by inspecting the host-level network state:

  • Validation Method: Inspection of the node network state via CLI.

Verification Steps:

  1. Check bond status:

    oc get nodenetworkstate <node-name> -o yaml

  2. Review NMState policy:

    oc get nncp

  3. Verify LACP partner status on the host:

    oc debug node/<node-name>

Evidence

  • NNCP YAML: The declarative policy defining the bond.

  • Node Network State Output: Export showing the bond interface status and active slave interfaces.

  • Network Diagram: Logical diagram showing physical cabling to redundant Top-of-Rack switches.

Risk Impact

  • High Risk (Single Point of Failure): Without bonding, the loss of a single $50 cable or a transceiver results in the total loss of a bare-metal node (and all hosted banking apps).

  • Performance Risk: A single link may become a bottleneck for high-traffic environments, leading to dropped packets and application timeouts.

  • Compliance Risk: Violates RMiT requirements for "Redundancy of Critical Infrastructure Components."

Key Aspects of Ingress HA:

  • Anti-Affinity: Ensuring Ingress pods are scheduled on different nodes (AR-005) and ideally on dedicated "Infra" nodes (AR-019).

Technical Rationale

If the Ingress layer fails, the entire cluster is effectively "offline" to the outside world, even if all applications are running perfectly.

  • Traffic Resilience: Ensures that a single router pod crash or a single "Infra" node failure does not interrupt the flow of customer banking transactions.

  • Seamless Upgrades: Allows the Ingress pods to be updated one at a time (rolling update) without any drop in external connectivity.

  • Performance Scaling: Distributes the TLS termination and routing logic across multiple CPUs, preventing a single pod from becoming a bottleneck.

  • Operational Risk: Routine maintenance of the networking stack becomes impossible without a declared maintenance window.

Description

Key Aspects of Replica Management:

Technical Rationale

Running a single instance (replicas: 1) is the primary cause of avoidable application downtime.

  • Load Distribution: Multiple replicas allow the cluster to distribute traffic via the Service (ClusterIP), improving responsiveness.

In a large bare-metal data center, "blind" scheduling is a risk.

  • Workload Optimization: Ensures that latency-sensitive workloads are placed on the fastest hardware or nodes with the best fiber connectivity.

AR-017Workload Resilience

Application Health Probes (Liveness, Readiness, Startup)

High

Description

OpenShift utilizes three distinct types of Health Probes to monitor the lifecycle of a container. Correct configuration of these probes ensures that traffic is only sent to "ready" pods and that "frozen" pods are automatically restarted.

Key Aspects of Health Probes:

  • Startup Probe: Disables liveness and readiness checks during the initial boot-up phase. Essential for "heavy" banking applications (like JBoss/Java) that take a long time to start.

  • Readiness Probe: Determines if the container is ready to accept traffic. If it fails, the pod is removed from the Service endpoint (load balancer) but not restarted.

  • Liveness Probe: Determines if the container is still running. If it fails (e.g., a deadlock), OpenShift restarts the container.

  • Probe Methods: Can use HTTP checks (/health), TCP socket checks, or custom Exec commands.

What to Assess

  • Probe Presence: Verify that all production containers have both livenessProbe and readinessProbe defined.

  • Endpoint Validity: Confirm that the probe targets a meaningful endpoint (e.g., a database connection check) rather than just a static index.html.

  • Threshold Tuning: Ensure initialDelaySeconds and failureThreshold are tuned so that pods aren't killed prematurely during normal heavy load.

Technical Rationale

Automated health monitoring is the first line of defense against application-level failures.

  • Zero-Downtime Deployments: Readiness probes ensure that during an update, the old version isn't killed until the new version is fully "ready" to take over traffic.

  • Self-Healing: Liveness probes automate the "reboot" of applications that have hung, reducing the need for manual intervention by the app support team.

  • Traffic Integrity: Prevents users from hitting a pod that is still initializing or is currently overwhelmed by a background task.

Verification

  • Validation Method: Analysis of pod templates in deployments.

Verification Steps:

  1. Check probes for all pods:

    oc get deployments -o json | jq '.items[].spec.template.spec.containers[].livenessProbe'

  2. Identify pods without probes:

    oc get pods -o custom-columns=NAME:.metadata.name,LIVENESS:.spec.containers[\*].livenessProbe,READINESS:.spec.containers[\*].readinessProbe

Evidence

  • Deployment YAML: Snippet showing the livenessProbe, readinessProbe, and startupProbe definitions.

  • Pod Events: Output of oc describe pod showing historical "Unhealthy" events and the subsequent automated recovery.

  • Application Logs: Proof that the health endpoint is being polled successfully by the kubelet.

Risk Impact

  • High Risk (Traffic Blackhole): Without readiness probes, OpenShift will send traffic to pods that haven't finished starting, leading to 503 errors for users.

  • Operational Risk: "Zombied" pods will stay in a Running state indefinitely despite being non-functional, requiring manual detection and restart.

  • Performance Risk: If liveness probes are too aggressive, they can trigger "restart loops" during periods of high CPU usage, making an outage worse.

AR-018Workload Resilience

Graceful Termination and Update Strategies

High

Description

When a pod is deleted (due to a scale-down or update), OpenShift sends a SIGTERM signal. Graceful Termination ensures the application has enough time to finish in-flight transactions, close database connections, and shut down cleanly before it is forcibly killed by a SIGKILL.

Key Aspects of Graceful Termination:

  • TerminationGracePeriodSeconds: The amount of time (default 30s) OpenShift waits before force-killing a pod.

  • PreStop Hooks: Custom commands or HTTP calls executed immediately before the SIGTERM to notify external systems or "drain" work.

  • RollingUpdate Strategy: Managing maxUnavailable and maxSurge to ensure the application capacity never drops below the required threshold during an update.

  • Connection Draining: Ensuring the load balancer stops sending new requests while existing requests are finished.

What to Assess

  • Grace Period Tuning: Verify that terminationGracePeriodSeconds is long enough for the application's longest-running transaction (e.g., 60s or 90s).

  • Update Strategy: Confirm strategy: type: RollingUpdate is used instead of Recreate.

  • MaxUnavailable Setting: Ensure maxUnavailable is not set to 100% (which would take the service offline).

Technical Rationale

In banking, a "hard kill" of a process can lead to data inconsistency.

  • Transaction Integrity: Ensures that a customer's transfer isn't cut off mid-execution during a mid-day deployment.

  • Clean Database Sessions: Prevents "orphaned" sessions or locks in the database that occur when an application client disappears without closing its connection.

  • Zero-Downtime Updates: Provides a smooth transition for users between old and new versions of the software.

Verification

  • Validation Method: Review of deployment strategies and termination settings.

Verification Steps:

  1. Check termination period:

    oc get deployment <name> -o jsonpath='{.spec.template.spec.terminationGracePeriodSeconds}'

  2. Review update strategy:

    oc get deployment <name> -o jsonpath='{.spec.strategy.rollingUpdate}'

Evidence

  • Deployment YAML: Snippet showing RollingUpdate and terminationGracePeriodSeconds.

  • Application Logs: Logs showing the "Shutdown signal received" followed by successful "Cleanup complete" messages.

  • Load Balancer Logs: Evidence of connections being drained before a pod IP is removed from the rotation.

Risk Impact

  • High Risk (Data Inconsistency): Interrupted writes can leave a database in a state that requires manual reconciliation.

  • Operational Risk: Users will experience dropped connections and "Reset by Peer" errors during every cluster maintenance event.

  • Performance Risk: Hard-kills of large Java apps can cause "Zombies" at the OS level or leave the node with un-recycled memory.

Mapping

  • BNM RMiT (2025): Section 11.1 (Data Integrity); Section 10.3 (Availability and Resilience).

  • CIS Benchmarks v8: Control 18 (Service Software Continuity).

  • NIST SP 800-53: SC-24 (Fail-Safe Procedures).

AR-019Physical Architecture & Resource Isolation

Infrastructure (Infra) Node Segregation

High

Description

In a production bare-metal environment, shared resource contention between the platform and applications is a major risk. Infra Node Segregation involves dedicating specific nodes to run platform-level services (Ingress, Monitoring, Logging, Registry) while keeping application workloads on separate Worker nodes.

Key Aspects of Infra Nodes:

  • Role-Based Separation: Assigning the node-role.kubernetes.io/infra="" label to a subset of nodes.

  • Resource Guarantee: Ensures that a memory leak in a user application cannot starve the Ingress Routers or Prometheus monitoring.

  • Subscription Optimization: Cores on correctly labeled "Infra" nodes are typically excluded from billable OpenShift core counts (check Red Hat subscription terms).

  • Scheduling Taints: Using taints (node-role.kubernetes.io/infra:NoSchedule) to prevent general applications from landing on these critical nodes.

What to Assess

  • Node Labels: Verify that at least 3 nodes are labeled as infra.

  • Workload Placement: Confirm that Ingress Controllers and Monitoring pods are actually running on these nodes via nodeSelector.

  • Taint Enforcement: Ensure that no non-platform pods are running on the infra nodes.

Technical Rationale

Platform stability is the prerequisite for application stability.

  • Noise Isolation: If an application pod on a Worker node triggers a "Kernel Panic" or saturates the CPU, the Ingress Controller on the Infra node remains unaffected, allowing traffic to reach other healthy Workers.

  • High Availability for Metrics: Ensures that even during a massive application failure, the monitoring stack stays alive to provide the logs and metrics needed to diagnose the issue.

  • Operational Predictability: Simplifies maintenance by allowing platform teams to upgrade infra components without touching application-hosting hardware.

Verification

  • Validation Method: Node and pod affinity audit.

Verification Steps:

  1. List infra nodes:

    oc get nodes -l node-role.kubernetes.io/infra

  2. Check pod placement:

    oc get pods -A -o wide | grep <infra-node-name> (Should only show openshift-ingress, openshift-monitoring, etc.).

  3. Verify Taints:

    oc describe node <infra-node> | grep Taints

Evidence

  • Node Role Report: A list of nodes and their roles.

  • Ingress/Monitoring YAML: Snippets showing the nodeSelector targeting the infra role.

  • Subscription Report: Proof that infra nodes are correctly recognized by the Red Hat Subscription Manager (if applicable).

Risk Impact

  • High Risk (Platform Contention): A runaway application pod could crash the Ingress Router, taking the entire cluster offline.

  • Operational Risk: Loss of visibility (monitoring) during a crisis if the Prometheus pod is evicted due to resource pressure from user apps.

  • Cost Risk: Inefficient use of billable cores by running non-billable infra services on worker nodes.

Mapping

  • BNM RMiT (2025): Section 10.3 (Availability and Resilience); Appendix 4 (Critical System Design).

  • CIS Benchmarks v8: Control 12 (Network Infrastructure Management).

  • NIST SP 800-53: SC-6 (Resource Availability); SC-32 (Information System Partitioning).

AR-020Physical Architecture & Resource Isolation

Dedicated Storage Node Roles (ODF Isolation)

Critical

Description

For high-performance bare-metal clusters using OpenShift Data Foundation (ODF), this control mandates that storage services are run on dedicated storage nodes. This isolates the high I/O and memory demands of the storage layer (Ceph) from the application and control plane layers.

Key Aspects of Dedicated Storage Nodes:

  • Resource Isolation: Ceph (the engine of ODF) is resource-intensive. Dedicating nodes ensures its memory cache doesn't compete with banking applications.

  • Taints & Tolerations: Using a taint like node.ocs.openshift.io/storage:NoSchedule so that only ODF-related pods can run on these nodes.

  • Network Optimization: These nodes can be equipped with dedicated 25Gbps/100Gbps links for storage replication traffic (back-end), separate from the application network (front-end).

  • Fault Isolation: Hardware issues with a physical disk or controller only affect the storage node, not the application workers.

What to Assess

  • Node Roles: Verify a subset of nodes carries the storage role label.

  • ODF Configuration: Confirm the StorageCluster resource is configured to use the storage node selector.

  • Taint Check: Verify that application pods are not scheduled on storage nodes.

Technical Rationale

Storage is the "foundation" of the cluster; if it is slow, everything is slow.

  • Latency Consistency: Prevents "I/O Wait" on worker nodes by ensuring the storage controller has 100% access to its own CPU and RAM.

  • Scale-Out Simplicity: Allows you to scale storage capacity (by adding more storage nodes) independently of application compute capacity.

  • Resilience: Ensures that a massive data rebuild (after a disk failure) doesn't consume the resources needed to run the banking API.

Verification

  • Validation Method: Node labeling and ODF configuration audit.

Verification Steps:

  1. Check storage nodes:

    oc get nodes -l cluster.ocs.openshift.io/openshift-storage

  2. Check taints:

    oc describe node <storage-node> | grep Taints

  3. Verify ODF placement:

    oc get storagecluster -n openshift-storage ocs-storagecluster -o yaml | grep nodeSelector -A 3

Evidence

  • StorageCluster YAML: Showing the placement and nodeSelector logic.

  • Node List: Showing dedicated nodes for storage.

  • Performance Metrics: Grafana screenshots showing consistent storage latency (below 5ms) due to lack of resource contention.

Risk Impact

  • High Risk (I/O Contention): If storage and apps share nodes, a peak in application load can slow down disk writes, causing "I/O Wait" across the entire cluster.

  • Critical Risk (Storage Instability): If a worker node crashes due to an app bug, the storage chunk on that node goes offline, potentially triggering a massive, resource-heavy data rebalance.

  • Operational Risk: Difficulty in troubleshooting performance issues when storage and compute metrics are "blended" on the same physical hardware.

Mapping

  • BNM RMiT (2025): Section 11.1 (Data Integrity); Section 10.3 (Availability and Resilience).

  • CIS Benchmarks v8: Control 18 (Service Software Continuity).

  • NIST SP 800-53: SC-36 (Distributed Processing and Storage); SC-32 (Information System Partitioning).

This completes the final set of controls for Pillar 1: Availability & Resilience (AR-021 to AR-024). These controls finalize the physical isolation strategy and incorporate the 2026 networking standards required for a bare-metal production environment.

AR-021Physical Architecture & Resource Isolation

Node Taints & Tolerations Enforcement (Role-Based Repulsion)

High

Description

Taints and Tolerations are the primary mechanism used to ensure that specific nodes "repel" pods unless those pods have a matching "toleration." In a bare-metal environment, this is essential for Role-Based Repulsion, ensuring that general application workloads do not accidentally land on specialized infrastructure (Infra), storage (ODF), or control plane (Master) nodes.

Key Aspects of Taints & Tolerations:

  • Taints: Applied to a node (e.g., node-role.kubernetes.io/infra:NoSchedule). This prevents any pod without a corresponding toleration from being scheduled on that node.

  • Tolerations: Applied to specific pods (e.g., Ingress Controllers or Monitoring stack) allowing them to "ignore" the taint and schedule on the restricted node.

  • Effect Types:

    • NoSchedule: New pods will not be placed on the node.

    • NoExecute: Existing pods will be evicted if they don't have the toleration.

  • Integrity of Roles: Prevents "Workload Bleeding" where a non-critical app consumes resources intended for critical platform services.

What to Assess

  • Master/Infra Taints: Verify that all Master and Infra nodes carry the NoSchedule taint.

  • Workload Compliance: Audit all production namespaces to ensure no unauthorized pods have "wide" tolerations (e.g., operator: Exists) that allow them to land anywhere.

  • Storage Isolation: Confirm that ODF storage nodes are tainted to prevent application pod placement (AR-020).

Technical Rationale

A "Well-Architected" cluster must have predictable resource allocation.

  • Resource Preservation: Ensures that the CPU and RAM on expensive bare-metal nodes are reserved for their intended purpose (e.g., preventing a dev-app from crashing the production Ingress router).

  • Security Isolation: Provides a secondary layer of isolation by keeping sensitive platform pods physically separated from user-generated application pods.

  • Operational Stability: Reduces the "blast radius" of application failures by confining them to designated worker nodes.

Verification

Verification is performed by inspecting node taints and pod tolerations:

  • Validation Method: Node taint audit and pod placement analysis.

Verification Steps:

  1. List all node taints:

    oc get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints

  2. Verify restricted pod tolerations:

    oc get pod <pod-name> -n <namespace> -o jsonpath='{.spec.tolerations}'

  3. Confirm no "rogue" pods on infra nodes:

    oc get pods -A --field-selector spec.nodeName=<infra-node-name>

Evidence

  • Node Taint Report: An export showing the taints assigned to Master, Infra, and Storage nodes.

  • Operator Configuration: YAML snippets for Ingress/Monitoring showing the specific tolerations required to run on Infra nodes.

  • Pod Placement Map: Evidence that application pods are strictly confined to the "Worker" pool.

Risk Impact

  • High Risk (Platform Starvation): Without taints, an application memory leak could evict critical platform pods (like Ingress), causing a cluster-wide outage.

  • Operational Risk: Difficulty in managing performance SLAs when platform and application workloads are competing for the same physical hardware resources.

  • Security Risk: Increased risk of side-channel attacks or resource exhaustion across different security tiers.

Mapping

  • BNM RMiT (2025): Section 10.3 (Availability and Resilience); Section 11.2 (User Access Management - Logical Isolation).

  • CIS Benchmarks v8: Control 12 (Network Infrastructure Management).

  • NIST SP 800-53: SC-32 (Information System Partitioning); SC-6 (Resource Availability).

AR-022Network Resilience

OVN-Kubernetes Architecture Standard

Critical

Description

As of 2026, OVN-Kubernetes is the mandatory SDN (Software Defined Network) for OpenShift, replacing the deprecated OpenShift SDN. It is based on Open Virtual Network (OVN) and provides a highly scalable, distributed logical network for containerized workloads.

Key Aspects of OVN-Kubernetes:

  • Distributed Load Balancing: Implements load balancing at the node level using OVS (Open vSwitch), reducing the bottleneck on centralized routers.

  • Geneve Encapsulation: Uses the Geneve protocol for tunnel encapsulation, which supports more metadata than the older VXLAN.

  • Logical Flow Performance: Optimized for high-churn environments where pods are frequently created and destroyed.

  • Gateway Modes: Supports "Shared" or "Local" gateway modes to optimize how traffic exits the bare-metal nodes to the corporate network.

What to Assess

  • Network Type Check: Verify that the network.config.openshift.io resource is set to OVNKubernetes.

  • MTU Alignment: Confirm that the network MTU is correctly configured (typically 1400 or 8900 for Jumbo Frames) to account for the 100-byte Geneve overhead.

  • Operator Health: Ensure the network-node-identity and ovnkube pods are healthy across all nodes.

Technical Rationale

Modern banking applications require the advanced networking features that only OVN-K provides.

  • Forward Compatibility: Standardizing on OVN-K ensures the cluster can be upgraded and supported through 2026 and beyond.

  • Performance at Scale: Distributed routing eliminates the "hairpinning" of traffic, reducing latency for inter-service communication.

  • Security Foundations: OVN-K is the prerequisite for advanced security features like IPsec encryption (SC-020) and Egress Firewalls.

Verification

  • Validation Method: Cluster network configuration audit.

Verification Steps:

  1. Confirm CNI type:

    oc get network.config/cluster -o jsonpath='{.status.networkType}' (Must return OVNKubernetes).

  2. Verify pod status:

    oc get pods -n openshift-ovn-kubernetes

  3. Check MTU settings:

    oc get network.config/cluster -o jsonpath='{.status.clusterNetworkMTU}'

Evidence

  • Network Config YAML: Export of the networks.config.openshift.io resource.

  • OVN Pod Logs: Logs from the ovnkube-node showing successful logical flow initialization.

  • Network Benchmark: Proof of successful pod-to-pod connectivity across different physical nodes.

Risk Impact

  • Critical Risk (Upgrade Failure): Environments still running the deprecated OpenShift SDN will be unable to upgrade to newer versions, leading to a "security debt" and loss of support.

  • Performance Risk: Legacy SDN types lack the distributed routing capabilities needed for high-traffic microservices.

  • Compliance Risk: Using deprecated software violates RMiT requirements for "Obsolescence Management."

Mapping

  • BNM RMiT (2025): Section 10.3 (Availability and Resilience); Section 10.6 (System Software Maintenance).

  • CIS Benchmarks v8: Control 12 (Network Infrastructure Management).

  • NIST SP 800-53: SC-7 (Boundary Protection).

AR-023Network Resilience

Multus Secondary Networking (Physical Network Segmentation)

High

Description

Multus CNI is a "meta-plugin" that allows a single pod to be attached to multiple physical or logical networks simultaneously. In a bare-metal banking environment, this is used to physically segment sensitive traffic (like storage or backup) from the general application traffic.

Key Aspects of Multus:

  • Multiple Interfaces: A pod can have eth0 for the standard cluster network and net1 for a dedicated high-speed storage network.

  • NetworkAttachmentDefinitions: Declarative YAML objects that define how the secondary interface should be plumbed (e.g., via Bridge, MACVLAN, or SR-IOV).

  • Traffic Isolation: Ensures that "Data Plane" traffic (like high-volume database replication) does not saturate the "Control Plane" or "User" network.

What to Assess

  • NAD Definitions: Verify that NetworkAttachmentDefinitions exist in the relevant namespaces.

  • Pod Configuration: Confirm that critical pods (like ODF or Databases) have the k8s.v1.cni.cncf.io/networks annotation.

  • Physical Interface Mapping: Ensure that the secondary networks are mapped to the correct physical NIC bonds (AR-012).

Technical Rationale

Regulatory standards often require physical or strict logical isolation for specific data types.

  • Security Segmentation: Keeps sensitive "Backend" traffic (like DB-to-Storage) completely invisible to the "Frontend" application network.

  • Performance Guarantee: Dedicating a physical NIC to storage traffic ensures that a spike in web traffic does not cause "I/O Wait" in the storage layer.

  • Legacy Integration: Allows pods to connect directly to existing VLANs in the data center without going through the OpenShift Ingress.

Verification

  • Validation Method: Inspection of CNI definitions and pod network interfaces.

Verification Steps:

  1. List NADs:

    oc get net-attach-def -A

  2. Inspect pod interfaces:

    oc exec <pod-name> -- ip addr (Verify multiple interfaces exist).

  3. Verify connectivity: Perform a:

    ping or traceroute over the secondary interface (net1).

Evidence

  • Net-Attach-Def YAML: The configuration for the secondary network.

  • Pod Annotation Snippet: The YAML metadata showing the Multus attachment.

  • Network Traffic Report: Evidence of traffic flowing across multiple interfaces simultaneously.

Risk Impact

  • High Risk (Network Contention): Without Multus, a high-volume backup or storage rebalance could "choke" the application network, leading to a service outage.

  • Security Risk: Co-mingling management and data traffic increases the risk of lateral movement if a pod is compromised.

  • Compliance Risk: Failure to demonstrate "Network Segmentation" as required by PCIDSS or RMiT.

Mapping

  • BNM RMiT (2025): Section 10.3 (Availability and Resilience); Section 11.2 (Network Security).

  • CIS Benchmarks v8: Control 12 (Network Infrastructure Management).

  • NIST SP 800-53: SC-7 (Boundary Protection); SC-32 (Information System Partitioning).

AR-024Infrastructure Resilience

Declarative Node Networking (NMState) (Host-level Bond/VLAN Management)

Critical

Description

Kubernetes NMState is an operator that allows administrators to manage the physical networking configuration of bare-metal hosts using a declarative Kubernetes API. Instead of manually editing scripts on each server, you define the desired state (Bonds, VLANs, MTU) in a YAML file.

Key Aspects of NMState:

  • NodeNetworkConfigurationPolicy (NNCP): The primary resource used to define the desired network state for a group of nodes.

  • Drift Prevention: The operator continuously monitors the physical nodes and automatically reverts any manual, non-compliant changes.

  • Safe Rollouts: NMState includes "Transaction Support"—if a network change causes a node to lose connectivity, it can automatically roll back to the previous known-good configuration.

  • Bare-Metal Efficiency: Simplifies the management of complex 25Gbps/100Gbps bonds and bridge configurations across dozens of servers.

What to Assess

  • Operator Health: Confirm the Kubernetes NMState Operator is installed and the nmstate pods are running on all nodes.

  • NNCP Status: Verify that all NodeNetworkConfigurationPolicy objects are in a SuccessfullyConfigured state.

  • Host Synchronization: Check that the physical NIC status on the hosts matches the NodeNetworkState reported in the API.

Technical Rationale

Manual network configuration is the leading cause of "gray failures" in bare-metal clusters.

  • Consistency: Ensures that every node in a worker pool has an identical network footprint, preventing "it works on Node A but not Node B" issues.

  • Auditability: Network changes are now part of the GitOps pipeline (MO-001), providing a full audit trail of who changed what and when.

  • Reduced Human Error: The automated rollback feature prevents an administrator from accidentally "locking themselves out" of a remote server during a network update.

Verification

  • Validation Method: Policy and state audit.

Verification Steps:

  1. Check policy status:

    oc get nncp (Look for STATUS: SuccessfullyConfigured).

  2. Review node state:

    oc get nodenetworkstate <node-name> -o yaml

  3. Verify bond/VLAN configuration: Inspect the interface section of the NNS output for correct MTU and slave interfaces.

Evidence

  • NNCP YAML: The policy defining the production network bond.

  • NodeNetworkState Export: A report showing the actual physical network state of the bare-metal fleet.

  • Event Logs: Records of successful network state reconciliations.

Risk Impact

  • High Risk (Configuration Drift): Manual changes to a single node's MTU or VLAN can cause intermittent, hard-to-debug application failures.

  • Operational Risk: Increases the manual effort and time required to scale the cluster or update networking hardware.

  • Critical Risk (Node Isolation): A manual error during a network change can permanently disconnect a bare-metal node, requiring a physical visit to the data center.

Mapping

  • BNM RMiT (2025): Section 10.1 (Operations Management); Section 10.3 (Resilience).

  • CIS Benchmarks v8: Control 12 (Network Infrastructure Management).

  • NIST SP 800-53: CM-3 (Configuration Change Control); SC-7 (Boundary Protection).
