Pillar 5: Monitoring & Observability

Architecture assessment page for validating observability-as-code, centralized logging, resilient monitoring, API audit logging, long-term metric retention, network flow visibility, distributed tracing, synthetic monitoring, Kubernetes state metrics, and event archiving controls.

Use note: This page is a consulting assessment artefact for OpenShift architecture and operations review. It is not an official Red Hat methodology. Validate technical statements and command syntax against the target OpenShift version and client environment before use.

Monitoring and Observability define the platform's capability to detect service degradation, preserve operational evidence, support incident response, and provide measurable visibility across infrastructure, workloads, applications, network flows, logs, metrics, traces, and Kubernetes events. For OpenShift environments supporting containerized workloads and OpenShift Virtualization, these controls validate that observability configuration, log forwarding, monitoring high availability, audit logging, metric retention, network observability, distributed tracing, synthetic monitoring, cluster-state telemetry, and event archiving are implemented through tested, automated, and evidence-backed operational practices.

Summary of Controls

Pillar 5 contains 10 assessment controls grouped by monitoring and observability domain to support auditability, telemetry, proactive detection, operational resilience, incident analysis, and long-term evidence retention.

MO-001Observability Architecture

GitOps-Driven Observability Configuration

High

Description

GitOps-Driven Observability mandates that all monitoring configurations—including Prometheus Rules, Alertmanager routing, and Grafana dashboards—are defined as code and managed via OpenShift GitOps (ArgoCD). No manual edits via the OpenShift Console or CLI are permitted for production monitoring alerts.

Key Aspects of GitOps Observability:

  • Declarative Alerts: Storing PrometheusRule objects in a version-controlled Git repository.

  • Dashboard as Code: Defining custom Grafana dashboards as JSON files injected via ConfigMaps managed by ArgoCD.

  • Peer Review: Requiring a Pull Request (PR) approval process before an alert threshold (e.g., changing a CPU warning from 80% to 90%) can be modified.

  • Drift Reconciliation: ArgoCD automatically reverts any unauthorized manual changes to the alerting pipeline back to the approved Git state.

What to Assess

  • ArgoCD Management: Verify that resources in the openshift-monitoring and openshift-user-workload-monitoring namespaces are labeled as managed by ArgoCD.

  • Git Repository: Audit the repository storing the monitoring manifests for proper access controls and branch protection rules.

  • Drift Status: Ensure that the ArgoCD application managing observability is reporting a Synced and Healthy status.

Technical Rationale

In a banking environment, an undocumented change to a monitoring alert can mask a critical failure.

  • Auditability: Provides a pristine, unalterable audit trail of who changed an alert, when, and why (via the Git commit history).

  • Disaster Recovery: If the cluster is lost, the entire observability stack and all custom dashboards can be restored to the DR site in seconds (RC-006).

  • Standardization: Ensures that the "Development" and "Production" environments use the exact same alerting logic, preventing surprises during deployment.

Verification

  • Validation Method: GitOps configuration audit.

Verification Steps:

  1. Check ArgoCD apps:

    oc get applications -n openshift-gitops | grep monitoring

  2. Verify resource labels:

    oc get prometheusrule -n openshift-monitoring -o jsonpath='{.items[*].metadata.labels}' (Look for app.kubernetes.io/instance).

  3. Check Git commit history for recent alert modifications.

Evidence

  • ArgoCD Application YAML: Showing the source repository for the monitoring stack.

  • Git PR Log: An example of an approved Pull Request modifying an alerting threshold.

  • Sync Status Report: Screenshot of ArgoCD showing no configuration drift in the monitoring namespace.

Risk Impact

  • High Risk (Missed Incidents): Manual, untracked changes to alerts can lead to "silenced" warnings, allowing minor issues to cascade into major banking outages.

  • Operational Risk: Dashboards built manually in the UI will be permanently lost during a cluster rebuild or migration.

  • Compliance Risk: May not meet regulatory requirements for strict Change Management and configuration tracking for critical systems.

Mapping

  • BNM RMiT (2025): Section 10.1 (Operations Management); Section 11.5 (Logging and Monitoring).

  • CIS Benchmarks v8: Control 4 (Secure Configuration of Enterprise Assets).

  • NIST SP 800-53: CM-3 (Configuration Change Control).

MO-002Audit and Logging

Centralized Log Forwarding (ClusterLogForwarder)

Critical

Description

Local storage on OpenShift nodes is ephemeral. Centralized Log Forwarding utilizes the OpenShift Logging Operator to collect logs from all containers and bare-metal nodes, format them, and securely transmit them to an external Security Information and Event Management (SIEM) system (e.g., Splunk, IBM QRadar, or Elastic).

Key Aspects of Log Forwarding:

  • Data Types: Must forward three specific types of logs:

  • Application: Output from the banking microservices (stdout/stderr).

  • Infrastructure: Logs from the OpenShift platform pods and node journals.

  • Audit: Security events from the Kubernetes API server (MO-004) and OpenVN.

  • ClusterLogForwarder API: The declarative configuration defining the inputs, outputs (external SIEM IP/FQDN), and pipelines.

  • TLS Encryption: Ensuring the transmission of logs from the cluster to the SIEM is encrypted using mutual TLS (mTLS).

What to Assess

  • Logging Operator: Verify the OpenShift Logging Operator is installed and healthy.

  • Forwarder Configuration: Audit the ClusterLogForwarder instance to ensure all three log types (App, Infra, Audit) are routed to the SIEM.

  • Transport Security: Confirm that the output configuration utilizes secure TLS certificates.

Technical Rationale

Logs are the definitive source of truth during a security breach or application failure.

  • Forensic Immutability: Once a log is pushed to an external SIEM, a cluster administrator (or an attacker who gains cluster-admin rights) cannot delete or alter the evidence.

  • Survival of Node Death: If a bare-metal node panics and crashes, the logs leading up to the crash are safely stored off-site.

  • Correlation: Allows the Security Operations Center (SOC) to correlate an OpenShift ingress event with a perimeter firewall event.

Verification

  • Validation Method: Forwarder configuration and SIEM receipt audit.

Verification Steps:

  1. Check forwarder object:

    oc get clusterlogforwarder instance -n openshift-logging -o yaml

  2. Verify pipeline routing: Ensure pipelines define inputRefs: [application, infrastructure, audit].

  3. Check collector health:

    oc get pods -n openshift-logging -l component=collector (Fluentd or Vector pods must be running).

Evidence

  • ClusterLogForwarder YAML: Export showing the configured pipelines and secure SIEM endpoints.

  • SIEM Query Screenshot: A screenshot from Splunk/QRadar showing recent OpenShift audit logs successfully ingested.

  • TLS Secret Export: Proof that a client certificate is mounted for secure transmission.

Risk Impact

  • Critical Risk (Forensic Blindness): If logs remain on the node, an attacker who deletes the container or reboots the node destroys all evidence of the intrusion.

  • Compliance Risk: Immediate non-compliance with regulatory expectations for continuous security monitoring and log retention.

  • Operational Risk: Application teams cannot troubleshoot production issues without access to historical application logs.

Mapping

  • BNM RMiT (2025): Section 11.5 (Logging and Security Monitoring).

  • CIS Benchmarks v8: Control 8 (Audit Log Management).

  • NIST SP 800-53: AU-4 (Audit Log Storage Capacity); AU-9 (Protection of Audit Information).

MO-003Observability Architecture

High Availability for the Monitoring Stack

High

Description

The monitoring stack (Prometheus, Alertmanager, Thanos) must be as resilient as the applications it monitors. This control mandates High Availability (HA) for all observability components and ensures they are physically isolated on dedicated infrastructure nodes (AR-019).

Key Aspects of Monitoring HA:

  • Prometheus Replicas: Running at least two identical instances of Prometheus that scrape the same targets independently.

  • Alertmanager Clustering: Running a highly available Alertmanager cluster that deduplicates alerts before sending them to external channels (e.g., PagerDuty, Email).

  • Node Segregation: Placing these pods exclusively on nodes labeled node-role.kubernetes.io/infra to prevent application spikes from crashing the monitoring tools.

  • Storage Resiliency: Utilizing persistent, replicated storage (ODF) for the Prometheus Write-Ahead Log (WAL) to prevent data loss during pod restarts.

What to Assess

  • ConfigMap Audit: Verify the cluster-monitoring-config to ensure retention and replicas are properly configured.

  • Pod Distribution: Confirm that Prometheus and Alertmanager pods are scheduled across different physical infra nodes (Anti-Affinity).

  • Storage Configuration: Ensure Prometheus is configured to use a PersistentVolumeClaim (PVC) rather than emptyDir.

Technical Rationale

A failure in monitoring during an application outage creates a "blind" disaster scenario.

  • Continuous Visibility: If one Infra node crashes, the secondary Prometheus instance continues to collect metrics and fire alerts without interruption.

  • Preventing Alert Fatigue: An HA Alertmanager ensures that engineers receive a single, consolidated notification rather than duplicate alerts from multiple Prometheus instances.

  • Resource Guarantee: By keeping monitoring off worker nodes, a rogue banking app with a memory leak cannot starve Prometheus of the RAM it needs to process metrics.

Verification

  • Validation Method: Operator configuration and pod placement audit.

Verification Steps:

  1. Check monitoring config:

    oc get configmap cluster-monitoring-config -n openshift-monitoring -o yaml

  2. Verify replicas:

    oc get statefulset prometheus-k8s -n openshift-monitoring -o jsonpath='{.spec.replicas}' (Must be $\ge 2$).

  3. Check pod placement:

    oc get pods -n openshift-monitoring -o wide | grep prometheus

Evidence

  • Cluster-Monitoring-Config YAML: Showing replicas: 2 and the nodeSelector targeting infra nodes.

  • Pod Affinity Report: Evidence that the two Prometheus instances are running on different bare-metal hosts.

  • PVC Status: Output of oc get pvc -n openshift-monitoring showing bound volumes.

Risk Impact

  • High Risk (Monitoring Blackout): A single-replica monitoring stack can crash under heavy load, precisely when it is needed most to diagnose an ongoing incident.

  • Operational Risk: Duplicate alerts or missed pages can lead to slower incident response times and SLA breaches.

  • Efficiency Risk: Losing local metric history during a pod restart complicates immediate troubleshooting.

Mapping

  • BNM RMiT (2025): Section 10.3 (Availability and Resilience); Section 11.5 (Logging and Monitoring).

  • CIS Benchmarks v8: Control 18 (Service Software Continuity).

  • NIST SP 800-53: SI-4 (Information System Monitoring).

MO-004Audit and Logging

API Audit Logging

Critical

Description

The OpenShift API Server processes every command executed in the cluster. API Audit Logging configures the API server to record a chronological set of records detailing the sequence of activities that have affected the system by individual users, administrators, or other components.

Key Aspects of API Audit Logging:

  • Audit Profile Levels: OpenShift offers different profiles. For production banking, RequestResponse (logs full request and response bodies) or Metadata (logs user, timestamp, resource, and action) must be explicitly configured.

  • Default Profile: The Default profile logs only metadata for write requests and does not log read requests, which is often insufficient for strict financial compliance.

  • Log Forwarding: These logs must be captured by the ClusterLogForwarder (MO-002) and pushed to the SIEM.

  • Retention: Ensuring local audit logs on the master nodes are rotated and retained long enough for the forwarder to process them securely.

What to Assess

  • Audit Profile Configuration: Verify the APIServer cluster resource to check the active audit.profile.

  • SIEM Ingestion: Confirm with the SOC team that API audit logs are successfully parsing in the SIEM and mapped to identity data (SC-002).

  • Custom Rules: If using a custom profile, verify that sensitive data (like secret contents) are "omitted" from the logs to prevent credential leakage into the SIEM.

Technical Rationale

API audit logs are the primary mechanism for detecting insider threats and compromised administrative credentials.

  • Non-Repudiation: Proves definitively that user "George" executed oc delete secret at 2:00 AM.

  • Behavioral Analytics: Allows the SOC to detect anomalous behavior, such as a service account suddenly attempting to list all secrets across all namespaces.

  • Root Cause Analysis: Helps determine if a service outage was caused by a configuration change applied via the API.

Verification

  • Validation Method: APIServer configuration audit.

Verification Steps:

  1. Check active profile:

    oc get apiserver cluster -o jsonpath='{.spec.audit.profile}'

  2. Check custom rules (if applicable):

    oc get apiserver cluster -o jsonpath='{.spec.audit.customRules}'

  3. Verify log existence on master node:

    oc debug node/<master-node> -- chroot /host tail /var/log/kube-apiserver/audit.log

Evidence

  • APIServer YAML: Export showing the enforced audit.profile.

  • Sample Audit Log Event: A JSON snippet from the SIEM showing an API action (e.g., creating a pod), the authenticated user, and the source IP.

  • Log Rotation Config: Proof that /etc/audit/auditd.conf is correctly configured to prevent disk exhaustion.

Risk Impact

  • Critical Risk (Unattributable Breaches): Without detailed API logging, an attacker can modify cluster security policies and the organization will have no idea how it happened or what was changed.

  • Compliance Risk: Major non-compliance with regulatory requirements Section 11.5 and general PCIDSS requirements for tracking privileged access.

  • Privacy Risk: If custom rules aren't set correctly, RequestResponse logging might accidentally record the plain-text payload of a Secret object into the SIEM.

Mapping

  • BNM RMiT (2025): Section 11.5 (Logging and Security Monitoring); Section 11.2 (User Access).

  • CIS Benchmarks v8: Control 8 (Audit Log Management).

  • NIST SP 800-53: AU-2 (Event Logging); AU-3 (Content of Audit Records).

MO-005Metrics & Telemetry

Long-Term Metric Retention (Thanos Integration)

Moderate

Description

By default, the local Prometheus instances in OpenShift only retain metric data for a short period (typically 15 days) to prevent local disk exhaustion. Long-Term Metric Retention utilizes the native Thanos Querier and Receiver components to push metrics to an external S3-compatible Object Store (like ODF or MinIO).

Key Aspects of Thanos Integration:

  • Object Storage: Configuring a highly durable, cheap object storage bucket to hold months or years of compressed metric data.

  • Global Query View: Thanos provides a single Grafana endpoint that can seamlessly query real-time data from local Prometheus and historical data from the S3 bucket simultaneously.

  • Downsampling: Automatically reducing the resolution of old data (e.g., turning 1-minute data points into 1-hour data points after 30 days) to save storage costs.

  • Multi-Cluster Visibility: Allows Thanos to aggregate metrics from both the Primary and DR clusters (RC-005) into a single pane of glass.

What to Assess

  • Secret Configuration: Verify the existence of the thanos-objstore-config secret in the openshift-monitoring namespace.

  • Monitoring Config: Confirm the cluster-monitoring-config ConfigMap is configured to enable Thanos and connect it to the object store.

  • Data Presence: Verify that metric blocks are actively being written to the target S3 bucket.

Technical Rationale

Capacity planning and seasonal trend analysis require historical context.

  • Trend Analysis: Allows the platform team to compare the cluster's CPU load during this month's payroll processing with last month's, identifying efficiency degradation.

  • SLA Reporting: Financial institutions require historical uptime and latency metrics to prove adherence to Service Level Agreements (SLAs).

  • Stateless Prometheus: By offloading data to S3, the local Prometheus pods become nearly stateless, making them much faster to restart and recover.

Verification

  • Validation Method: Object storage configuration and data verification.

Verification Steps:

  1. Check Thanos secret:

    oc get secret thanos-objstore-config -n openshift-monitoring

  2. Check monitoring config:

    oc get configmap cluster-monitoring-config -n openshift-monitoring -o yaml | grep -A 5 thanos

  3. Verify Thanos Pods:

    oc get pods -n openshift-monitoring -l app=thanos-query

Evidence

  • Thanos Configuration Snippet: The YAML showing the integration with the S3 bucket.

  • S3 Bucket Listing: Evidence from the storage provider (e.g., Ceph Object Gateway) showing Thanos metric chunks stored securely.

  • Grafana Dashboard Screenshot: A chart displaying metric data spanning 90+ days, proving successful historical retrieval.

Risk Impact

  • Moderate Risk (Loss of Baseline): Without long-term metrics, the engineering team cannot establish a "normal" performance baseline, making it difficult to detect subtle degradations over time.

  • Operational Risk: Prometheus local disks filling up and crashing because retention was increased without using an external object store.

  • Business Risk: Inability to accurately forecast hardware procurement needs for the bare-metal data center due to a lack of historical growth data.

Mapping

  • BNM RMiT (2025): Section 10.5 (Capacity Management and Performance).

  • CIS Benchmarks v8: Control 18 (Service Software Continuity).

  • NIST SP 800-53: AU-4 (Audit Log Storage Capacity); AU-11 (Audit Record Retention).

MO-006Network Monitoring

Network Observability & Flow Logging (eBPF)

High

Description

Traditional network monitoring relies on capturing packets, which is heavily resource-intensive. This control mandates the use of the OpenShift Network Observability Operator, which leverages eBPF (Extended Berkeley Packet Filter) technology to securely and efficiently monitor pod-to-pod network flows directly at the Linux kernel level.

Key Aspects of Network Observability:

  • eBPF FlowCollector: Captures highly granular network flow data (source, destination, protocol, bytes, dropped packets) without requiring a "sidecar" proxy in every pod.

  • Loki Integration: Flow data is stored in a highly scalable Loki datastore for fast querying and visualization.

  • Network Policy Verification: Provides real-time visual proof of whether a Network Policy (SC-006) is actively blocking or allowing specific traffic.

  • Topology Mapping: Automatically generates a visual dependency map of how microservices are communicating across the cluster.

What to Assess

  • Operator Status: Verify the Network Observability Operator is installed and the FlowCollector instance is active.

  • Data Retention: Confirm that Loki is backed by persistent object storage (ODF/S3) with an appropriate retention period for flow logs.

  • Sampling Rate: Ensure the eBPF sampling rate is tuned to balance visibility with bare-metal CPU overhead.

Technical Rationale

"Blind" networks are a massive security liability in a financial institution.

  • Detecting Lateral Movement: Allows the SOC to detect if a compromised frontend pod suddenly attempts to scan the IP addresses of the backend databases.

  • Troubleshooting Network Drops: Instantly identifies if a connection timeout is caused by a firewall drop, an OpenShift Network Policy, or an application-level failure.

  • Performance Optimization: Identifies "chatty" microservices that may be saturating the inter-node network bandwidth (AR-008).

Verification

  • Validation Method: Operator audit and flow querying.

Verification Steps:

  1. Check FlowCollector status:

    oc get flowcollector cluster -o yaml

  2. Verify Loki deployment:

    oc get pods -n netobserv | grep loki

  3. Console Verification:

    Navigate to Observe -> Network Traffic in the OpenShift Console to ensure data is populating.

Evidence

  • FlowCollector YAML: Snippet showing the eBPF agent configuration and Loki storage endpoint.

  • Traffic Topology Export: A screenshot from the console showing the mapped traffic flows of a critical banking application.

  • SIEM Integration Log: (If applicable) Proof that high-risk flow alerts are forwarded to the central SIEM.

Risk Impact

  • High Risk (Undetected Intrusions): Without flow logging, an attacker exfiltrating data out of the cluster may go completely unnoticed until the data appears on the dark web.

  • Operational Risk: Network engineers lack the data needed to resolve "finger-pointing" between the application and infrastructure teams during an outage.

  • Compliance Risk: Fails the RMiT Section 11.2 requirement for monitoring internal network traffic in critical systems.

Mapping

  • BNM RMiT (2025): Section 11.2 (Network Security); Section 11.5 (Logging and Monitoring).

  • CIS Benchmarks v8: Control 13 (Network Monitoring and Defense).

  • NIST SP 800-53: SI-4 (Information System Monitoring); SC-7 (Boundary Protection).

MO-007Application Observability

Distributed Tracing (OpenTelemetry & Jaeger)

Moderate

Description

In a microservices architecture, a single user click (e.g., "Transfer Funds") might traverse 10 different pods across 5 different bare-metal nodes. Distributed Tracing uses OpenTelemetry and Jaeger to inject a unique "Trace ID" into the request header, tracking its journey and timing at every hop.

Key Aspects of Distributed Tracing:

  • OpenTelemetry Integration: The standardized framework used to instrument the banking applications (Java, Go, Node.js) to emit trace data.

  • Span Measurement: A "Trace" is made up of "Spans." Each span measures the exact time spent in a specific function or database query.

  • Jaeger Backend: The centralized datastore and UI used to visualize the traces and identify bottlenecks.

  • Sampling Strategies: Configuring probabilistic sampling (e.g., capturing 5% of all traffic) to avoid overwhelming the storage backend during peak loads.

What to Assess

  • Operator Presence: Confirm the OpenShift Distributed Tracing Platform (Jaeger) and OpenTelemetry Operators are installed.

  • Application Instrumentation: Verify that critical production applications have the OpenTelemetry agent injected (via auto-instrumentation or code libraries).

  • Trace Generation: Confirm that valid traces are appearing in the Jaeger UI.

Technical Rationale

Traditional logging (MO-002) is insufficient for debugging complex, asynchronous microservices.

  • Pinpointing Latency: Identifies exactly which microservice—or which specific SQL query—is causing a 5-second delay in the mobile banking app.

  • Error Isolation: If a transaction fails, tracing shows the exact sequence of events leading up to the failure, drastically reducing Mean Time to Resolution (MTTR).

  • Architecture Validation: Visually proves that requests are adhering to the designed application architecture and not making redundant or circular calls.

Verification

  • Validation Method: Operator check and trace UI audit.

Verification Steps:

  1. Check OTel Collectors:

    oc get opentelemetrycollector -A

  2. Check Jaeger instances:

    oc get jaeger -A

  3. UI Verification: Access the Jaeger Route and query for a trace associated with a known frontend transaction.

Evidence

  • Jaeger UI Trace Export: A screenshot or JSON export of a completed multi-hop transaction trace.

  • OTel Collector YAML: Showing the pipeline configuration for receiving and exporting traces.

  • Application Deployment YAML: Snippet showing the annotations or environment variables used to enable auto-instrumentation.

Risk Impact

  • Moderate Risk (Prolonged Outages): Diagnosing a microservice failure using only fragmented text logs can take hours, leading to prolonged SLA breaches.

  • Performance Risk: Hidden bottlenecks remain unoptimized, leading to poor customer experience and inefficient use of bare-metal CPU resources.

  • Operational Risk: High developer frustration and burnout due to the complexity of debugging distributed systems without the right tools.

Mapping

  • BNM RMiT (2025): Section 10.5 (Capacity and Performance Management).

  • CIS Benchmarks v8: Control 18 (Service Software Continuity).

  • NIST SP 800-53: SI-4 (Information System Monitoring).

MO-008Metrics & Telemetry

Synthetic Proactive Monitoring (Blackbox / Uptime)

High

Description

Standard monitoring tells you if a pod is Running. Synthetic Monitoring (often utilizing the Prometheus Blackbox Exporter) tells you if the application is actually functioning from the user's perspective. It involves simulating user traffic by sending continuous, automated HTTP/HTTPS, TCP, or DNS requests to the application's endpoints.

Key Aspects of Synthetic Monitoring:

  • Outside-In Testing: Probes should ideally originate from outside the cluster (e.g., a dedicated monitoring VM) or from a completely isolated namespace to test the full Ingress path (SC-013).

  • HTTP Status Assertion: Verifying not just that the port is open, but that the endpoint returns a 200 OK and specific expected text content.

  • Certificate Expiration Alerts: Using synthetic probes to monitor the expiry dates of the TLS certificates on the Ingress routes.

  • Latency Baselines: Tracking the time to first byte (TTFB) to ensure performance SLAs are met.

What to Assess

  • Probe Configuration: Verify that Probe objects (part of the Prometheus Operator) are defined for all Tier 1 application endpoints.

  • Target Diversity: Ensure probes test both the internal Service IPs and the external public/corporate Routes.

  • Alert Rules: Confirm that an alert is triggered if an endpoint fails consecutively (e.g., 3 failures over 3 minutes).

Technical Rationale

Applications can fail in ways that Kubernetes cannot detect internally (e.g., a database connection pool is exhausted, but the pod process hasn't crashed).

  • True Uptime Measurement: Measures availability exactly as the customer experiences it, providing the most accurate metric for SLA reporting.

  • Proactive Alerting: Alerts the operations team to a degraded service before customers start calling the helpdesk.

  • Ingress Validation: Verifies that external load balancers, DNS, and OpenShift routers are all functioning in unison.

Verification

  • Validation Method: Probe resource audit and Alertmanager check.

Verification Steps:

  1. List active probes:

    oc get probes -A

  2. Check Prometheus Targets: In the OpenShift Console, navigate to Observe -> Targets and filter for blackbox.

  3. Review Alert Rules:

    oc get prometheusrule -A | grep -i endpoint (Look for rules tied to probe success metrics).

Evidence

  • Probe YAML Configuration: Showing the target URL and the expected HTTP response code.

  • Grafana Uptime Dashboard: A screenshot showing the 99.99% uptime status generated from synthetic probe data.

  • TLS Expiry Alert Rule: A snippet of the Prometheus rule alerting on certificates expiring in < 14 days.

Risk Impact

  • High Risk (Silent Outages): The cluster reports all pods are healthy, but an internal application deadlock prevents users from logging in, severely damaging the bank's reputation.

  • Operational Risk: Reactive, rather than proactive, incident management.

  • Compliance Risk: Inability to provide accurate, independent verification of system uptime to regulators.

Mapping

  • BNM RMiT (2025): Section 10.3 (Availability and Resilience).

  • CIS Benchmarks v8: Control 18 (Service Software Continuity).

  • NIST SP 800-53: SI-4 (Information System Monitoring).

MO-009Metrics & Telemetry

Cluster State Metrics (kube-state-metrics)

Moderate

Description

While Prometheus natively collects hardware metrics (CPU, Memory, Disk I/O), it requires kube-state-metrics (KSM) to understand the logical state of Kubernetes objects. This control ensures KSM is fully operational and configured to monitor the lifecycle of deployments, nodes, pods, and quotas.

Key Aspects of Kube-State-Metrics:

  • Object Lifecycle Tracking: Emits metrics on the status of Deployments, StatefulSets, DaemonSets, and CronJobs.

  • CrashLoopBackOff Detection: Provides the data necessary to alert when a pod is constantly crashing and restarting.

  • Resource Quota Monitoring: Tracks namespace-level ResourceQuotas, triggering alerts before a development team hits their maximum CPU limit and gets blocked from deploying.

  • Node Readiness: Monitors the Ready and NotReady conditions of the bare-metal nodes (AR-004).

What to Assess

  • Deployment Status: Confirm the kube-state-metrics deployment is running within the openshift-monitoring namespace.

  • Alerting Rules: Audit the default Prometheus rules to ensure alerts like KubePodCrashLooping, KubeDeploymentReplicasMismatch, and KubeNodeNotReady are active.

  • Scrape Configuration: Verify that Prometheus is successfully scraping the KSM endpoint without dropping metrics due to high cardinality.

Technical Rationale

Application health is intrinsically tied to the state of its Kubernetes orchestration objects.

  • Configuration Error Detection: Instantly flags deployments that are "stuck" because of a typo in an image name or a missing Secret.

  • Capacity Forecasting: By monitoring quotas vs. actual usage, platform engineers can proactively allocate more resources to growing business units.

  • Job Reliability: Ensures that critical scheduled tasks (like nightly database backups or batch processing CronJobs) completed successfully.

Verification

  • Validation Method: Pod verification and PromQL query testing.

Verification Steps:

  1. Check KSM pod:

    oc get pods -n openshift-monitoring -l app.kubernetes.io/name=kube-state-metrics

  2. PromQL Test: In the Console UI, execute the query kube_pod_status_phase{phase="Failed"}.

  3. Check active rules:

    oc get prometheusrule kube-state-metrics -n openshift-monitoring -o yaml

Evidence

  • Prometheus Alert Rule YAML: Showing the configuration for CrashLoopBackOff alerting.

  • Grafana Dashboard Screenshot: Showing a "Cluster Health" dashboard powered by KSM data (e.g., Total Pods, Nodes Offline).

  • PromQL Query Result: Export of metric data showing accurate state tracking.

Risk Impact

  • Moderate Risk (Deployment Stalls): Without KSM, a failed deployment update will just sit indefinitely without notifying the CI/CD pipeline or the operations team.

  • Operational Risk: "Ghost" pods consuming resources in an error state without being detected and remediated.

  • Efficiency Risk: Inability to effectively enforce or monitor Resource Quotas across multi-tenant clusters.

Mapping

MO-010Audit and Logging

Kubernetes Event Forwarding & Archiving

High

Description

Kubernetes "Events" are objects generated by the cluster in response to state changes (e.g., an image pulling successfully, a pod being evicted due to memory pressure, or a node rebooting). By default, these events are stored in etcd and deleted after 1 hour. This control mandates that Events be captured and forwarded to the central SIEM for long-term archiving.

Key Aspects of Event Forwarding:

  • Event Router/Collector: Utilizing the OpenShift Logging ClusterLogForwarder (with the kubernetes.events input) or deploying an eventrouter pod to capture this data stream.

  • SIEM Indexing: Events must be pushed to a searchable index in the SIEM (MO-002) alongside standard application and audit logs.

  • Alert Generation: Translating specific high-severity Kubernetes Events (e.g., FailedToPullImage, NodeHasDiskPressure) into actionable SIEM alerts.

  • Historical Context: Providing the operational narrative for why a system behaved the way it did days or weeks after the occurrence.

What to Assess

  • Forwarding Pipeline: Verify the OpenShift Logging configuration to ensure Kubernetes Events are explicitly included in the output stream.

  • Data Verification in SIEM: Confirm with the SOC or monitoring team that the SIEM contains OpenShift event data older than 24 hours.

  • Format Integrity: Ensure the forwarded events contain the original JSON metadata (reason, message, object reference) for accurate parsing.

Technical Rationale

A one-hour retention period is fundamentally incompatible with enterprise incident investigation.

  • Post-Mortem Analysis: If a major outage occurs at 2:00 AM and engineers log in at 8:00 AM, the cluster events that triggered the outage have already been erased. Event forwarding preserves this critical timeline.

  • Security Forensics: Captures low-level operational anomalies (like an unexpected node reboot or a flood of pod evictions) that might indicate a sophisticated denial-of-service attack.

  • Troubleshooting Context: While logs show what an application is doing, Events show what the platform is doing to the application.

Verification

  • Validation Method: Forwarder config audit and SIEM query validation.

Verification Steps:

  1. Check ClusterLogForwarder:

    oc get clusterlogforwarder instance -n openshift-logging -o yaml (Look for the infrastructure or specific event inputs being routed).

  2. Generate a test event:

    oc run test-event-pod --image=nginx:does-not-exist (This forces a FailedToPullImage event).

  3. Verify SIEM:

    Check the central logging system to ensure the generated test event was successfully received and archived.

Evidence

  • ClusterLogForwarder YAML: Snippet showing the inclusion of system events in the SIEM pipeline.

  • SIEM Screenshot: A view from Splunk/Elastic showing the test-event-pod failure event safely archived.

  • Retention Policy Document: Documentation proving the SIEM retains these events for the duration required by financial regulations (e.g., 1-7 years).

Risk Impact

  • High Risk (Loss of Incident Context): Inability to accurately determine the root cause of transient or historical cluster failures, leading to repeated, preventable outages.

  • Compliance Risk: May result in non-compliance with regulatory requirements for comprehensive system activity logging and incident reporting data preservation.

  • Operational Risk: Wasted engineering hours trying to reconstruct the timeline of an event without the native orchestration data.

Mapping

  • BNM RMiT (2025): Section 11.5 (Logging and Security Monitoring); Section 12.1 (Incident Management).

  • CIS Benchmarks v8: Control 8 (Audit Log Management).

  • NIST SP 800-53: AU-2 (Event Logging); AU-11 (Audit Record Retention).
