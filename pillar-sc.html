Pillar 4: Security & Compliance

Architecture assessment page for validating identity and access control, workload hardening, cryptographic controls, network security, infrastructure protection, vulnerability management, supply-chain trust, and data protection controls.

Use note: This page is a consulting assessment artefact for OpenShift architecture and operations review. It is not an official Red Hat methodology. Validate technical statements and command syntax against the target OpenShift version and client environment before use.

Security and Compliance define the platform's capability to protect identities, workloads, data, infrastructure, network paths, and software supply chains through enforceable policies and auditable controls. For OpenShift environments supporting containerized workloads and OpenShift Virtualization on bare-metal infrastructure, these controls validate that RBAC, identity provider integration, pod admission controls, SELinux, FIPS, network policies, TLS, API hardening, secret encryption, immutable nodes, runtime hardening, vulnerability scanning, image signing, node-to-node encryption, and key management are implemented through tested, evidence-backed security practices.

SC-001Identity and Access Management

RBAC Implementation (Least Privilege)

Critical

Description

Role-Based Access Control (RBAC) is the foundational security mechanism in OpenShift that regulates access to cluster resources based on the roles of individual users or groups. This control mandates the enforcement of the Principle of Least Privilege (PoLP), ensuring users have only the minimum permissions necessary to perform their job functions.

Key Aspects of RBAC:

  • Role/ClusterRole: Defining sets of permissions (verbs like get, list, create) at either the namespace or cluster level.

  • RoleBinding/ClusterRoleBinding: Granting defined roles to specific users, groups, or service accounts.

  • Default Deny: Access is denied by default; all permissions must be explicitly granted.

  • Separation of Duties: Distinct roles for Cluster Admins, Network Admins, and Application Developers to prevent a single account from having total control over the environment.

What to Assess

  • Cluster Admin Audit: Verify the number of users with the cluster-admin role; this should be limited to a minimal set of infrastructure engineers.

  • Default Roles: Confirm that no users are using broad default roles like edit or admin at the cluster level.

  • Service Account Review: Ensure service accounts used by applications do not have excessive permissions (e.g., ability to list secrets in other namespaces).

Technical Rationale

In a banking environment, uncontrolled administrative access is a significant risk.

  • Blast Radius Limitation: If a developer's credentials are compromised, RBAC ensures the attacker is confined to a specific namespace and cannot escalate to the cluster level.

  • Auditability: Standardizing roles makes it easier to audit "who can do what," which is a core requirement of RMiT Section 11.2.

  • Insider Threat Mitigation: Prevents unauthorized changes to security policies or logging configurations by non-security personnel.

Verification

  • Validation Method: RBAC policy audit and binding analysis.

Verification Steps:

  1. List all Cluster Admins:

    oc get clusterrolebinding -o json | jq '.items[] | select(.roleRef.name=="cluster-admin") | .subjects'

  2. Check permissions for a specific user:

    oc adm policy who-can <verb> <resource>

  3. Audit namespace-level bindings:

    oc get rolebindings -n <namespace>

Evidence

  • RBAC Binding Report: An export of all ClusterRoleBindings and RoleBindings for production namespaces.

  • Policy Verification Log: Output of oc adm policy who-can delete nodes showing only authorized groups.

  • Custom Role YAML: Snippets of custom-defined roles that follow the "Least Privilege" model for developers.

Risk Impact

  • Critical Risk (Privilege Escalation): Weak RBAC allows a malicious actor to gain full control of the cluster, potentially leading to data exfiltration or total system destruction.

  • Compliance Risk: Failure to demonstrate strict access controls violates RMiT and CIS Benchmarks.

  • Operational Risk: Accidental deletion of critical cluster components (like the etcd operator) by an over-privileged user.

Mapping

  • BNM RMiT (2025): Section 11.2 (User Access Management).

  • CIS Benchmarks v8: Control 5 (Account Management); Control 6 (Access Control Management).

  • NIST SP 800-53: AC-2 (Account Management); AC-3 (Access Enforcement).

SC-002Identity and Access Management

Identity Provider (IDP) Integration (AD/LDAP/OIDC)

High

Description

OpenShift should never use local "htpasswd" files for production user management. This control mandates the integration of OpenShift with an enterprise-grade Identity Provider (IDP) such as Microsoft Active Directory (via LDAP), Azure AD, or an OIDC-compliant provider (e.g., Keycloak).

Key Aspects of IDP Integration:

  • Centralized Authentication: Users log in using their standard corporate credentials, ensuring a single source of truth for identity.

  • Group Syncing: Automatically mapping corporate groups (e.g., AD_OCP_ADMINS) to OpenShift RBAC groups, automating onboarding and offboarding.

  • Multi-Factor Authentication (MFA): Leveraging the IDP's MFA capabilities (e.g., Microsoft Authenticator or Duo) to secure cluster access.

  • Token Management: Utilizing short-lived OAuth tokens for CLI and Console access.

What to Assess

  • OAuth Configuration: Verify the OAuth cluster resource to see the configured IDPs.

  • MFA Enforcement: Confirm that the connected IDP is enforcing MFA for all users with administrative roles.

  • Local Account Status: Verify that the default kubeadmin user is disabled or its password is securely vaulted and only used for emergencies.

Technical Rationale

Identity is the new perimeter in modern infrastructure.

  • Automated Offboarding: When an employee leaves the bank and their AD account is disabled, their access to OpenShift is revoked automatically.

  • Password Policy Enforcement: Ensures that corporate password complexity and rotation policies are applied to cluster access.

  • Audit Consistency: Logs will reflect actual corporate usernames (e.g., george.titus) rather than generic local accounts, making forensic analysis possible.

Verification

  • Validation Method: OAuth configuration audit.

Verification Steps:

  1. Check IDP configuration:

    oc get oauth cluster -o yaml

  2. Verify group synchronization:

    oc get groups (Compare against AD/LDAP source).

  3. Attempt login: Verify the login flow redirects to the corporate identity portal.

Evidence

  • OAuth YAML: Export showing the LDAP/OIDC provider details (with sensitive secrets redacted).

  • Group Mapping Log: Evidence of successful group synchronization from the external IDP.

  • Authentication Log: A sample log showing a successful login via the corporate IDP with MFA verification.

Risk Impact

  • High Risk (Unauthorized Access): Use of local accounts makes offboarding difficult, potentially leaving "backdoor" access for former employees.

  • Compliance Risk: Violates RMiT requirements for "Strong Authentication" and "Centralized Identity Management".

  • Security Risk: Without MFA, a single credential leak (phishing) can grant an attacker access to the management plane of the cluster.

Mapping

  • BNM RMiT (2025): Section 11.2 (User Access Management).

  • CIS Benchmarks v8: Control 5 (Account Management).

  • NIST SP 800-53: IA-2 (Identification and Authentication); IA-5 (Authenticator Management).

SC-003Workload Security

Pod Security Admissions (PSA) Enforcement

Critical

Description

Pod Security Admissions (PSA) is the Kubernetes-native replacement for Pod Security Policies (PSP). It evaluates pod specifications against a set of security standards (Privileged, Baseline, or Restricted) and blocks the creation of pods that do not comply.

Key Aspects of PSA:

  • Restricted Profile: The mandatory standard for production banking workloads. It prevents pods from running as root, using host networking, or mounting sensitive host paths.

  • Namespace-Level Enforcement: Policies are applied via labels on the namespace (e.g., pod-security.kubernetes.io/enforce: restricted).

  • Audit Mode: Allows administrators to "Audit" or "Warn" on non-compliant pods before switching to strict "Enforce" mode.

  • Exemption Management: Carefully controlled exemptions for system-level pods (e.g., Ingress or Logging) while maintaining a strict posture for user applications.

What to Assess

  • Namespace Labels: Verify that all production and UAT namespaces have the restricted enforcement label.

  • Exemptions: Audit the PodSecurityConfiguration to ensure no general-purpose namespaces are exempted from the checks.

  • Compliance Check: Attempt to deploy a privileged pod in a restricted namespace; the action must be blocked.

Technical Rationale

Container "breakouts" often rely on excessive pod privileges.

  • Prevention of Container Breakouts: By blocking "Privileged" containers, PSA ensures that an attacker who compromises a container cannot easily gain control of the underlying bare-metal host.

  • Host Protection: Prevents pods from accessing /etc/shadow or other sensitive host files through hostPath mounts.

  • Standardization: Provides a consistent, out-of-the-box security baseline across the entire cluster.

Verification

  • Validation Method: Namespace metadata audit and negative testing.

Verification Steps:

  1. Check labels:

    oc get namespaces --show-labels | grep pod-security

  2. Negative Test:

    oc run privileged-test --image=bitnami/nginx --privileged -n <prod-namespace> (Expected result: Error from server (Forbidden))

Evidence

  • Namespace Label Export: A list of all namespaces and their enforced PSA level.

  • Blocked Event Log: An audit log showing the PSA controller rejecting an insecure pod request.

  • Cluster-wide PSA Policy: Export of the global PSA configuration resource.

Risk Impact

  • Critical Risk (Host Compromise): Without PSA, a single compromised "privileged" container can lead to full access to the bare-metal server and all other workloads running on it.

  • Security Risk: Running as root (UID 0) allows an attacker to bypass many internal container security layers.

  • Compliance Risk: Violates CIS Benchmarks for Kubernetes and RMiT guidelines for "System Hardening".

Mapping

  • BNM RMiT (2025): Section 11.3 (System and Network Hardening).

  • CIS Benchmarks v8: Control 18 (Service Software Continuity).

  • NIST SP 800-53: SC-7 (Boundary Protection); AC-3 (Access Enforcement).

SC-004System Hardening

SELinux Reinforcement

Critical

Description

SELinux (Security-Enhanced Linux) is a mandatory access control (MAC) system that is enabled by default in Red Hat Enterprise Linux CoreOS (RHCOS). On OpenShift, SELinux ensures that every container is confined to a unique security context, preventing it from interacting with the host or other containers even if it is compromised.

Key Aspects of SELinux:

  • Enforcing Mode: SELinux must always be in Enforcing mode, never Permissive or Disabled.

  • MCS (Multi-Category Security) Labeling: OpenShift automatically assigns a unique SELinux label to each pod and its volumes. Only a pod with the matching label can access its specific data.

  • Context Isolation: Even if a container manages to "escape" to the host, SELinux prevents it from reading or writing to any host file not explicitly labeled for container use.

What to Assess

  • Node Status: Verify that all nodes (Master/Worker) are in Enforcing mode.

  • Pod Contexts: Confirm that running pods have assigned SELinux contexts (e.g., s0:c12,c34).

  • Audit Logs: Check the node audit logs for any avc: denied messages, which indicate SELinux successfully blocked an unauthorized action.

Technical Rationale

SELinux is the "Final Defense" against Zero-Day exploits.

  • Kernel-Level Protection: Provides an independent layer of security that does not rely on the container runtime or Kubernetes configuration.

  • Prevention of Cross-Pod Data Theft: If Pod A is compromised, SELinux ensures it cannot read the persistent volume attached to Pod B, even if the file permissions appear to allow it.

  • Host Hardening: Protects critical bare-metal OS files (like /boot or /root) from any unauthorized container access.

Verification

  • Validation Method: Node and Pod level inspection.

Verification Steps:

  1. Check node mode:

    oc debug node/<node-name> -- chroot /host getenforce (Must return Enforcing).

  2. Check pod context:

    oc get pod <name> -o jsonpath='{.spec.securityContext.seLinuxOptions}'

  3. Verify container process:

    oc exec <pod> -- ps -Z

Evidence

  • Getenforce Output: Proving all production nodes are in Enforcing mode.

  • AVC Denial Report: A filtered list of blocked SELinux events (if any) from the node's /var/log/audit/audit.log.

  • Pod Security Context Export: Showing the unique MCS labels assigned to different applications.

Risk Impact

  • Critical Risk (Kernel Escape): If SELinux is disabled, a kernel vulnerability could allow an attacker to gain full root access to the physical host.

  • High Risk (Lateral Movement): Without SELinux labels, a compromised container could potentially read the data of every other container on the same host.

  • Compliance Risk: Non-compliant with Red Hat's security baseline and general financial industry hardening standards.

Mapping

  • BNM RMiT (2025): Section 11.3 (System and Network Hardening).

  • CIS Benchmarks v8: Control 3 (Data Protection).

  • NIST SP 800-53: AC-3 (Access Enforcement); SI-7 (Software, Firmware, and Information Integrity).

SC-005Cryptographic Standards

FIPS 140-2/3 Compliance

High

Description

For high-security banking environments, the underlying operating system and the OpenShift platform itself must be configured to use FIPS-validated cryptographic modules. This ensures that all encryption (at rest and in transit) utilizes algorithms and implementations that have been strictly tested and certified.

Key Aspects of FIPS Compliance:

  • FIPS Mode: Enabling FIPS at the kernel level during the initial installation of RHCOS. This cannot be enabled later.

  • Restricted Algorithms: The system will block the use of non-compliant algorithms (e.g., MD5 or older versions of SHA).

  • Golang Compliance: OpenShift's internal components (written in Go) are compiled to use the FIPS-validated OpenSSL library.

  • End-to-End Cryptography: Ensures that everything from etcd encryption (RC-001) to Ingress TLS (SC-008) uses FIPS-compliant cryptography.

What to Assess

  • Kernel Check: Verify that the fips=1 flag is present in the kernel arguments on all nodes.

  • Crypto Status: Confirm that the internal cryptographic checks return a "FIPS enabled" status.

  • Algorithm Audit: Ensure that any custom application encryption also utilizes FIPS-validated libraries.

Technical Rationale

Financial institutions are often mandated to use FIPS-validated crypto for all sensitive data handling.

  • Regulatory Alignment: Directly addresses RMiT requirements for "Strong Cryptography" and "Standardized Encryption Algorithms".

  • Guaranteed Strength: Prevents the accidental use of "broken" or weak encryption that could be decrypted by unauthorized parties.

  • Audit Readiness: Provides a clear, certified baseline for auditors to verify the cryptographic strength of the entire platform.

Verification

  • Validation Method: Node-level kernel and crypto check.

Verification Steps:

  1. Check kernel args:

    oc debug node/<node-name> -- chroot /host cat /proc/cmdline | grep fips=1

  2. Verify crypto status:

    oc debug node/<node-name> -- chroot /host cat /proc/sys/crypto/fips_enabled (Must return 1).

  3. Check platform status:

    oc get infrastructures cluster -o jsonpath='{.status.fipsDisabled}' (Must be false).

Evidence

  • Fips_enabled Output: Proving FIPS is active at the OS level.

  • Infrastructure Resource Export: Showing the cluster was installed with FIPS mode enabled.

  • OpenSSL Check: Output showing the node's OpenSSL is operating in FIPS mode.

Risk Impact

  • High Risk (Cryptographic Vulnerability): Use of non-validated crypto may leave data vulnerable to decryption through known weaknesses in older algorithms.

  • Compliance Risk: Immediate failure of many high-level financial security audits (like SWIFT or BNM RMiT) that require validated encryption.

  • Interoperability Risk: Some external secure gateways may reject connections that do not meet FIPS standards.

Mapping

  • BNM RMiT (2025): Section 11.1 (Data Integrity); Section 11.3 (Hardening).

  • CIS Benchmarks v8: Control 3 (Data Protection).

  • NIST SP 800-53: SC-13 (Cryptographic Protection).

SC-006Network Security

Network Policies (Namespace Isolation)

Critical

Description

By default, Kubernetes networking is a "flat" structure where all pods can communicate with all other pods across the cluster. Network Policies act as a pod-level firewall, allowing administrators to define explicit "Allow" rules for ingress and egress traffic. This control mandates a Default Deny posture for all production namespaces.

Key Aspects of Network Policies:

  • Default Deny: A catch-all policy that drops all traffic to and from a namespace unless a specific permit rule exists.

  • Label-Based Filtering: Defining rules based on pod labels (e.g., "Allow traffic from app=frontend to app=backend").

  • Namespace Selectors: Restricting traffic between different business units or environments (e.g., "Block all traffic from UAT namespace to PROD").

  • Port/Protocol Restriction: Limiting communication to specific necessary ports (e.g., only TCP 5432 for database access).

What to Assess

  • Default Deny Policy: Verify that a NetworkPolicy exists in each namespace with an empty podSelector that denies all ingress/egress.

  • Allow-List Audit: Review existing policies to ensure they are not too broad (e.g., using 0.0.0.0/0 instead of specific pod selectors).

  • Policy Coverage: Confirm that all applications in production are covered by at least one explicit Network Policy.

Technical Rationale

In a banking environment, lateral movement is the primary technique used by attackers after an initial compromise.

  • Micro-segmentation: Ensures that even if a web-facing pod is compromised, the attacker cannot reach the core database or other internal services.

  • Reduction of Attack Surface: Limits the "visibility" of the cluster; an attacker cannot perform internal port scanning if a default-deny policy is in place.

  • Regulatory Compliance: Directly fulfills RMiT requirements for "Network Segmentation" and "Internal Firewalling" within critical systems.

Verification

  • Validation Method: Network policy inspection and connectivity testing.

Verification Steps:

  1. Check for Default Deny:

    oc get networkpolicy -n <namespace> -o yaml

  2. Test blocked traffic:

    oc exec <pod-a> -- curl <pod-b-ip> (Should time out).

  3. Verify active flows: Use the OpenShift Console "Network Observability" plugin to visualize blocked vs. allowed flows.

Evidence

  • NetworkPolicy YAML: Export of the default-deny and application-specific permit policies.

  • Connectivity Matrix: A document showing the intended flow of traffic between microservices.

  • Observability Screenshot: A visual graph from the console showing restricted traffic patterns.

Risk Impact

  • Critical Risk (Lateral Movement): Without network policies, a single compromised pod can scan and attack every other service in the cluster, including the control plane.

  • High Risk (Data Exfiltration): Lack of egress controls allows a compromised pod to send banking data to a malicious external command-and-control (C2) server.

  • Compliance Risk: Immediate non-compliance with RMiT Section 11.2 regarding network security.

Mapping

  • BNM RMiT (2025): Section 11.2 (Network Security).

  • CIS Benchmarks v8: Control 12 (Network Infrastructure Management).

  • NIST SP 800-53: SC-7 (Boundary Protection).

SC-007Network Security

Egress Firewalls (EgressNetworkPolicy)

High

Description

While Network Policies (SC-006) manage traffic within the cluster, Egress Firewalls (or EgressNetworkPolicies) manage traffic leaving the cluster to the external banking network or the internet. This control restricts which external IP addresses or DNS domains a pod can communicate with.

Key Aspects of Egress Firewalls:

  • IP-Based Rules: Restricting pod access to specific external database IPs or API gateways.

  • Domain-Based Rules: (In OVN-Kubernetes) Allowing access to specific FQDNs (e.g., api.agrobank.com.my) while blocking everything else.

  • Namespace Scoping: Policies are applied at the namespace level, ensuring that different applications have different external access profiles.

  • Integration with Corporate Firewalls: Acts as the first layer of defense before traffic reaches the physical data center perimeter firewalls.

What to Assess

  • Policy Existence: Verify EgressNetworkPolicy objects exist in namespaces requiring external access.

  • Rule Precision: Confirm rules use CIDR blocks or FQDNs rather than broad allow-alls.

  • Logging: Check if egress violations are being logged in the cluster's centralized logging system.

Technical Rationale

Endpoints within the cluster should not have unrestricted internet access.

  • Prevention of Data Phoning Home: If a pod is infected with malware, an egress firewall blocks it from reaching the attacker's external server.

  • Dependency Protection: Ensures that application pods only talk to authorized external services (e.g., specific SWIFT gateways or payment processors).

  • Regulatory Alignment: Supports RMiT's requirement for controlling outbound connections from critical environments.

Verification

  • Validation Method: Policy audit and egress testing.

Verification Steps:

  1. List egress policies:

    oc get egressnetworkpolicy -n <namespace>

  2. Negative Test:

    oc exec <pod> -- curl http://www.google.com (Should be denied if not explicitly allowed).

  3. Inspect policy rules:

    oc describe egressnetworkpolicy <name>.

Evidence

  • EgressNetworkPolicy YAML: Export showing the allowed external destinations.

  • Egress Log Export: A sample log showing a blocked attempt to reach an unauthorized external IP.

  • External Dependency List: A document mapping applications to their required external service endpoints.

Risk Impact

  • High Risk (Data Exfiltration): Unrestricted egress allows an attacker to "tunnel" sensitive data out of the cluster using common protocols like HTTPS or DNS.

  • Security Risk: Allows pods to download malicious scripts or tools from the internet after an initial compromise.

  • Compliance Risk: Fails the RMiT requirement for "outbound traffic filtering" for critical systems.

Mapping

  • BNM RMiT (2025): Section 11.2 (Network Security).

  • CIS Benchmarks v8: Control 13 (Network Monitoring and Defense).

  • NIST SP 800-53: SC-7 (Boundary Protection).

SC-008Data in Transit

Ingress TLS Encryption (Route Hardening)

Critical

Description

All external traffic entering the OpenShift cluster must be encrypted using Transport Layer Security (TLS). This control mandates that every "Route" uses secure termination (Edge, Re-encrypt, or Passthrough) and utilizes strong, bank-approved cipher suites.

Key Aspects of Ingress Hardening:

  • TLS Termination Types:

  • Edge: TLS is terminated at the router (Ingress Controller).

  • Re-encrypt: TLS is terminated at the router and then re-encrypted before being sent to the pod (mandatory for end-to-end security).

  • HSTS (HTTP Strict Transport Security): Forcing browsers to communicate only over HTTPS.

  • Minimum TLS Version: Restricting connections to TLS 1.2 or 1.3 only.

  • Certificate Management: Utilizing automated certificate rotation (e.g., via cert-manager) with CA-signed certificates.

What to Assess

  • Route Audit: Scan all routes for termination: edge or reencrypt and ensure none are set to allowHTTP: true.

  • Cipher Suite Check: Verify the IngressController configuration to ensure weak ciphers (e.g., DES, RC4) are disabled.

  • Certificate Validity: Confirm certificates are valid, unexpired, and issued by an approved internal or public Certificate Authority (CA).

Technical Rationale

Cleartext traffic (HTTP) is unacceptable for banking data.

  • Prevention of Eavesdropping: Ensures that sensitive customer data (PINs, account numbers) cannot be intercepted by anyone on the network path.

  • Man-in-the-Middle (MitM) Protection: Cryptographic verification ensures the user is communicating with the genuine Agrobank service.

  • Compliance: Fulfills RMiT's mandate for "strong encryption for data in transit".

Verification

  • Validation Method: Route configuration audit and SSL scanning.

Verification Steps:

  1. Check for insecure routes:

    oc get routes -A -o json | jq '.items[] | select(.spec.tls==null)'

  2. Check TLS version:

    openssl s_client -connect <route-url>:443 -tls1_2

  3. Verify HSTS:

    curl -I https://<route-url> (Check for Strict-Transport-Security header).

Evidence

  • Route Resource YAML: Snippet showing the TLS configuration and HSTS annotations.

  • SSL Labs / Qualys Report: A scan showing an "A" or "A+" rating for the production ingress.

  • IngressController Config: Showing the global TLS profile and cipher restrictions.

Risk Impact

  • Critical Risk (Data Interception): Use of HTTP or weak TLS allows attackers to steal credentials and transaction data in plain text.

  • Reputational Risk: Browsers showing "Not Secure" warnings for banking portals.

  • Compliance Risk: Direct violation of RMiT Section 11.1 and 11.3 regarding data protection.

Mapping

  • BNM RMiT (2025): Section 11.1 (Data Integrity); Section 11.3 (Hardening).

  • CIS Benchmarks v8: Control 3 (Data Protection).

  • NIST SP 800-53: SC-8 (Transmission Confidentiality and Integrity).

SC-009Infrastructure Security

API Server Hardening & Private Endpoints

Critical

Description

The OpenShift API Server is the most sensitive endpoint in the cluster. This control mandates that the API server be restricted from public internet access and secured through IP allow-listing and private networking.

Key Aspects of API Hardening:

  • Internal-Only Access: Configuring the API server to be reachable only via the internal corporate VPN or leased lines.

  • IP Allow-listing: Restricting API access to a specific range of "Jump Host" or "Admin VDI" IP addresses.

  • Audit Logging: Enabling full request/response auditing to track every administrative action (MO-004).

  • Load Balancer Isolation: Using a private Internal Load Balancer (ILB) to front the master nodes.

What to Assess

  • Public Access Check: Attempt to reach the API endpoint (https://api.<cluster-name>.<domain>:6443) from an external, non-VPN network. It must fail.

  • Infrastructure Config: Verify the Infrastructure resource to ensure apiServer.servingCerts and endpoints are configured as "Internal."

  • Firewall Rules: Confirm with the network team that port 6443 is blocked at the data center perimeter.

Technical Rationale

The management plane is the primary target for advanced persistent threats (APTs).

  • Prevention of Brute Force: If the API is not on the internet, it cannot be scanned or brute-forced by external bots.

  • Management Plane Isolation: Ensures that even if the "Data Plane" (applications) is under a DDoS attack, the "Control Plane" remains accessible to administrators.

  • Audit Readiness: Strict access controls on the API fulfill RMiT requirements for "Administrator Access Security".

Verification

  • Validation Method: Network reachability testing and configuration audit.

Verification Steps:

  1. Check infrastructure status:

    oc get infrastructure cluster -o jsonpath='{.status.apiServerInternalURI}'

  2. Verify allow-list: Check the apiserver resource for additionalCORSAllowedOrigins or restricted CIDR configurations.

  3. Audit Log Check:

    oc get configmap -n openshift-kube-apiserver (Check for audit policy).

Evidence

  • Infrastructure YAML: Showing the internal API URI.

  • External Scan Result: Proving port 6443 is "Filtered" or "Closed" from the internet.

  • Admin VDI Proof: A screenshot showing API access is only possible from an authorized management workstation.

Risk Impact

  • Critical Risk (Full Cluster Takeover): An exposed API server with a single credential leak allows an attacker to delete the entire cluster or exfiltrate all data.

SC-010Data Protection

Secret Management & Encryption (etcd KMS)

Critical

Description

Kubernetes "Secrets" are stored in etcd and, by default, are only base64 encoded, not encrypted. This control mandates that Encryption at Rest be enabled for the etcd database using a KMS (Key Management Service) or a provider like AES-CBC.

Key Aspects of Secret Encryption:

  • etcd Encryption: Ensuring that if the physical disks are stolen or the etcd database is dumped, the secrets (passwords, TLS keys, API tokens) remain unreadable.

  • External KMS Integration: Utilizing an external Hardware Security Module (HSM) or HashiCorp Vault to manage the encryption keys.

  • Automatic Rotation: Periodically rotating the encryption keys to minimize the impact of a potential key compromise.

  • Least Privilege Secret Access: Using RBAC (SC-001) to ensure pods can only see the specific secrets they require.

What to Assess

  • Encryption Status: Verify the apiserver cluster resource shows encryption is active.

  • Algorithm Check: Confirm that a strong algorithm (e.g., aescbc) is in use.

  • Rotation Schedule: Audit the logs to see when the last secret encryption key rotation occurred.

Technical Rationale

Secrets are the "Keys to the Kingdom."

  • Protection of Credentials: Ensures that database passwords and internal certificates are never stored in cleartext on physical media.

  • Regulatory Compliance: Directly fulfills RMiT's requirement for "Encryption of sensitive data at rest".

  • Defense in Depth: Even if an attacker gains OS-level access to a master node, they cannot read the cluster secrets without the decryption key.

Verification

  • Validation Method: Configuration check and data verification.

Verification Steps:

  1. Verify encryption is on:

    oc get apiserver cluster -o jsonpath='{.spec.encryption.type}' (Should return aescbc).

  2. Check encryption progress:

  3. Test etcd data: (For auditors only) Attempt to read a secret directly from an etcd backup file; it must appear as encrypted gibberish.

Evidence

  • APIServer YAML: Showing the encryption stanza.

  • Encryption Status Log: Output showing the percentage of secrets successfully encrypted.

  • Vault/KMS Integration Proof: Documentation of the external key management lifecycle.

Risk Impact

  • Critical Risk (Secret Exposure): Without encryption, anyone with access to a master node backup or the storage layer can steal every password and certificate in the bank's cluster.

  • Compliance Risk: Immediate failure of RMiT and PCIDSS audits regarding the protection of sensitive data.

  • Operational Risk: Inability to securely rotate keys after a suspected breach.

Mapping

SC-011System Hardening

RHCOS Immutable Operating System

High

Description

Red Hat Enterprise Linux CoreOS (RHCOS) is the mandatory operating system for all OpenShift 4.x nodes. Unlike traditional Linux distributions, RHCOS is immutable, meaning the root filesystem is mounted as read-only. Changes to the OS configuration are not performed manually via SSH; instead, they are managed through a centralized Machine Config Operator (MCO).

Key Aspects of RHCOS:

  • Read-Only Root File System: Prevents persistent malware from modifying core system binaries (e.g., /usr).

  • Ignition-Based Provisioning: Nodes are initialized using a declarative "Ignition" config, ensuring every bare-metal node starts from an identical security baseline.

  • Transactional Updates: OS updates are performed as a single atomic unit; if an update fails, the node automatically rolls back to the previous known-good version.

  • Minimal Attack Surface: RHCOS excludes unnecessary packages (like Python, compilers, or standard shells) to reduce the surface area available to attackers.

What to Assess

  • Filesystem Status: Verify that /usr and other system directories are mounted as ro (read-only) on all nodes.

  • Manual Access Audit: Confirm that SSH access is restricted and that no manual modifications exist in /etc that aren't managed by a MachineConfig.

  • MCO Health: Ensure the Machine Config Operator is reporting a "Ready" status for all machine pools.

Technical Rationale

In a banking environment, "Configuration Drift" is a primary security risk.

  • Prevention of Unauthorized Persistence: Even if an attacker gains root access, they cannot easily modify the OS to survive a reboot because the filesystem is locked.

  • Auditability: Since all OS changes must go through the MCO, there is a clear, cluster-wide audit trail of every configuration change.

  • Rapid Recovery: In line with the "Cattle" model (RC-004), a compromised or misconfigured node can be wiped and re-imaged to its exact desired state in minutes.

Verification

  • Validation Method: Node-level filesystem and operator audit.

Verification Steps:

  1. Check mount status:

    oc debug node/<node-name> -- chroot /host mount | grep " /usr "

  2. Check MCO status:

    oc get machineconfigpool

  3. Verify OS immutability:

    oc debug node/<node-name> -- chroot /host touch /usr/bin/testfile (Expected result: Read-only file system).

Evidence

  • MachineConfigPool Output: Showing all nodes are "Updated" and "Ready."

  • Mount Point Report: Proving system directories are read-only across the bare-metal fleet.

  • Ignition Config Export: Snippets showing the declarative nature of node initialization.

Risk Impact

  • High Risk (System Tampering): Use of a non-immutable OS allows attackers to install "rootkits" that are nearly impossible to detect through standard container monitoring.

  • Operational Risk: Manual changes to nodes lead to "Snowflakes" that fail during cluster upgrades or disaster recovery.

  • Compliance Risk: Fails the RMiT requirement for "System Integrity" and "Standardized Build Images."

Mapping

  • BNM RMiT (2025): Section 11.3 (System Hardening).

  • CIS Benchmarks v8: Control 3 (Data Protection); Control 4 (Secure Configuration).

  • NIST SP 800-53: SI-7 (Software, Firmware, and Information Integrity).

SC-012Workload Security

Container User Mapping (Non-Root Enforcement)

Critical

Description

A core tenet of container security is that processes should never run as the root user (UID 0). This control mandates that all application containers use a non-privileged user and that OpenShift's Security Context Constraints (SCC) are used to enforce unique, random UIDs for every namespace.

Key Aspects of User Mapping:

  • MustRunAsNonRoot: Ensuring the container manifest explicitly denies running as root.

  • SCC Restricted Profile: By default, OpenShift's restricted-v2 SCC assigns a high-number random UID (e.g., 1000640000) to the container process.

  • User Namespace Isolation: Utilizing the Linux kernel's user namespace feature to map a container's "root" to a non-privileged user on the host.

  • Block SetUID/SetGID: Preventing containers from escalating their own privileges through special file bits.

What to Assess

  • SCC Audit: Verify that the restricted-v2 SCC is the default for all application service accounts.

  • Process Check: Inspect running containers to ensure the effective UID is not 0.

  • Manifest Review: Check for runAsUser or runAsNonRoot fields in the Pod Security Context.

Technical Rationale

Most container escape vulnerabilities rely on the process running as root within the container.

  • Privilege Containment: If an attacker gains a shell in a container running as a random UID, they cannot modify system files, install packages, or interact with the host kernel in a meaningful way.

  • Defense in Depth: Even if the container runtime has a bug, being a non-privileged user provides a critical second layer of protection against host-level compromise.

  • Multi-tenancy Safety: Ensures that Pod A in Namespace A cannot interfere with the files of Pod B, as they are running as entirely different UIDs on the physical host.

Verification

  • Validation Method: Pod process audit and SCC analysis.

Verification Steps:

  1. Check running UID:

    oc exec <pod-name> -- id (Should show a high-number UID, not 0).

  2. Check SCC assignment:

    oc get pod <pod-name> -o jsonpath='{.metadata.annotations.openshift\.io/scc}'

  3. Verify "Non-Root" enforcement:

    oc get pod <pod-name> -o jsonpath='{.spec.securityContext.runAsNonRoot}'

Evidence

  • SCC Restricted-V2 YAML: Showing the runAsUser: type: MustRunAsRange configuration.

  • Pod ID Output: Screenshot or log showing the application running as a non-privileged user.

  • Admission Controller Log: Proof of the cluster blocking a container that attempted to run as root.

Risk Impact

  • Critical Risk (Host Escape): Root containers can more easily exploit kernel vulnerabilities to take control of the bare-metal node.

  • Security Risk: Allows an attacker to easily install tools and modify the application environment if they gain access to the container.

  • Compliance Risk: Direct violation of RMiT Section 11.3 and CIS Benchmarks for secure container execution.

Mapping

  • BNM RMiT (2025): Section 11.3 (Hardening).

  • CIS Benchmarks v8: Control 18 (Service Software Continuity).

  • NIST SP 800-53: AC-3 (Access Enforcement); AC-6 (Least Privilege).

SC-013Workload Security

HostPath Mount Restrictions

Critical

Description

A hostPath volume mounts a file or directory from the host node's filesystem directly into a pod. This is one of the most dangerous capabilities in OpenShift. This control mandates that hostPath mounts be strictly forbidden for all application workloads, with exceptions only granted for critical system agents.

Key Aspects of HostPath Restrictions:

  • Volume Type Blocking: Using PSA (SC-003) and SCC (SC-12) to block the hostPath volume type in all user namespaces.

  • Alternative Storage: Forcing the use of Persistent Volumes (PVs) from ODF or other managed storage (AR-010) instead of local host directories.

  • Read-Only Exceptions: If a system agent must use a hostPath (e.g., for log collection), it must be mounted as read-only whenever possible.

  • Audit of Exceptions: Any existing hostPath mount must be documented with a specific technical justification and approved by the Technology Risk department.

What to Assess

  • Volume Audit: Scan all pods in production namespaces for any volumes of type hostPath.

  • SCC Review: Ensure the restricted and non-root SCCs do not allow the hostPath volume type.

  • System Pod Justification: Review system pods (Monitoring, Logging) to ensure their hostPath usage is limited to the minimum necessary directory.

Technical Rationale

HostPath is the "Doorway to the Host."

  • Prevention of Data Theft: Prevents a container from mounting the host's /etc or /var/lib/etcd and stealing cluster-wide secrets or credentials.

  • Integrity Protection: Prevents a container from modifying host-level configurations (like SSH keys or Cron jobs) to establish persistence.

  • Isolation Enforcement: Ensures that the "Container Boundary" remains intact and that pods remain portable across the cluster.

Verification

  • Validation Method: Cluster-wide volume audit.

Verification Steps:

  1. Search for hostPath:

    oc get pods -A -o json | jq '.items[] | select(.spec.volumes[].hostPath != null) | {name: .metadata.name, ns: .metadata.namespace}'

  2. Check SCC permissions:

    oc describe scc restricted-v2 | grep -i hostpath

  3. Verify Read-Only:

    For any system hostPath, check oc get pod <name> -o yaml for readOnly: true.

Evidence

  • Volume Audit Report: A zero-result list of hostPath mounts in application namespaces.

  • SCC Configuration YAML: Showing allowHostDirVolumePlugin: false.

  • Risk Approval Document: For any authorized system-level hostPath usage.

Risk Impact

  • Critical Risk (Total Host Compromise): Allows an attacker to read/write any file on the physical server, bypassing almost all container security controls.

  • Security Risk: Leads to "Break-out" scenarios where an attacker moves from one container to the host, and then to all other containers.

  • Compliance Risk: Direct violation of CIS Kubernetes Benchmark 5.2.4 and RMiT hardening standards.

Mapping

  • BNM RMiT (2025): Section 11.3 (Hardening).

  • CIS Benchmarks v8: Control 18 (Service Software Continuity).

  • NIST SP 800-53: AC-3 (Access Enforcement); SC-7 (Boundary Protection).

SC-014System Hardening

Secure Container Runtime (CRI-O Hardening)

High

Description

OpenShift uses CRI-O as its native container runtime. Unlike generic Docker, CRI-O is specifically built for Kubernetes and is hardened by default. This control ensures that CRI-O is further restricted to block dangerous Linux capabilities and system calls.

Key Aspects of CRI-O Hardening:

  • Capability Dropping: Automatically dropping all Linux capabilities (e.g., CAP_NET_ADMIN, CAP_SYS_ADMIN) and only allowing the absolute minimum required for a standard process.

  • Seccomp (Secure Computing Mode): Applying a default seccomp profile to every container that filters the system calls (syscalls) the process can make to the kernel.

  • Process Tree Isolation: Ensuring that containers cannot see or interact with processes running on the host or in other containers (PID Namespace isolation).

  • No New Privileges: Ensuring that the no_new_privs flag is set, preventing child processes from gaining more permissions than their parents.

What to Assess

  • Default Seccomp Profile: Verify that pods are running with the RuntimeDefault seccomp profile.

  • Dropped Capabilities: Check the container spec to ensure capabilities: drop: ["ALL"] is enforced by the SCC.

  • CRI-O Config: Audit the /etc/crio/crio.conf file on the nodes for security-specific tuning.

Technical Rationale

The Linux kernel provides thousands of features that containers don't need but attackers can exploit.

  • Attack Surface Reduction: By blocking 90% of available syscalls, seccomp prevents an attacker from exploiting many known (and unknown) kernel vulnerabilities.

  • Hardened Perimeter: Dropping capabilities ensures that even a root-compromised container cannot reconfigure the network or mount new filesystems.

  • Predictable Execution: Ensures the runtime is optimized for performance and security without the "bloat" of legacy container engines.

Verification

  • Validation Method: Pod security context and runtime audit.

Verification Steps:

  1. Check seccomp:

    oc get pod <name> -o jsonpath='{.spec.securityContext.seccompProfile.type}' (Must be RuntimeDefault).

  2. Check capabilities:

    oc exec <pod> -- capsh --print (Should show an extremely limited list).

  3. Verify no-new-privs:

    oc get pod <name> -o jsonpath='{.spec.securityContext.allowPrivilegeEscalation}' (Must be false).

Evidence

  • CRI-O Configuration Snippet: Showing the default security settings.

  • Capsh Output: From a production pod proving that all dangerous capabilities are dropped.

  • Seccomp Profile YAML: Showing the RuntimeDefault policy in use across the cluster.

Risk Impact

  • High Risk (Kernel Exploitation): Without seccomp, an attacker can use obscure syscalls to trigger kernel bugs and gain host-level access.

  • Security Risk: Excess capabilities allow for lateral network movement and unauthorized system modifications within the container.

  • Compliance Risk: Non-compliance with the NIST and CIS guidelines for container runtime security.

Mapping

  • BNM RMiT (2025): Section 11.3 (System Hardening).

  • CIS Benchmarks v8: Control 18 (Service Software Continuity).

  • NIST SP 800-53: SC-39 (Process Isolation).

Description

Direct SSH access to bare-metal OpenShift nodes bypasses the cluster's API-level audit logs and RBAC. This control mandates that SSH access be disabled by default for all personnel and only enabled through a strictly controlled "Break Glass" process.

Key Aspects of SSH Restriction:

  • SSH Key Management: No individual user keys should be present on the nodes. Only a cluster-wide deployment key (stored in a secure vault) is permitted.

  • Firewall Blocking: Port 22 must be blocked at the internal firewall level for all traffic except from designated "Jump Hosts."

  • Audit Logging: Every SSH login attempt (successful or failed) must be forwarded to the centralized SIEM (MO-004).

  • Use of oc debug: Encouraging the use of oc debug node/ which provides a shell via the API server, maintaining the full Kubernetes audit trail.

What to Assess

  • Port 22 Reachability: Perform a scan of the worker and master nodes from a non-authorized network; port 22 must be "Filtered" or "Closed."

  • Authorized Keys Audit: Audit the /root/.ssh/authorized_keys file on nodes to ensure no personal keys are present.

  • SSHD Config: Verify that PermitRootLogin is set to prohibit-password or no and that password authentication is disabled.

Technical Rationale

SSH is an "unmanaged" entry point that can lead to undocumented changes.

  • Prevention of Undocumented Changes: Ensures that no one can manually "fix" a node in a way that isn't captured by the Machine Config Operator (SC-011).

  • Credential Protection: Reduces the risk of "SSH Key Sprawl" where hundreds of developer keys are left on production servers.

  • Accountability: By forcing use of the oc CLI, every action is tied to an authenticated Identity Provider user (SC-002).

Verification

  • Validation Method: Network scan and node-level configuration audit.

Verification Steps:

  2. Check keys:

    oc debug node/<node-name> -- chroot /host cat /root/.ssh/authorized_keys

  3. Verify SSHD config:

    oc debug node/<node-name> -- chroot /host cat /etc/ssh/sshd_config | grep PasswordAuthentication

Evidence

  • Nmap Scan Report: Proving port 22 is unreachable from general corporate networks.

  • SSHD Configuration YAML: Export from the MachineConfig showing the hardened SSH settings.

  • SIEM Alert Sample: A log showing an alert triggered by a "Break Glass" SSH login.

Risk Impact

  • High Risk (Lateral Movement): An attacker with SSH access can easily move between nodes and bypass all container-level security controls.

  • Operational Risk: "Drift" caused by manual SSH edits can cause cluster upgrades to fail or produce inconsistent application behavior.

  • Compliance Risk: Violates RMiT requirements for "Administrator Access Control" and "Auditability of Privileged Actions."

Mapping

  • BNM RMiT (2025): Section 11.2 (User Access Management).

SC-016Infrastructure Security

UEFI Secure Boot Enforcement

Critical

Description

UEFI Secure Boot is a verification mechanism that ensures the bare-metal server only boots software that is trusted by the hardware manufacturer or the organization. This control mandates that Secure Boot be enabled in the physical server BIOS/UEFI settings to protect the boot chain.

Key Aspects of Secure Boot:

  • Signature Verification: The hardware UEFI firmware checks the digital signature of the bootloader (shim), the Linux kernel, and kernel modules before execution.

  • Hardware Root of Trust: Leverages the physical TPM (Trusted Platform Module) or UEFI secure variables to store trusted keys.

  • Protection Against Bootkits: Prevents malicious code (Rootkits/Bootkits) from inserting itself into the boot process before the operating system or OpenShift security layers are active.

  • RHCOS Support: Red Hat Enterprise Linux CoreOS (RHCOS) is fully signed and supports Secure Boot out of the box for bare-metal deployments.

What to Assess

  • BIOS/UEFI Configuration: Physically or via BMC (IPMI/Redfish) verify that "Secure Boot" is set to Enabled.

  • OS Verification: Check the running state on the node to confirm the kernel recognizes it was booted securely.

  • TPM Presence: Confirm that a TPM 2.0 module is present and initialized on all master and worker nodes.

Technical Rationale

In a high-security banking environment, the integrity of the physical server is the foundation of all other security layers.

  • Prevention of Low-Level Attacks: Ensures that an attacker with temporary physical access or firmware-level access cannot subvert the OS by loading a compromised kernel.

  • Integrity Assurance: Guarantees that the "Immutable" OS (SC-011) has not been tampered with before it even finishes booting.

  • Compliance: Directly addresses RMiT requirements for "System Integrity" and the use of trusted hardware foundations.

Verification

  • Validation Method: Node-level boot status audit.

Verification Steps:

  1. Check Secure Boot status:

    oc debug node/<node-name> -- chroot /host mokutil --sb-state (Should return SecureBoot enabled).

  2. Verify kernel lockdown:

    oc debug node/<node-name> -- chroot /host dmesg | grep -i "Secure boot enabled"

  3. Check TPM status:

    oc debug node/<node-name> -- chroot /host ls /dev/tpm0 (Device must exist).

Evidence

  • Mokutil Output: Proving Secure Boot is active across the production fleet.

  • BIOS Configuration Export: A report from the server management tool (e.g., HPE iLO or Dell iDRAC) showing Secure Boot enabled.

  • Kernel Log Snippet: Proof of the kernel entering "Lockdown" mode due to Secure Boot.

Risk Impact

  • Critical Risk (Rootkit Persistence): Without Secure Boot, an attacker can replace the bootloader, gaining total control over the server that is invisible to the OS and OpenShift.

  • High Risk (Unauthorized OS): Allows the booting of unapproved or modified operating systems on banking hardware.

  • Compliance Risk: Fails the RMiT and NIST standards for hardware-based root of trust.

Mapping

  • BNM RMiT (2025): Section 11.3 (System Hardening).

  • CIS Benchmarks v8: Control 4 (Secure Configuration).

  • NIST SP 800-53: SI-7 (Software, Firmware, and Information Integrity).

SC-019Data in Transit

Node-to-Node Encryption (IPsec)

High

Description

While TLS (SC-008) secures traffic from the user to the cluster, Node-to-Node Encryption secures the "East-West" traffic between the bare-metal nodes themselves. Using IPsec within the OVN-Kubernetes CNI, all pod-to-pod traffic is encrypted at the network layer.

Key Aspects of Node Encryption:

  • OVN-K IPsec: A native feature of the OVN-Kubernetes network plugin that encrypts all Geneve-encapsulated tunnels.

  • Automated Key Management: Utilizing the ovn-ipsec daemon to manage and rotate encryption keys automatically.

  • Standard Encryption: Uses AES-GCM for high-performance hardware-accelerated encryption.

  • Transparency: Encryption happens at the network layer; applications do not need any modification to be secured.

What to Assess

  • Cluster Network Config: Verify that ipsec: true is set in the networks.config.openshift.io resource.

  • Daemon Status: Confirm that the ovn-ipsec pods are running on all nodes in the openshift-ovn-kubernetes namespace.

  • Encryption Verification: Use network tools to verify that traffic between nodes is indeed encrypted (ESP packets).

Technical Rationale

In a bare-metal environment, traffic travels over physical top-of-rack switches that could be intercepted.

  • Zero-Trust Networking: Ensures that even if the physical network infrastructure (switches/cables) is compromised, the banking data remains encrypted.

  • Compliance with RMiT Appendix 4: Fulfills the "High" criticality requirement for "Encryption of all sensitive data in transit within the internal network."

  • Defense Against Sniffing: Prevents an attacker with physical access to the network from "sniffing" sensitive inter-service communication.

Verification

  • Validation Method: Configuration audit and packet analysis.

Verification Steps:

  1. Check IPsec setting:

    oc get networks.config/cluster -o jsonpath='{.spec.defaultNetwork.ovnKubernetesConfig.ipsecConfig}'

  2. Check pod status:

    oc get pods -n openshift-ovn-kubernetes -l app=ovn-ipsec

  3. Packet capture:

    (Authorized only) tcpdump -i <interface> esp (Should show Encapsulating Security Payload packets).

Evidence

  • Network Config YAML: Export showing IPsec is enabled.

  • IPsec Status Report: Output of oc rsh into an ovn-ipsec pod showing active security associations (SAs).

  • Security Architecture Diagram: Showing the encrypted tunnels between bare-metal hosts.

Risk Impact

  • High Risk (Internal Eavesdropping): Unencrypted internal traffic allows anyone with network-level access to steal sensitive data as it moves between microservices.

  • Compliance Risk: Immediate non-compliance with RMiT mandates for internal data encryption for critical systems.

  • Performance Risk: While hardware-accelerated, IPsec does add a minor CPU overhead that must be accounted for in capacity planning.

Mapping

  • BNM RMiT (2025): Section 11.1 (Data Integrity); Appendix 4.

  • CIS Benchmarks v8: Control 13 (Network Monitoring and Defense).

  • NIST SP 800-53: SC-8 (Transmission Confidentiality and Integrity).

SC-020Data Protection

Hardware Security Module (HSM) for Master Key Storage

Critical

Description

For the highest level of secret protection, the "Master Key" used to encrypt the etcd database (SC-010) should not reside on the cluster's local disks. This control mandates the use of an external Hardware Security Module (HSM) to store and manage the cryptographic keys.

Key Aspects of HSM Integration:

  • Root of Trust: The encryption key is generated and stored inside a tamper-resistant physical appliance.

  • PKCS#11 / KMIP Integration: Using standard protocols to allow OpenShift to request encryption/decryption operations without the key ever leaving the HSM.

  • Audit Logging: HSMs provide non-repudiable logs of every time the key is accessed.

  • FIPS 140-2 Level 3: Typically, HSMs are certified to a higher physical security standard than standard servers.

What to Assess

  • KMS Provider Config: Verify the APIServer configuration to see if a KMS provider (e.g., Vault with HSM backend) is active.

  • Key Storage Location: Confirm through documentation that the root of trust resides in a physical HSM.

  • Access Control: Verify that only the OpenShift master nodes have the necessary permissions to call the HSM.

Technical Rationale

If the master key is stored on the same servers as the encrypted data, the security is only as good as the server's OS hardening.

  • Physical Protection: Protects the cluster's most sensitive keys from being stolen, even if an attacker has physical access to the bare-metal servers.

  • Regulatory Requirement: Many central banks (including BNM) suggest or require HSMs for the management of keys for critical infrastructure.

  • Logical Separation: Separates the "Key Management" responsibility from the "Infrastructure Management" responsibility.

Verification

  • Validation Method: KMS configuration and HSM log audit.

Verification Steps:

  1. Check KMS config:

    oc get apiserver cluster -o yaml (Look for KMS provider details).

  2. HSM Audit: Request a log export from the HSM administrator showing successful key-access events from the cluster.

  3. Negative Test: Verify that secrets cannot be decrypted if the connection to the HSM is severed.

Evidence

  • KMS Configuration YAML: Snippets showing the integration with the external key manager.

  • HSM Certification: A copy of the FIPS 140-2 Level 3 certificate for the HSM appliance.

  • Audit Log Sample: A log from the HSM showing a successful key wrap/unwrap request.

Risk Impact

  • Critical Risk (Key Theft): Without an HSM, an attacker who compromises the master node's filesystem can potentially steal the decryption keys and unlock all cluster secrets.

  • Compliance Risk: Non-compliance with RMiT requirements for "Secure Key Management" in highly critical systems.

  • Security Risk: Increased risk of key duplication or unauthorized key export.

Mapping

  • BNM RMiT (2025): Section 11.1 (Data Integrity); Section 11.2 (Access Control).

  • CIS Benchmarks v8: Control 3 (Data Protection).

  • NIST SP 800-53: SC-12 (Cryptographic Key Establishment and Management).
