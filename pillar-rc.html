Pillar 2: Recoverability / Disaster Recovery

Architecture assessment page for validating the platform capability to protect cluster state, preserve workload data, orchestrate disaster recovery, and restore business services predictably after infrastructure, storage, application, or site-level failures.

Use note: This page is a consulting assessment artefact for OpenShift architecture and operations review. It is not an official Red Hat methodology. Validate technical statements and command syntax against the target OpenShift version and client environment before use.

Recovery and Continuity define the platform's capability to protect cluster state, preserve workload data, orchestrate disaster recovery, and restore business services predictably after infrastructure, storage, application, or site-level failures. For OpenShift environments supporting containerized workloads and OpenShift Virtualization, these controls validate that etcd, persistent volumes, virtual machine disks, registries, GitOps configuration, and multi-cluster recovery mechanisms are protected through tested, automated, and evidence-backed recovery practices.

Summary of Controls

Pillar 2 contains 9 assessment controls grouped by recovery and continuity domain to support cluster-state restoration, workload data protection, disaster recovery readiness, registry continuity, and automated application recovery.

RC-001Backup and Recovery

etcd Database Backup and Encryption

Critical

Description

The etcd backup is a snapshot of the entire OpenShift cluster state, including all configurations, secrets, and metadata. In the event of a catastrophic control plane failure or data corruption, this backup is the only way to restore the cluster to a functional state.

Key Aspects of etcd Backup:

  • Encryption at Rest: Ensuring the backup file itself is encrypted to prevent sensitive data (like kubeconfig or credentials) from being exposed if the storage media is compromised.

  • Automated Scheduling: Utilizing a CronJob or a dedicated operator to perform daily snapshots of the etcd database.

  • Off-Node Storage: Moving the backup files off the master nodes and into a secure, immutable storage location (e.g., S3-compatible storage or a hardened backup server).

  • Snapshot Validation: Periodically testing the integrity of the backup files to ensure they are not corrupted.

What to Assess

  • Backup Frequency: Verify that backups are occurring at least once every 24 hours.

  • Encryption Status: Confirm that the etcd encryption is enabled within the cluster (

    oc get apiserver cluster -o yaml

  • Storage Location: Verify the secure, external destination where the backup files are being pushed.

Technical Rationale

For regulated financial services compliance, "Recovery of Critical Data" is non-negotiable.

  • Disaster Recovery Foundation: If the etcd quorum is lost (AR-001) and cannot be recovered, the etcd backup is the "Point of No Return" for cluster reconstruction.

  • Regulatory Compliance: Financial regulations mandate that system state and configuration be backed up and stored securely to ensure business continuity.

  • Protection Against Ransomware: Having an encrypted, off-site backup protects the cluster's "DNA" from being encrypted or deleted by a malicious actor.

Verification

  • Validation Method: Resource check and script audit.

Verification Steps:

  1. Check encryption configuration: (Should be aescbc).

    oc get apiserver cluster -o jsonpath='{.spec.encryption.type}'

  2. Verify backup script existence: Inspect the etcd-backup CronJob or script in the openshift-etcd namespace.

  3. Check backup logs:

    oc logs -n openshift-etcd <backup-pod-name>

Evidence

  • etcd Backup Log: A success log from the most recent backup job.

  • Encryption YAML: Export of the apiserver resource showing active encryption.

  • Sample Backup Artefact: A directory listing from the external storage showing timestamped .db files.

Risk Impact

  • Critical Risk (Permanent Cluster Loss): Without an etcd backup, a total control plane failure requires a manual, from-scratch rebuild of the cluster, losing all configuration and history.

  • High Risk (Security Breach): Unencrypted backups on insecure storage allow anyone with access to the file to extract every secret and password in the cluster.

  • Operational Risk: Massive increase in recovery time (MTTR) during a crisis.

Mapping

  • BNM RMiT (2025): Section 11.1 (Data Integrity); Section 15.1 (Backup and Recovery).

  • CIS Benchmarks v8: Control 11 (Data Recovery).

  • NIST SP 800-53: CP-9 (System Backup).

RC-002Backup and Recovery

Workload Data Protection (VMs & PVCs)

Critical

Description

While etcd backs up the cluster state, Workload Data Protection focuses on the persistent data stored by applications (Persistent Volumes) and Virtual Machines. This is typically implemented using the OpenShift API for Data Protection (OADP) and the Velero plugin.

Key Aspects of Workload Protection:

  • Application Consistency: Using "Hooks" to freeze a database or flush a filesystem before a snapshot is taken to ensure data is consistent.

  • PVC Backups: Taking snapshots of the underlying ODF (Ceph) or SAN storage.

  • VM Awareness: Backing up both the VM's disk (PVC) and its metadata (VirtualMachine instance config) so it can be restored as a functioning unit.

  • Cross-Namespace Restore: The ability to restore an application to a different namespace or even a different cluster for DR testing.

What to Assess

  • OADP Status: Verify the OADP Operator is installed and the DataProtectionApplication (DPA) is healthy.

  • Backup Schedule: Check the Schedule resources to confirm critical applications are being backed up regularly.

  • Storage Location: Ensure backups are stored in a separate, resilient location (e.g., MinIO or S3).

Technical Rationale

Application data is the lifeblood of the bank.

  • Transactional Integrity: Ensures that databases can be recovered to a specific point in time without data corruption.

  • Operational Flexibility: Allows for the "Cloning" of production environments into UAT for troubleshooting or testing.

  • Bare-Metal Resilience: In a bare-metal environment, if a local disk fails, this control provides the path to restore the app to a new node.

Verification

  • Validation Method: OADP resource inspection.

Verification Steps:

  1. Check DPA health:

    oc get dpa -n openshift-adp

  2. List current backups:

    oc get backup -n openshift-adp

  3. Verify restore test: Review records of the most recent successful restore test.

Evidence

  • OADP DPA YAML: The configuration for the data protection application.

  • Backup Completion Report: Output of

    velero backup get

  • Restore Log: A log showing a successful test restore of a sample application.

Risk Impact

  • Critical Risk (Total Data Loss): In the event of a storage-level disaster, without application-level backups, customer transaction data is permanently lost.

  • High Risk (Recovery Failure): Backups that are not application-consistent may result in corrupted databases that cannot be started after restore.

  • Compliance Risk: May result in non-compliance with regulatory requirements for business continuity management.

Mapping

  • BNM RMiT (2025): Section 15.1 (Backup and Recovery).

  • CIS Benchmarks v8: Control 11 (Data Recovery).

  • NIST SP 800-53: CP-9 (System Backup).

RC-003Backup and Recovery

CSI Volume Snapshots

High

Description

CSI (Container Storage Interface) Volume Snapshots provide a rapid, storage-level point-in-time copy of a Persistent Volume. Unlike a full backup (which moves data to an external site), a snapshot is typically stored on the same storage system (e.g., ODF/Ceph) for near-instant recovery.

Key Aspects of CSI Snapshots:

  • VolumeSnapshotClass: A declarative template that defines how snapshots are created on the specific storage hardware.

  • Incremental Efficiency: Snapshots are usually incremental, meaning they only consume additional space for data that has changed.

  • Self-Service Recovery: Allows application owners to revert their own data to a previous state without involving the storage administrator.

  • Snapshot Content: Represents the raw block-level state of the volume at a specific second.

What to Assess

  • SnapshotClass: Verify a VolumeSnapshotClass exists and is correctly mapped to the ODF or SAN provisioner.

  • Snapshot Usage: Audit if critical applications are actually utilizing VolumeSnapshot resources before high-risk changes.

  • Retention Policy: Ensure that old snapshots are automatically pruned to prevent storage exhaustion (CO-004).

Technical Rationale

Time-to-recovery (TTO) is critical during operational errors.

  • Instant Rollback: If a software update corrupts a database, a CSI snapshot allows the team to roll back the disk in seconds, rather than waiting hours for a full backup restore.

  • Foundation for Backup: OADP (RC-002) uses CSI snapshots as the primary mechanism to "freeze" data before moving it to long-term storage.

  • Reduced Performance Impact: Because they happen at the storage layer, CSI snapshots have minimal impact on application performance compared to file-based backups.

Verification

  • Validation Method: Resource check.

Verification Steps:

  1. Check snapshot classes:

    oc get volumesnapshotclass

  2. View active snapshots:

    oc get volumesnapshot -A

  3. Verify snapshot readiness: (Check for ReadyToUse: true).

    oc describe volumesnapshot <name>

Evidence

  • VolumeSnapshotClass YAML: The definition of the snapshot class.

  • VolumeSnapshot Snapshot: A listing of active snapshots with timestamps.

  • Recovery Test Report: Documentation showing a successful volume restoration from a snapshot.

Risk Impact

  • High Risk (Delayed Recovery): Without snapshots, the only path to recovery is a full restore from off-site storage, which may take hours, violating RTO targets.

  • Operational Risk: Lack of "safety nets" during application upgrades or patching cycles.

  • Storage Risk: Unmanaged snapshots can fill up the storage cluster, triggering a "Read-Only" state for the whole cluster.

Mapping

  • BNM RMiT (2025): Section 10.4 (Recovery Time Objective).

  • CIS Benchmarks v8: Control 11 (Data Recovery).

  • NIST SP 800-53: CP-9 (System Backup); CP-10 (System Recovery).

RC-004Infrastructure Resilience

Node Recovery Strategy (Pets vs. Cattle)

High

Description

This control defines the operational procedure for recovering a bare-metal node. In a "Well-Architected" OpenShift environment, nodes should be treated as Cattle, meaning they are disposable and can be automatically re-provisioned from a known image, rather than being manually repaired like Pets.

Key Aspects of Node Recovery:

  • Infrastructure-as-Code (IaC): Ensuring the node's physical configuration (PXE boot, BIOS settings) is automated via tools like Ironic (Machine API) or Ansible.

  • Fast Re-imaging: The ability to wipe a failing node and have it rejoin the cluster with all security and networking configurations (NMState - AR-024) applied automatically.

  • Disposable OS: Utilizing Red Hat Enterprise Linux CoreOS (RHCOS) which is immutable and designed for "replace rather than repair" operations.

  • Hardware Standardization: Ensuring all nodes in a pool are identical to make the "Cattle" model predictable.

What to Assess

  • Provisioning Automation: Verify the method used to install the nodes (e.g., Assisted Installer, PXE/Ironic).

  • Node Immutability: Confirm that no manual changes (e.g., manual SSH edits to /etc) are being performed on the nodes.

  • Recovery Time: Assess the time it takes for a node to be re-imaged and marked as Ready.

Technical Rationale

Bare-metal hardware will eventually fail.

  • Elimination of Configuration Drift: Re-imaging a node ensures it is 100% clean and matches the cluster's current security baseline.

  • Simplified Maintenance: If a node has a mysterious kernel error, the solution is a 10-minute automated re-image rather than 4 hours of manual troubleshooting.

  • Scalability: The same process used for recovery is used to add new capacity to the cluster.

Verification

  • Validation Method: Process audit and Machine API inspection.

Verification Steps:

  1. Check Machine status:

    oc get machines -n openshift-machine-api

  2. Verify RHCOS Version: (Should show identical OS versions).

    oc get nodes -o wide

  3. Review provisioning logs: Check the logs of the machine-api-operator during a node replacement.

Evidence

  • MachineSet YAML: The template used to generate new nodes.

  • Ignition Configs: The configuration files used during node boot-up to set up networking and security.

  • Provisioning Success Report: Documentation showing a node being replaced automatically.

Risk Impact

  • High Risk (Operational Slowness): Treating bare-metal nodes as "Pets" leads to long recovery times and inconsistent configurations.

  • Security Risk: Manually repaired nodes may contain "residue" or unpatched configurations that don't match the rest of the cluster.

  • Operational Risk: Increases the burden on sysadmins and makes the cluster difficult to scale.

Mapping

  • BNM RMiT (2025): Section 10.1 (Operations Management); Section 10.6 (Maintenance).

  • CIS Benchmarks v8: Control 18 (Service Software Continuity).

  • NIST SP 800-53: SI-2 (Flaw Remediation); CM-3 (Configuration Change Control).

RC-005Disaster Recovery

Multi-Cluster / Site-to-Site DR

Critical

Description

For critical banking services, a single cluster failure (due to a data center outage) must be mitigated by a Multi-Cluster Disaster Recovery strategy. This involves maintaining a second OpenShift cluster at a geographically separate site and orchestrating the failover of data and applications.

Key Aspects of Site-to-Site DR:

  • Active-Passive vs. Active-Active: * Active-Passive: The DR site is idle until a failover is triggered.

  • Active-Active: Both sites serve traffic simultaneously, providing better utilization and zero-second failover.

  • Global Load Balancing (GSLB): An external mechanism that routes user traffic to Site A or Site B based on health and proximity.

  • Data Mirroring: Ensuring persistent data is synchronized between sites (e.g., via ODF Regional DR or synchronous storage replication).

  • Governance: Using Red Hat Advanced Cluster Management (RHACM) to manage policies and applications across both sites from a single pane of glass.

What to Assess

  • DR Strategy Documentation: Confirm the RPO/RTO targets are defined and the architecture (Active-Active/Passive) matches.

  • Data Replication Health: Verify the status of storage mirroring between sites (e.g., Ceph RBD Mirroring).

  • RHACM Integration: Confirm both clusters are managed by a central RHACM hub.

Technical Rationale

Regulatory expectations require critical systems to have an off-site recovery capability.

  • Survival of Data Center Disaster: Protects the bank's services from floods, power grid failures, or fires at the primary site.

  • Compliance with RPO/RTO: Provides the technical framework needed to meet the strict Recovery Point Objective (RPO) and Recovery Time Objective (RTO) targets.

  • Business Continuity: Ensures that customers can still access banking services even during a major regional infrastructure crisis.

Verification

  • Validation Method: RHACM and Storage audit.

Verification Steps:

  1. Check Managed Clusters: (on the RHACM Hub).

    oc get managedclusters

  2. Verify Mirroring:

    oc get cephblockpool <name> -n openshift-storage -o jsonpath='{.status.mirroringStatus}'

  3. Test Failover: Review the results of the most recent annual "DR Drill."

Evidence

  • RHACM Dashboard: Screenshot showing all clusters as "Ready."

  • Storage Replication Log: Proof that data is being synchronized within the required RPO time (e.g., every 5 minutes).

  • DR Test Report: A formal report detailing a successful application failover between sites.

Risk Impact

  • Critical Risk (Business Failure): A total loss of the primary data center without a DR site results in a complete and prolonged shutdown of all banking services.

  • Compliance Risk: May result in non-compliance with regulatory disaster recovery requirements.

  • Reputational Risk: Massive loss of customer trust during an extended outage.

Mapping

  • BNM RMiT (2025): Section 15.2 (Disaster Recovery Site); Section 15.3 (DR Testing).

  • CIS Benchmarks v8: Control 11 (Data Recovery).

  • NIST SP 800-53: CP-6 (Alternate Storage Site); CP-7 (Alternate Processing Site).

RC-006Recovery Orchestration

GitOps Application Recovery

High

Description

GitOps Application Recovery utilizes OpenShift GitOps (ArgoCD) to maintain the "Desired State" of applications in a Git repository. In a recovery scenario, the cluster does not rely on manual backups of YAML files; instead, ArgoCD automatically synchronizes the cluster state with the configuration stored in Git.

Key Aspects of GitOps Recovery:

  • Declarative Source of Truth: Every Deployment, Service, and Route is defined in Git. If a namespace is deleted, ArgoCD detects the "Out of Sync" status and recreates the entire stack.

  • Automated Drift Correction: Prevents manual, undocumented changes ("Snowflakes") from persisting in the environment, ensuring the recovered application is identical to the original production version.

  • Cluster Bootstrapping: Allows a brand-new bare-metal cluster to be fully populated with all banking applications in minutes simply by pointing ArgoCD to the "Production" repository.

  • Version Control Recovery: Allows for "Point-in-Time" recovery of the application configuration by rolling back to a previous Git commit.

What to Assess

  • ArgoCD Installation: Verify the OpenShift GitOps Operator is installed and the ArgoCD instance is healthy.

  • Application Synchronization: Confirm that critical banking applications are managed as "Application" objects in ArgoCD.

  • Sync Policy: Verify that automated: selfHeal: true is enabled for production workloads.

Technical Rationale

Manual recovery is slow and prone to human error during a high-pressure disaster event.

  • Zero-Knowledge Recovery: An engineer does not need to remember how an app was configured; they only need to ensure the GitOps controller is running.

  • Rapid MTTR: Reduces the Mean Time to Recovery from hours (searching for backup tapes/files) to minutes (automated synchronization).

  • Audit Trail: Provides a complete audit history (via Git logs) of every configuration change leading up to the disaster.

Verification

  • Validation Method: ArgoCD resource audit and synchronization test.

Verification Steps:

  1. Check ArgoCD status:

    oc get argocd -n openshift-gitops

  2. List managed applications: argocd app list (or

    oc get applications -n openshift-gitops

  3. Verify sync status: (Should be Synced).

    oc get application <app-name> -n openshift-gitops -o jsonpath='{.status.sync.status}'

Evidence

  • ArgoCD Application YAML: Snippet showing the source Git repo and the automated sync policy.

  • Git Commit History: Logs showing the "Desired State" changes over time.

  • Synchronization Report: A screenshot of the ArgoCD dashboard showing all green "Synced" and "Healthy" status for the banking suite.

Risk Impact

  • High Risk (Configuration Inconsistency): Without GitOps, a recovered application may have missing environment variables or incorrect secrets, leading to functional failures after "recovery."

  • Operational Risk: Recovery becomes dependent on specific individuals who "know" how the system was set up, creating a single point of failure in the human team.

  • Compliance Risk: Lack of a verifiable, automated path from "Source" to "Running State" may result in non-compliance with regulatory expectations for change management and resilience.

Mapping

  • BNM RMiT (2025): Section 10.1 (Operations Management); Section 15.3 (DR Testing).

  • CIS Benchmarks v8: Control 18 (Service Software Continuity).

  • NIST SP 800-53: CM-3 (Configuration Change Control); CP-10 (System Recovery).

RC-007Data Resilience

Image Registry Protection

Critical

Description

The Image Registry is a critical component that stores the container images required to boot every application in the cluster. Image Registry Protection ensures that the registry's backend storage is resilient and that the registry service itself can be recovered quickly during a disaster.

Key Aspects of Registry Protection:

  • Persistent Storage Backend: Ensuring the registry uses a Persistent Volume (typically ODF/Ceph with RWX) rather than ephemeral local storage.

  • Registry Snapshots: Taking regular CSI snapshots (RC-003) of the registry's storage bucket/volume.

  • Read-Only Mode for DR: The ability to put the registry into a read-only state during a storage migration to prevent data corruption.

  • High Availability: Running multiple replicas of the registry pod across different infra nodes (AR-019).

What to Assess

  • Storage Provider: Verify the registry is using a supported persistent storage (e.g., registry-storage PVC).

  • Replica Count: Confirm the registry is running at least 2 replicas.

  • Backup Status: Ensure the registry's PVC is included in the OADP (RC-002) backup schedule.

Technical Rationale

If the registry is lost, the cluster cannot restart any pods because it cannot pull the underlying images.

  • Foundation for Recovery: During a node failure, the new node must pull the image from the registry. If the registry is down, the node stays empty.

  • Internal Dependency Management: OpenShift relies on the internal registry for build-time artifacts and "ImageStreams."

  • RPO for Software Assets: Ensures that the specific versions of software currently running in production are preserved and can be redeployed.

Verification

  • Validation Method: Registry operator and storage audit.

Verification Steps:

  1. Check registry config: (Check managementState and storage).

    oc get configs.imageregistry.operator.openshift.io/cluster -o yaml

  2. Verify replicas:

    oc get deployment image-registry -n openshift-image-registry

  3. Confirm PVC:

    oc get pvc -n openshift-image-registry

Evidence

  • Registry Configuration YAML: Export showing managementState: Managed and the pvc storage backend.

  • PVC Snapshot Log: Proof that the registry storage is being snapshotted daily.

  • Pod Placement Report: Showing registry replicas distributed across multiple nodes.

Risk Impact

  • Critical Risk (Cluster Boot Failure): If the registry storage is lost, no applications can start after a cluster reboot, leading to a permanent outage until images are manually re-pushed.

  • Operational Risk: "ImagePullBackOff" errors during node maintenance, preventing the cluster from self-healing.

  • Performance Risk: Single-replica registries become a bottleneck during large-scale application deployments or scaling events.

Mapping

  • BNM RMiT (2025): Section 10.3 (Availability and Resilience); Section 15.1 (Backup and Recovery).

  • CIS Benchmarks v8: Control 11 (Data Recovery).

  • NIST SP 800-53: CP-9 (System Backup).

RC-008Disaster Recovery

Automated Multi-Cluster Failover (RHACM Orchestration)

Critical

Description

Automated Multi-Cluster Failover uses Red Hat Advanced Cluster Management (RHACM) and the DR Policy to orchestrate the movement of workloads between a primary and a secondary site. This control automates the decision and action phase of a disaster recovery event.

Key Aspects of RHACM Failover:

  • DRPolicy Definition: A declarative policy that links two clusters and defines the replication schedule, such as synchronous or asynchronous replication.

  • One-Click Failover: A centralized RHACM console action that triggers workload movement from Site A to Site B in a controlled and repeatable manner.

  • Health Monitoring: RHACM continuously monitors managed clusters and flags the appropriate recovery posture when the primary site becomes unavailable.

  • Automatic DNS Update: Integration with external load balancers or DNS automation to redirect application traffic after failover is completed.

What to Assess

  • RHACM Hub Health: Verify that the RHACM hub cluster is running and monitoring both production and DR clusters.

  • DR Policy Status: Confirm that DRPolicy resources exist and that peer readiness is reported as healthy.

  • Application Placement: Verify that protected applications are assigned to placements that include both primary and recovery sites.

  • Failover Readiness: Review whether the failover workflow has been tested and whether required dependencies such as secrets, routes, storage replication, and DNS updates are included.

Technical Rationale

Manual failover of large application estates across two sites is too complex and error-prone to rely on during a high-pressure disaster event.

  • Elimination of Human Latency: Automates the reconfiguration of routes, secrets, volumes, placements, and application activation at the DR site.

  • Predictable RTO: Provides a consistent and repeatable recovery process, supporting defined Recovery Time Objectives (RTO).

  • DR Drill Simplicity: Allows DR exercises to be performed with lower manual effort and stronger evidence capture for governance and audit reporting.

Verification

  • Validation Method: RHACM console review, CLI inspection, and DR drill evidence review.

Verification Steps:

  1. Check DRPolicies:

    oc get drpolicies -A

  2. Check DRPlacementControl:

    oc get drplacementcontrol -n <app-namespace>

    Verify that the phase is available and the current active site is correctly reported.

  3. Verify data synchronization: Review the last schedule time or replication status to confirm that replicated data is within the approved RPO.

  4. Review failover test results: Confirm that a recent DR drill completed successfully and that failback or recovery validation was documented.

Evidence

  • RHACM DR Dashboard: Screenshot showing protected status for critical applications.

  • DRPlacementControl YAML: Export showing failover history, current active site, and placement configuration.

  • DRPolicy YAML: Export showing replication scheduling and cluster pairing.

  • Failover Log: Report from the most recent DR drill showing the automated sequence of events and recovery outcome.

Risk Impact

  • Critical Risk (RTO Breach): Manual failover is prone to errors such as missing secrets, incorrect IP addresses, incomplete routes, or failed volume attachments, leading to failed recovery and breach of RTO targets.

  • Operational Risk: Configuration drift between Site A and Site B may mean the recovery site cannot support the production workload during an actual disaster.

  • Compliance Risk: Inability to provide automated failover evidence for high-priority critical systems weakens disaster recovery assurance and audit defensibility.

Mapping

  • BNM RMiT (2025): Section 15.2 (DR Site); Section 15.3 (DR Testing).

  • CIS Benchmarks v8: Control 11 (Data Recovery).

  • NIST SP 800-53: CP-7 (Alternate Processing Site).

RC-009Disaster Recovery

Registry Geo-Replication (Red Hat Quay synchronization)

High

Description

While RC-007 protects the internal registry, Registry Geo-Replication utilizes Red Hat Quay as an enterprise-grade external registry that automatically synchronizes image data across different geographical sites (Primary and DR).

Key Aspects of Geo-Replication:

  • Bidirectional Sync: Quay ensures that if an image is pushed to the Primary site, it is automatically replicated to the DR site over the WAN.

  • Global Namespace: Applications at both sites pull from the same "Logical" registry, ensuring that the image tags and digests match perfectly.

  • Backend Storage Mirroring: Syncing the underlying S3 or block storage between sites.

  • Site Autonomy: If the connection between sites is lost, the DR site can still function using its local copy of the images.

What to Assess

  • Quay Deployment: Verify Red Hat Quay is installed in a highly available, multi-site configuration.

  • Replication Status: Confirm that the Quay "Repository Mirroring" or "Geo-replication" logs show success.

  • Storage Provider: Verify that the underlying storage (e.g., ODF) is configured for inter-site replication (RC-005).

Technical Rationale

Image availability is a prerequisite for site failover.

  • Zero-Download Failover: During a disaster, the DR cluster doesn't need to pull images from the "dead" primary site or the internet; everything is already local.

  • Consistent Software State: Guarantees that the exact binary running in Site A is available at Site B, preventing "version mismatch" during recovery.

  • WAN Optimization: Replication happens in the background, rather than as a burst of traffic during a crisis, protecting the bank's inter-site bandwidth.

Verification

  • Validation Method: Quay Management Console and Storage audit.

Verification Steps:

  1. Check Quay health:

    oc get quayregistry -n quay-enterprise

  2. Verify replication logs: Access the Quay UI and check the "Mirroring" tab for critical repositories.

  3. Test local pull: On a node in the DR site, attempt to pull a production image from the local Quay instance.

Evidence

  • Quay Registry YAML: Showing the geo-replication and mirror configurations.

  • Replication Sync Report: A screenshot or log showing all production images are "In-Sync" across sites.

  • DR Pull Test Log: Output of a successful

    podman pull from the DR site's registry

Risk Impact

  • High Risk (Delayed Site Boot): Without geo-replication, the DR site must pull thousands of layers from a remote location during a failover, potentially crashing the inter-site link or failing to boot in time.

  • Operational Risk: Mismatch in image versions between sites can lead to unpredictable application behavior or security vulnerabilities during a DR event.

  • Compliance Risk: May result in non-compliance with regulatory expectations for data availability and DR site readiness.

Mapping

  • BNM RMiT (2025): Section 10.3 (Availability and Resilience); Section 15.2 (DR Site).

  • CIS Benchmarks v8: Control 11 (Data Recovery).

  • NIST SP 800-53: CP-6 (Alternate Storage Site).
